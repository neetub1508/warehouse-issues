not sellable.

### 1 · Performance targets, stated (`FR-422`)

- **One million ledger rows per day at peak** for a large third-party site.
- The ledger grid's pagination must survive `OFFSET` depth at 100M rows — **it does not**
  (`PD-D2`/`PP-7`). v1 ships an **enforced date-range filter**, which is cheap and honest; keyset/seek
  paging is v1.1.
- Export beyond 10,000 rows: `BaseExportService.DEFAULT_MAX_EXPORT_ROWS = 10_000` and the target is
  100,000. **Raising the constant solves only the first of three problems** — the transaction is held
  open for the duration, and a per-cell style blows the 64k Excel cell-style limit **at scale, not in
  dev** (`PD-D3`/`PP-6`). The answer is a **streaming** export path (`Stream<T>` with a fetch size,
  written straight to the output) **in `warehouse-base`**, and a *separate* proposal to extract it to
  platform. Do not couple the two. Built in `P2-29`; the target is stated here.
- Filter-aware statistics over ledger-sized tables are **rollup tables maintained by the same job
  that proves `L-4`** — decided *with* the reconciliation design, not after it — and **never** a
  `statistics.*` cache name (`FR-395`, `PD-D4`/`PP-8`).

### 2 · The partition and archive strategy, at design time (`FR-423` is `P0-02`'s; the strategy is here)

`whb_stock_movements` is `PARTITION BY RANGE` monthly with an automatic partition-creation job.
**Archiving is a transaction** (`FR-023`, owned later): for each surviving position tuple it writes an
`OPENING_BALANCE` movement dated at the cut-off, **then** moves the archived rows. Stating it now is
what stops someone writing a `DELETE`-based archiver in v2.

### 3 · The mobile-decision-per-screen contract (`FR-218`, `D-13`)

**A mobile decision is stated per screen with a reason, and silence is a defect.** Where no mobile
counterpart is built, the contract says so and says why. This task ships the **register**: every
`WS-nnn` in `BUILD-SPEC-SCREENS.md` has a mobile cell, and a blank cell fails review.

Note the correction to CLAUDE.md found by R1 `CM-1`: `mobile/…/ListHeader.tsx:210-218` **now**
supports `type?: 'dropdown' | 'text'` — **date filters are still unsupported** (`C-044`). Every
warehouse mobile grid therefore replaces a date range with a bounded **dropdown**
(`expiringWithinDays`, `occurredWithin`, `receivedWithin`, `inTransitOverDays`), resolved to a range
on the backend. That divergence is deliberate and is what `D-13` means by *"apply the equivalent
behaviour within those constraints"*.

**Registry-backed fields on mobile (`FR-382`, `RL-009`).** *A registry-backed field is
`z.string().min(1)` validated against the fetched dropdown list, never a `z.enum`. A `z.enum` literal
containing a seeded registry code fails CI.* `mobile/src/schemas/common.schemas.ts` carries 36
`z.enum` literals today. An adapter's seed row would pass the web and fail a handheld save silently,
and handhelds update on an MDM schedule, so the lag is a release cycle. `PC-67` carries the same
sentence, and every task already citing `FR-382` inherits it.

**Versioning the endpoints handhelds call (`RL-017`)** is a v1.1 rule owned by **`P3-04`**. Every
management endpoint a mobile screen calls becomes additive-only under `PORT…` §10.2, and
`warehouse.mobile.min_app_version` is checked at login and sync with `426 CLIENT_UPGRADE_REQUIRED`.
It is not restated here.

### 4 · Offline behaviour, decided per screen (`FR-221`)

**Read-cached** lists for putaway and pick; **queued writes** with a **per-scan idempotency key** and
a device-supplied `occurred_at`. v1 is **online-only and says so**; the irreversible half — the key —
ships in `P0-08` (`FR-047`, `PP-12`).

### 5 · The platform restore task, filed with an owner (`FR-429`, `PP-1`)

`grep -c -i "restore" DatabaseBackupService.java` → **0**. `pg_dump`, retention, cleanup, history and
download URLs all exist; there is **no restore method, no WAL archiving, no point-in-time recovery,
no restore-verification job and no stated RPO/RTO.**

**This is platform's to build, and it must be filed now rather than assumed.** It does not compete
with warehouse engineers, which is exactly why it gets forgotten. **Warehouse's fallback if it does
not arrive is not a workaround — it is a disclosure:** the product ships with a **written** RPO/RTO of
"unknown" in the install guide and the customer decides. A statutory stock ledger whose backup cannot
be restored does not satisfy the Rule 56 / 3CD reproducibility obligation.

### 6 · Support impersonation — the split (`PP-4`)

`grep -ril "impersonat"` → **5 files, all in `accounting-base`, all the audit schema anticipating
it.** There is **no feature**. The **feature is platform's**; the **column is warehouse's and it is
v1** — `on_behalf_of_actor_id` on the movement and the audit event, `P0-13`. Without the feature the
column is always null; without the column, **year one cannot answer the question, forever.**

## Traps

- **`PP-6`, `PP-7`, `PP-8`, `PP-10`, `PP-11` and `PP-12` are routinely mistaken for platform gaps and
  are ours** (plan §6). Naming the owner wrongly is how a blocker sits unclaimed for a release. Only
  **`PP-1` (restore)** is platform's, and `PP-2` (the service principal, `OD-8`) and `PP-3`
  (mobile date filters) are platform-adjacent.
- **Do not edit `BaseExportService` to raise the row cap.** Add the streaming path in
  `warehouse-base` and propose the platform extraction separately (`PD-D3`).
- **Do not register a `statistics.*` cache name for a filter-aware strip.** The repository already
  records that exact mistake at `CacheConfiguration.java:190-196` (issues
  `neetub1508/classic#790`, `#791`): the names cached nothing while reading as though they did.
- **`FLYWAY_OUT_OF_ORDER=true` is required for a warehouse-first install that later adds a
  vertical.** The effective Docker setting is `false` (`docker-compose.yml:183`,
  `startX2.sh:200`), only `start.sh --restore-backup` flips it, and it persists the flip to `.env`
  (`start.sh:367`, `:785`) (`C-046`). **State it in the install guide; it is not discoverable.**
- **A performance target with no measurement is decoration.** Each number here needs a test or a
  stated measurement method, or it will be quoted in a sales conversation and discovered in
  production.
- **Do not run `mvn`, `npm` or `tsc` to "verify".** There is no usable local toolchain; the project
  builds only in Docker. Verification is by reading, grep and diff against the canonical references
  (`DECISIONS.md` §7 rule 6).
