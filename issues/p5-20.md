## This task is what `A-3` bought

`DECISIONS.md` §5.1 `A-3` put the **variant model in v1 schema** and the **matrix screens in v2**, on the
argument that a flat SKU model is *unrecoverable* — it is a re-keying of the item master and every
movement that references it — and that apparel and footwear is the largest Indian segment we would
otherwise decline. `whb_items.style_item_id` and `variant_axis_1/2/3_value_id`, plus
`whb_item_variant_axes` and `whb_item_variant_axis_values` (`V500014`), all shipped in v1.
**This task spends that concession, and it is the only reason the segment is servable at v2 at all.**

## Scope

- **WS-032 — Variant Axes & Values.** An axis a style varies along — SIZE, COLOUR, FIT — with
  `is_ordered` so **a size scale is an axis whose values are ordered**, and its values with `sort_order`.
- **WS-033 — Style × Variant Matrix.** The matrix screen over `style_item_id` and the three axis-value
  columns: one style, N variants, quantities per cell, from the v1 schema unchanged.
- **Ratio and assortment packs.** A **pack template naming a quantity per variant**, received and shipped
  as **one line** and **exploded into variant-level movements** — *so a carton of "2 small, 4 medium,
  4 large" is one scan and eight units of ledger truth.*
- The explosion is a **movement with N lines**, one per variant, conserving quantity — never one line with
  a pack quantity that a report has to unpick later.

## Traps

- **✅ CLOSED 2026-09-02 — this task had no migration and needed one** (`IMPLEMENTATION-PLAN.md` §2.7
  defect). The variant *axes* exist (`V500014`) and the *style* pointer exists on `whb_items` — but
  **the pack template naming a quantity per variant had no table anywhere in `DATA-MODEL.md`**. It
  cannot be an item attribute (a template spans N variants) and it cannot be
  `whb_item_packaging_levels` (that is a pack hierarchy of **one** item). `whb_ratio_pack_templates` +
  `whb_ratio_pack_template_lines` are now `DATA-MODEL.md` §2.1.5 rows allocated to **`WHB-64`,
  `V500064`** — the first number of §7.2's declared `V500064`–`V500199` post-v1 base DDL gap — and this
  task's header claims it. Read the two rows before writing the DDL; do not re-derive the shape.
- **The explosion is N lines on one movement, not N movements.** One physical act, one movement — that is
  `D-4`. N movements makes the receipt un-reversible as a unit and breaks the one-scan promise.
- **Conservation is per `(owner, item, lot, serial, duty status)`** (`L-1`) — and each variant is a
  **different item**, so the movement balances per variant against the virtual receipt location, not in
  aggregate across the pack. Check `whb_movement_types.balance_rule` is `MUST_BALANCE_PER_OWNER_ITEM` for
  the receipt type; `MUST_BALANCE_PER_MOVEMENT` would let a mis-specified pack balance itself out.
- **`uk(owner_id, sku)`, never a global unique SKU** (`P1-01`, `PNR-4`). A ratio pack for two different
  owners is two template sets, not a shared one.
- **The matrix screen is not a grid.** WS-033 carries no `gridIdentifier` (`BUILD-SPEC-SCREENS.md` §1
  marks it `—` / `N`), so it gets **no** `grid_column_definitions`, **no** `filter_definitions` and **no**
  `COMMON_FILTER_CONFIGS` scope. WS-032 is a `D`-shaped master and does.
- **An ordered axis is ordered by `sort_order`, never alphabetically.** `S`, `M`, `L`, `XL` sorts to
  `L`, `M`, `S`, `XL` in every locale, and a size scale rendered in that order is the first thing an
  apparel customer notices.
- **Frontend filenames must be globally unique** — `Dockerfile.frontend:80-177` merges module `src/`
  last-write-wins (R1 `C-012`). `VariantMatrix.tsx` will collide; `WhVariantMatrix.tsx` will not.
