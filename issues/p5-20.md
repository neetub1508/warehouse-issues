## This task is what `A-3` bought

`DECISIONS.md` §5.1 `A-3` put the **variant model in v1 schema** and the **matrix screens in v2**, on the
argument that a flat SKU model is *unrecoverable* — it is a re-keying of the item master and every
movement that references it — and that apparel and footwear is the largest Indian segment we would
otherwise decline. `whb_items.style_item_id`, `whb_item_variant_axes` and `whb_item_variant_axis_values`
(`V500014`), plus `whb_style_variant_axes` and `whb_item_variant_values` (`V500015`), all shipped in v1;
the three fixed `variant_axis_1/2/3_value_id` slots were dropped for that junction (`RG-009`).
**This task spends that concession, and it is the only reason the segment is servable at v2 at all.**

## Scope

- **WS-032 — Variant Axes & Values.** An axis a style varies along — SIZE, COLOUR, FIT — with
  `is_ordered` so **a size scale is an axis whose values are ordered**, and its values with `sort_order`.
- **WS-033 — Style × Variant Matrix.** The matrix screen over `style_item_id`, the style's axes in
  `whb_style_variant_axes.sequence` order and each variant's value per axis in `whb_item_variant_values`
  — never three axis-value columns (`RG-009`): one style, N variants, quantities per cell, from the v1
  schema unchanged.
- **Ratio and assortment packs.** A **pack template naming a quantity per variant**, received and shipped
  as **one line** and **exploded into variant-level movements** — *so a carton of "2 small, 4 medium,
  4 large" is one scan and eight units of ledger truth.*
- The explosion is a **movement with N lines**, one per variant, conserving quantity — never one line with
  a pack quantity that a report has to unpick later.

## Traps

- **✅ CLOSED 2026-09-02 — this task had no migration and needed one** (`IMPLEMENTATION-PLAN.md` §2.7
  defect). The variant *axes* exist (`V500014`) and the *style* pointer exists on `whb_items` — but
  **the pack template naming a quantity per variant had no table anywhere in `DATA-MODEL.md`**. It
  cannot be an item attribute (a template spans N variants) and it cannot be
  `whb_item_packaging_levels` (that is a pack hierarchy of **one** item). `whb_ratio_pack_templates` +
  `whb_ratio_pack_template_lines` are now `DATA-MODEL.md` §2.1.5 rows allocated to **`WHB-64`,
  `V500090`** — inside §7.2's declared post-v1 base DDL gap; the gap's first number was taken by the
  `P3-16` remediation before this task ran (`DESIGN-SET-DEFECTS.md` `X-061`) — and this
  task's header claims it. Read the two rows before writing the DDL; do not re-derive the shape.
- **The explosion is N lines on one movement, not N movements.** One physical act, one movement — that is
  `D-4`. N movements makes the receipt un-reversible as a unit and breaks the one-scan promise.
- **Conservation is per `(owner, item, lot, serial, duty status)`** (`L-1`) — and each variant is a
  **different item**, so the movement balances per variant against the virtual receipt location, not in
  aggregate across the pack. Check `whb_movement_types.balance_rule` is `MUST_BALANCE_PER_OWNER_ITEM` for
  the receipt type; `MUST_BALANCE_PER_MOVEMENT` would let a mis-specified pack balance itself out.
- **`uk(owner_id, sku)`, never a global unique SKU** (`P1-01`, `PNR-4`). A ratio pack for two different
  owners is two template sets, not a shared one.
- **The matrix screen is not a grid.** WS-033 carries no `gridIdentifier` (`BUILD-SPEC-SCREENS.md` §1
  marks it `—` / `N`), so it gets **no** `grid_column_definitions`, **no** `filter_definitions` and **no**
  `COMMON_FILTER_CONFIGS` scope. WS-032 is a `D`-shaped master and does.
- **The variant junction is deliberately undated** (`RG-009`, R22 §1.3 rule 6). A variant whose size
  changes is a different item, so the matrix never reads a variant's value "as of" a date (`RG-009`).
- **An ordered axis is ordered by `sort_order`, never alphabetically.** `S`, `M`, `L`, `XL` sorts to
  `L`, `M`, `S`, `XL` in every locale, and a size scale rendered in that order is the first thing an
  apparel customer notices.
- **Frontend filenames must be globally unique** — `Dockerfile.frontend:80-177` merges module `src/`
  last-write-wins (R1 `C-012`). `VariantMatrix.tsx` will collide; `WhVariantMatrix.tsx` will not.
- **Decided while building (W3 driver, 2026-09-26).** A ratio-pack template is a template, so `OD-3` applies: it
  is **exportable and importable** — not as a grid export (WS-033 is not a grid) but as the `P5-21` transfer pair:
  `whb_ratio_pack_templates:export` serves `GET …/variant-matrix/templates/export-import-file` in the
  `WHB_RATIO_PACK_TEMPLATE` import kind's own columns (one row per pack, lines as `VARIANT_SKU=QUANTITY;…`), and
  `whb_ratio_pack_templates:import` is that kind's permission on Import Batches (`FR-416`; `V500090` seeds both).
  Axes and packs created from a screen carry `owning_module = 'INSTALL'` (install data, `RL-012`), as every sibling
  screen-created registry does. Mobile stays **out of scope** by user decision (`INSTALL.md` §FR-218) — the RF
  pack receipt is the `POST /warehouse/movements/ratio-pack` port the handheld will call.

## Decisions recorded at build
W3 gate (functional-reviewer `p520-func.md`), ratified by the driver (`W3-FIX-DECISIONS.md` §P5-20):
- **The port is the deliverable** (F1). Acceptance 2, 3 and 9 are amended above: `POST /warehouse/movements/ratio-pack`
  is the one-scan. **Open interfaces:** a `warehouse` GRN / receipt line and a shipment line that name a pack and call
  the port; the customer-facing "one line" on a shipment document. Mobile RF Receive is out of scope (user ruling,
  `INSTALL.md` §FR-218).
- **A replay answers the original** (F2, PC-15 before the explosion). The ratio-pack service reads the idempotency
  key BEFORE it explodes a pack. A consumed key explodes without the pack's current state (a retired pack, a variant
  moved since) and the port replays it, because the contents cannot change (next bullet). A pack **deleted** since
  is answered from the body the key first posted, when the envelope's header matches; a different header under the
  key is `409 IDEMPOTENCY_KEY_REUSED`. *Limit:* with the pack deleted, only the header is compared.
- **T1 guard — a pack's contents are immutable** (F3). Once created, its lines (variant → quantity) and
  `packQuantity` never change, as its code and style never do: an edit that changes them is refused
  `422 RATIO_PACK_CONTENTS_IMMUTABLE` on the field ("create a new pack instead"). The edit form shows them
  read-only; only name, description and status are edited. The import already refused rewriting a pack.
- **T2 row — owner scope on the explode path** (F4). The pack's owner is checked (`OWNER_NOT_PERMITTED`, 403)
  right after the lookup, before its code, status or style is told; refusals never carry an owner UUID.
- **A port refusal is keyed on the line as sent** (F5). `lines[k]` of the exploded body is re-keyed to the pack
  line it came from, the message naming the variant (`… (variant TSHIRT-M)`); the rule code and status are the port's.
- **FR-044 carve-out** (F6). A refusal of the pack line itself (unknown / inactive pack, forbidden field, owner,
  pack quantity, movement type) is answered BEFORE the port records the request and leaves no
  `whb_inbound_messages` row; the port records the exploded body only. `WH-SC-386` states this.
- **T1 guard — activation re-validates** (F7). Activating a pack re-runs the line rules on its stored lines (style,
  variant-of-style, owner, one base unit, the sum); the explode refuses a variant no longer of the pack's style
  (`RATIO_PACK_VARIANT_NOT_OF_STYLE`).
- **T1 guard — one base unit** (F8). All of a pack's variants share one base UoM (`RATIO_PACK_UOM_MIXED` on the
  screen, the same words on an import row).
- **Transfer file** (F9). The export checks the style first (404 not a style, 403 another owner's) whether or not it
  has packs, and a scoped caller's file is filtered by owner in the query, not in memory.
- **T1 type list** (F10). A pack posts only under `RECEIPT`, `ISSUE`, `RECEIPT_REVERSAL`, `ISSUE_REVERSAL`
  (`422 RATIO_PACK_MOVEMENT_TYPE_NOT_ALLOWED`), and each must still balance `MUST_BALANCE_PER_OWNER_ITEM` (L-1).
