Two rules, and they are separate (`FR-408`):

1. **Approval permissions are distinct from execution permissions.**
   `wh_stock_adjustments:create` is not `wh_stock_adjustments:approve`; `wh_counts:post` is not
   `wh_counts:approve`. Distinct rows, distinct grants, distinct `@PreAuthorize`.
2. **The approver may not be the actor.** *The counter may not approve their own count variance;
   the adjuster may not approve their own write-off.* This is a **service check against the stored
   actor**, not a UI gate — the same row must be refused to the same user through the API.

**Where it lands in v1:** `wh_stock_adjustments` (`P2-01`), `wh_counts` (`P2-04`),
`wh_supplier_returns` (`P2-13`), `wh_revaluations` (`P2-17`), and the `SCRAP` disposition on
`wh_return_receipts` (`P2-12`). Every one already carries `approved_by` and `approved_at`; this task
makes the pair enforceable and consistent.

**The `AUDITOR` shape is the counter-example that proves the design.** `FR-403`/`WH-SC-245`: the
auditor is **read-only across everything including the ledger and is never a writer** — so the
maker-checker rule and the read-only role are two different mechanisms and neither substitutes for
the other.

**`permission_dependencies` rows are inserted, never created** (`T-10`), and `approve` **requires**
`view` on the same resource. The columns are `permission_id` and **`dependent_permission_id`**
(not `depends_on_permission_id`); semantics: `(permission_id = X, dependent_permission_id = Y)`
means *granting X also grants Y*.

**Mobile.** The mobile adjustment screen (`P2-01`) **states that approval is desk-only** rather than
hiding the button — a hidden button reads as a bug and a stated constraint reads as a decision
(`D-13`).

## Traps

- **`FR-401`/`WH-SC-241` — the gate is the API, and the UI merely agrees with it.** *The port returns
  `403`; the screen's post control is **not rendered**, because permission gating is
  `useMemo`-computed.* Both, not either. A UI-only check is defeated by curl; a backend-only check
  ships a button that always fails.
- **CLAUDE.md CRITICAL #13** — permissions are computed in `useMemo`:
  `const { canApprove } = useMemo(() => ({ canApprove: hasPermission(...) }), [hasPermission]);`
  never `const canApprove = hasPermission(...)`. That is the **standards reviewer's** rule and it is
  restated here only because this task is where the approval gates are written.
- **`@PreAuthorize` on EVERY controller method** (CLAUDE.md CRITICAL #1), format `resource:action`.
  There is no exception for an approve endpoint.
- **The maker-checker check reads the *stored* actor, not the request.** Comparing the approver to a
  `submittedBy` supplied in the request body is defeated by editing the request body.
- **A `:view`-named permission can gate a write and often does.** Do not assume the verb in the name
  is the verb enforced; read the `@PreAuthorize`.
- **`T-10` — never `CREATE TABLE permission_dependencies` from a module migration.** It is a
  platform table (`V248:17-30`, header `:4-13`); the vestigial second creator at
  `dealer/V20501:10` is the documented false premise.
- **`hasAnyRole` skips named roles.** Gate on the authority, not on a role list that silently
  excludes a named role.
- **The rule must be a shared service, not five copies.** Five hand-written
  `if (approver.equals(actor)) throw` blocks are five places for it to be omitted in v1.1.

## Round-4 additions (folded from former P5-27, #160) — value-banded approval levels

**v2 increment of this task — design the schema now, build in the v2 wave.** Round 4 filed value-banded
approval levels as their own task, `P5-27` (`#160`). On 2026-09-10 it was closed as a duplicate and
folded here, because this task owns the approval rule every level applies (`FR-408`) and is enforced on
*"every later approval surface"*. Migrations **`V510222`**, **`V511180`**, **`V511210`** and **`V511240`**,
requirement **`FR-466`** and screen **`WS-241`** move here with it.

**Scope — one bounded table the existing approve actions read (`RK-008`).** Every approval in v1 is one
step: `FR-408` keeps approver and actor apart, and adjustments, counts, POs and transfers carry a value
threshold. The market's approval is a value-banded chain: *"POs over ₹5 lakh need the parts manager, then
the general manager"* (`RK-008`). This increment adds that chain as **ordered, typed rows**. It stays
inside refusal #10 (FRD §10 row 11): it is not a workflow engine (`FR-466`).

1. **`wh_approval_levels`** (`V510222`) — `company_id`, `document_type_code` (the document-type registry,
   `P0-04`), `sequence_no`, `min_value` `DECIMAL(19,4)` (`OD-7`), `required_permission` (a §10.2 approve
   string), `effective_from`, `effective_to`; `uk(company_id, document_type_code, sequence_no)` among
   current rows. The value band is the range from one level's `min_value` to the next.
2. **The rule.** A document requires every current level of its type whose `min_value` is at or below the
   document's value, in `sequence_no` order. With no rows for a type, the v1 single-step threshold behaves
   exactly as before.
3. **The existing approve actions read it.** The approve actions that ship in v1 — PO (`P1-12`),
   adjustment (`P2-01`), count variance (`P2-04`) and transfer (`P2-02`, `FR-462`) — ask for the next level
   instead of approving outright. The document stays in its approval state until the last level approves.
   The existing `approved_by` column holds the last approver.
4. **Each level's approval is an audit event** (`whb_audit_events`, `P0-13`) naming the document, the
   level's `sequence_no` and the approver. The next level and the no-twice rule read those events. There
   is no second approval table.
5. **`WS-241` Approval Levels** — a Department-shaped master: grid (`V511180`), add/edit and view modals,
   company and document-type filters. Its resource permissions, dependency rows and menu are the `WH-206`
   pair `V511210`/`V511240`.

**Requirement** `FR-466` — owned here now. **Scenario** `WH-SC-323` — a PO over the second value band
needs the parts manager, then the general manager; the same user cannot approve twice. **Closes**
`RK-008`. **Depends on** `P1-12` and `P2-02` besides this task's existing `P2-01` and `P2-04` — all v1.

**Traps (v2 increment)**

- **Not a workflow engine** (`RK-008`, refusal #10). No conditions beyond document type and value, no
  branching, no parallel levels, no expressions. A request for any of those is a new refusal row, not a
  column on this table.
- **The levels are resolved once, at submission.** An edit to `wh_approval_levels` closes the old row and
  opens a new one (`D-14`). A document already submitted keeps the set it resolved, recorded on its first
  audit event. Re-routing a document in flight is how an approval chain loses its audit trail.
- **`FR-408` applies at every level, and one user approves a document at most once.** Holding two levels'
  permissions does not let one user clear both. The check reads the document's approval events, not the
  user's roles — the same stored-actor rule this task already enforces.
- **A level whose permission nobody holds blocks forever, so refuse it on save.** Saving a level whose
  `required_permission` is granted to no active user in the company is a validation error with that
  message, not a silent dead end.
- **The value is the document's value in the company's base currency**, computed by the document, not by
  this table. A PO in a foreign currency converts at the rate it already carries.
