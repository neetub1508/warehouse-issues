## The deliverable is an answer to one question, with evidence — not a migration

`FR-365`: *"**The dealer vehicle inventory is not migrated in v1 or v2.** The test for whether it ever
should be is stated rather than the answer: **can the serial entity carry a chassis number, a colour, a
variant and a pre-delivery-inspection status without `warehouse-base` learning what a vehicle is?**
If the answer needs a base column, the answer is no."*

`OD-2`'s deadline is **v3 planning, not before**, and its recommendation is *"do not migrate in v1 or v2;
model it as a documented future adapter, and prove the ledger on **parts** first."* This task runs the
test now that the ledger has been proved on parts.

## Scope

- **Run the test, in the exact form `PORT-AND-ADAPTER-CONTRACT.md` §9.9 states it:**
  *can `whb_serials` + `whb_movement_line_attributes` carry a chassis number, a colour, a variant and a
  PDI status **without `warehouse-base` acquiring a single vehicle-shaped column**?*
- **Build the falsifier as a real fixture**, not a thought experiment: a `whad_`-prefixed proof that
  registers a vehicle as a serial-controlled item, attaches chassis / colour / variant / PDI status as
  **registered `whb_attribute_keys`** on `whb_movement_line_attributes`, and posts a receipt, a yard move
  and a delivery through the port. **If any of the four needs a base column, the answer is no — and the
  answer is then permanent, not deferred again.**
- **State the answer with its evidence**, and either open a migration programme as its own epic or close
  `OD-2` as *no, permanently*, with the reason.
- **Nothing migrates in this task.** `pdi_vehicle_inventory` is a live, load-bearing dealer workflow;
  migrating it is a rewrite of a shipped vertical.

## Traps

- **⚠ `pdi_storage_slot_assignments` is the best occupancy model in this repository, and it is not
  warehouse's.** Append-only, released rows retained, exclusivity via **partial unique indexes**,
  occupancy **derived at read time and deliberately not cached** — `dealer/…/V20735:8`, `:43-52`,
  `:57-69`; `PdiYardStorageLocationService.java:67`; `PdiStockYardMapper.java:83,118` (R1 `C-033`).
  Warehouse **copied this shape** for **`whb_reservations`** (`FR-093`, §2.1.2 — `C-033`'s recommendation
  column names a location-occupancy table that this design set does not create; the shape landed on the
  reservation object instead, and there is no separate occupancy table to migrate onto). Migrating the
  vehicles onto warehouse would therefore be migrating onto a copy of their own model — which is an argument for care, not for speed.
- **`pdi_vehicle_inventory` is quantity-free** — one chassis per row, 26 `pdi_*` tables. R1 §5.2 puts it
  precisely: it *"is quantity-free … the right model for serial-tracked warehouse stock and useless for
  everything else."* A migration would have to reconcile a quantity-free model with a quantity ledger, and
  that is where the base columns get requested.
- **The failure mode is a *small* base column.** Nobody proposes `whb_items.is_vehicle`. Somebody proposes
  `whb_serials.chassis_number` because *"it is just one column and everyone calls it that"* — and
  `warehouse-base` has then learned what a vehicle is, permanently, in every install including ones with
  no dealer. **That single column is the falsifier.**
- **`whb_movement_line_attributes` is the escape hatch, and it is typed, not JSONB.** Attributes are keyed
  by registered `whb_attribute_keys` (`PC-09`), because CLAUDE.md forbids JSONB and *"a schema nobody can
  filter, index or reconcile"* is not a model. If the four vehicle facts cannot be expressed as registered
  attribute keys, that is the answer.
- **Do not conflate this with the gate or the yard.** A gate event and a yard slot are `P5-21`'s and
  `logistics`' respectively (`FR-340`, R7 §2.3). This test is only about whether a **vehicle is a serial**.
- **Answer it or close it.** `D-12`'s whole point is that nothing is left to *"we'll look at it later"*.
  A third deferral is not an acceptable output of this task.
