## Scope

- **`V540131`** — `whin_itc_reversals` (`DATA-MODEL.md` §7.6 WIN-16): reason code, statutory
  category, movement reference, lot, quantity, **original ITC**, reversed amount, period, and the
  return it was reported in.
- **The reversal amount needs the original credit** (`FR-316`), and the original credit is the tax on
  **the receipt that brought *that lot* in**. So a **write-off movement must be able to reach that
  receipt** — through the lot-to-cost-layer linkage: `whb_cost_layers` and
  `whb_cost_layer_consumptions`, present from v1 under `OD-6`, with `cost_layer_id` a **v1 column on
  the movement line** (`IRR-38`) even though FIFO consumption ships in v1.1. *An AVCO-only v1 has
  nothing to build layers from later.*
- **Scrap is inventory, and its sale is a supply** (`FR-317`) — with its own classification code and
  a **tax-collected-at-source flag** — **not shrinkage**. Modelled exactly as
  `INDIA-LOCALISATION-PACK.md` §5.5 states: scrap is a **`stock_status_code`** with
  `is_on_hand = true`, `is_valued = true`, `is_allocatable = false` (which is why the status registry
  carries behaviour flags rather than a badge colour, `FR-102`), reached by a **balanced two-line
  status-change movement with a reason code** (`FR-103`). The sale is an ordinary outbound.

## Traps

- **The linkage is what makes this possible, and it was a v1 decision.** `cost_layer_id` on the
  movement line and `whb_cost_layer_consumptions` shipped in `P0-02`/`P2-16` precisely so this task
  could exist. If the write-off path does not consume a layer, the reversal has no original credit
  and the amount is a guess.
- **A year of free-text reasons cannot be reclassified**, and that year is the one the first audit
  covers (`S-028`, `FR-315`). Every write-off reason code carries an `itc_treatment` and a
  `statutory_category` from v1; a code without them makes the reversal uncomputable for every
  movement already posted.
- **Scrap is not shrinkage and the difference is money.** Scrap has a value, a location, a stock
  status and an owner, and its sale is a **taxable supply**. Booking it as shrinkage loses both the
  asset and the output tax. The live precedent that got this half right is `asset_disposals`
  (`assets/…/V60160:94-126`), which carries `hsn_code`, `taxable_value`, `cgst_amount`,
  `sgst_amount`, `igst_amount` and `buyer_gstin` under a comment reading *"GST block for the scrap
  sale"* at `:120` — it is the only place in the codebase that treats a disposal as a supply, and its
  shape is worth copying.
- **The status change to scrap is a balanced two-line movement at the same location** (`FR-103`), not
  an `UPDATE` to a status column. Quarantine and recall use the same mechanism, which is what lets a
  recall hold stock **in place**.
- **`is_allocatable = false` is what stops scrap being picked**, and it is a registry flag, not a
  hardcoded status list. `WH-SC-147` asserts the whole chain: a new status added by migration is
  excluded by the allocator because of the flag, with **no code change** and no
  `CHECK (status IN (…))`.
- **The TCS rate is a seed row with effective dates, never a constant.** A rate change by
  notification must not be a release.
- **Money is `DECIMAL(19,4)`; per-unit figures are `DECIMAL(19,6)`; percentages and rates expressed
  as percentages are `DECIMAL(9,6)`** (`DATA-MODEL.md` §5.1). `DECIMAL(19,8)` is the
  currency-conversion type and nothing else — a `tcs_rate_percent` is `DECIMAL(9,6)`.
- **The reversal is reported once.** `reported_in` plus an `unreportedOnly` filter is what stops the
  same reversal appearing in two periods; without it a re-run double-counts.
- **This task depends on `P4-03`** — the statutory categories and the period shape come from the
  stock account, and a reversal computed against a category the report does not carry reconciles to
  nothing.

## Acceptance
- [ ] A write-off of a lot resolves the **receipt that brought that lot in**, through the cost-layer consumption chain
- [ ] The reversal amount is computed from the **original** input tax on that receipt, not from the current value
- [ ] A write-off whose reason code carries no ITC treatment is refused, or is recorded as uncomputable and named — never silently zero
- [ ] Scrap is a stock status with `is_on_hand = true`, `is_valued = true`, `is_allocatable = false`, reached by a **balanced two-line status-change movement** with a reason code
- [ ] Scrap cannot be allocated, and the exclusion comes from the registry flag rather than a status list in code
- [ ] A scrap sale is an ordinary outbound carrying its classification code and its TCS flag
- [ ] The TCS rate is a seed row with effective dates and no constant appears in Java or TypeScript
- [ ] Reversals reconcile to `P4-03`'s statutory categories for the same period
- [ ] A reversal already reported cannot be reported again
- [ ] Every threshold carries its value and a RE-VERIFY marker; the `s.17(5)(h)` clause letter is marked `UNVERIFIED` in the migration comment
- [ ] **Scenarios** — none claimed; `WH-SC-215` still passes, and its v2 half is what this task builds
