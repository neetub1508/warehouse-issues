- **A sandbox / practice warehouse with disposable data** (`FR-442`). For a warehouse this is not a
  nicety: **you cannot train pickers on live stock**. Every training pick is a real movement in an
  **append-only ledger that has no delete**, so the alternative is a month of reversals with training
  reason codes polluting the adjustment register (`WH-SC-254`).
- **In-product help content per screen**, on the platform's existing help affordance. `HelpButton.tsx`
  is verified present in `platform/frontend/src/components/common/` — it **exists and needs content**
  (`PLATFORM-DEPENDENCIES.md` §1.13, `S-094`).
- The sandbox is a **flagged warehouse whose data is disposable**, not a second database and not a
  second install: `OD-3` keeps one database per customer, so a parallel environment is a parallel
  customer.

## How the sandbox is shaped, and what it must not be

- **It is a `whb_warehouses` row carrying a sandbox flag**, and every movement in it is an ordinary
  movement with that warehouse's id. That is what makes it disposable *and* realistic: the operator
  learns the real screens, the real scans and the real refusals.
- **Every report, valuation, statistics strip, export and accounting handover excludes it by
  predicate.** This is the load-bearing half. The accounting set learned it as
  `acc_companies.is_rehearsal`: *reports written before the flag exists include rehearsal data with
  no predicate to exclude it.*
- **Disposal is a purge of that warehouse's rows, not a ledger delete.** `L-2`/`L-3` hold everywhere
  else in the product; the sandbox's exemption is that its whole warehouse can be dropped, and that
  exemption is stated in one place rather than discovered as a delete path on the ledger service.

## Traps

- **The flag must exist before the first movement, or the exclusion predicate has nothing to read.**
  This is a `PNR-3`-class problem in miniature: a sandbox warehouse identified retroactively means
  every report already run included training data and nobody can say which figures were affected.
  The flag belongs on `whb_warehouses` (`P1-05`, `V500012`) — if it is not there when this task
  starts, adding it is a **new migration in the base band**, and every report predicate is amended in
  the same task.
- **A purge is not a `DELETE` on the ledger service.** `L-2` and `L-3` make movements append-only and
  immutable and there is deliberately no delete path. The sandbox purge is a maintenance operation
  scoped to one warehouse id, permissioned, audited, and it does **not** open a general delete method
  on the writer service. One escape hatch on the ledger becomes the way a support engineer "fixes"
  production.
- **Do not train with real reason codes.** Training movements posted into the live warehouse with a
  `TRAINING` reason code are `WH-SC-254`'s named failure: they pollute the adjustment register, they
  reach the Rule 56 statutory categories (`P4-03`) and they are then part of a filed return.
- **Help content is en / fr / hi**, registered in the module SafeTranslation. `S-095`: warehouse
  operators are the most language-diverse users in the suite.
- **`HelpButton` exists — do not build a second help affordance.** `/preflight-check` before writing
  any component; the platform component set is verified present at
  `platform/frontend/src/components/common/HelpButton.tsx`.
- **The sandbox is not a demo dataset.** A seeded fixture that cannot be reset is used once and then
  abandoned; the requirement is **disposable**, which means resettable on demand.
- **Exclusion applies to the accounting handover too** (`D-6`): a sandbox movement handed over to
  accounting is a journal in a real ledger, and `posting_status` will happily carry it.

## Acceptance
- [ ] A sandbox warehouse exists, an operator completes a full receive→putaway→pick→pack→ship cycle in it, and the movements are ordinary ledger movements
- [ ] Every report, valuation, statistics strip and export **excludes** the sandbox by predicate, verified on at least the position report, the valuation report and the movement register
- [ ] No sandbox movement reaches the accounting handover
- [ ] The sandbox resets on demand, by a permissioned and audited purge scoped to one warehouse id
- [ ] The ledger writer service gains **no** delete method, and `L-2`/`L-3` still hold for every other warehouse
- [ ] Training produces **zero** rows in the live adjustment register
- [ ] Every warehouse screen has help content behind the existing `HelpButton`, in en / fr / hi
- [ ] No second help component is created
