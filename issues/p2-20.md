## Scope

**All six are computed from the ledger.** That sentence is the task. It is also the last link but
two on the critical path, because *the v1 exit is a reconciliation, not a feature*.

| id | Report | The rule that makes it correct |
|---|---|---|
| **WS-208** | **Stock on hand by every dimension** (`FR-384`) — item, location, lot, serial, LPN, status, owner, duty status — **with a by-location tab and a by-item tab**, the two-tab pattern a shipped module already cites | The nine-member grain appears on the *by location* tab; `nonZeroOnly` defaults **true** |
| **WS-209** | **The stock movement register — report number one** (`FR-385`) | Line grain, filterable by item, warehouse, location, lot, serial, movement type, reason, source module and date range, in **opening → in → out → closing** shape per item, drilling to the movement and from the movement to the source document **through the display resolver** (`FR-357`). *It is the report auditors and storemen both live in.* |
| **WS-210** | **The godown-wise stock statement** (`FR-386`) — godown × item group × item, **opening / inward / outward / closing / value**, with branch and period filters | *A grid with a warehouse dropdown is not this report; the opening/inward/outward/closing shape is the whole point, and a bank asks for it monthly against a cash-credit limit* |
| **WS-211** | **Stock valuation with an as-at date** (`FR-387`), computed from the ledger and `whb_cost_layers` | It **reproduces the same answer for the same date next year** |
| **WS-212** | **Stock ageing** (`FR-388`) with buckets measured **from the last outward movement** (`FR-162`, `P2-05`), **value per bucket**, warehouse split | A lot received two years ago that shipped last week is **not** aged stock |
| **WS-224** | **Stock as at a back date, computed from movements, never from balances** (`FR-328`) | *The section-44AB quantitative statement, the bank stock statement and the 31-March closing stock all ask "as at a date in the past, **recomputed including entries made since**"* |

**`asAtDate` on WS-211/WS-212 and `asAtDateTime` on WS-224 are required parameters, not filters.**
A report of this shape with no as-at date is a report of today, mislabelled.

**Which branch a site's stock belongs to** (`RG-001`, R22 §1.2.4 row 11; `RH-006`). Under `D-14` a
site can be linked to several branches. A report that grouped by *"linked branch"* would count a
shared godown once per branch, and three branches' totals would sum to three times the company's
valuation. **The rollup rule, stated in the header of every branch-grouped report in this pack:**
- **Stock and value roll up to the `REGISTERED` branch only**, so each site is counted once. For
  the as-at reports (WS-208, WS-211, WS-212, WS-224) that is the link as at the report date. For the
  period report WS-210 it is the link at each movement's `occurred_at`, so a site re-registered
  mid-period splits at the switch instant.
- **Flows and demand roll up to the document's own branch**: the counter sale's `branch_id`, and a
  transfer's two ends.
- **A branch filter selects the sites linked to that branch** — *"linked to"*, not *"registered
  under"*. A shared site then shows its whole stock under each linked branch, and the header says
  *"shared by N branches"*. **A total row over a branch-filtered set is refused.**
- A *linked branches* grouping may be offered as a separate view. It is labelled **not additive**
  and never sums.

*Before round 4 every one of these reports was specified when a site had one branch.*

**Month-end snapshots exist for performance and are explicitly a cache** (`FR-328`).
`whb_stock_position_snapshots` (`V500045`, `P0-03`) may accelerate a bucket computation; **the
as-at answer is always derived from movements**, and the two must agree.

## Traps

- **`WH-SC-060` and `WH-SC-061` are the reason this task exists, and the second is the harder one.**
  Ship the rebuild diff as a **test**, not as a manual procedure. `L-4` says a full rebuild
  reproduces every position row exactly; if it does not, this report pack is reporting a broken
  cache with three decimal places of confidence.
- **`C-027` — do not repeat the accessories valuation defect.** Its valuation report reads
  **`last_cost`, not `average_cost`** (`StockReportQueryService.java:543`), so the report and the
  balance disagree by construction. WS-211 reads `whb_cost_layers`, and its footer states the
  method it used.
- **`PP-7` — `OFFSET` depth is not survivable at 100M rows.** v1's answer is an **enforced
  date-range filter** on WS-209 and WS-224 — cheap and honest; keyset/seek paging is v1.1. A report
  that opens on "all time" is a report that times out on the first real install.
- **`PP-6` / `FR-400` — 100,000-row exports need the streaming path**, which is `P2-29`'s.
  `BaseExportService.DEFAULT_MAX_EXPORT_ROWS = 10_000` (`:48`); raising the constant fixes only the
  first of three problems — the transaction is held open for the duration, and a per-cell style
  blows the 64k Excel cell-style limit **at scale, not in dev**. These six reports are its consumers.
- **`FR-395` — every statistics strip here is filter-aware, so none carries a cache name.**
  `CacheConfiguration.java:190-196` records that exact mistake with its issue numbers
  (`neetub1508/classic#790`, `#791`): those names cached nothing while reading as though they did.
- **`T-5` — `SqlSortBuilder` whitelist or no sorting.** One `getWh…FieldMappings()` per report grid,
  **always with a default sort**. A report is exactly where a concatenated ORDER BY gets written.
- **`T-4` — the `Object[]` timestamp mapper.** These are all native-query reports;
  `occurred_at`/`posting_date`/`last_outward_movement_at` can come back as `OffsetDateTime`,
  `Instant`, `java.sql.Timestamp` **or** `LocalDateTime`. Copy
  `platform/…/service/UserActivityLogQueryService.java:288-307` **including its warning on an
  unknown type**; returning `null` renders a blank cell over real data.
- **`T-6` and the `date` / `dateOnly` split, which this pack gets wrong most easily.**
  `occurredFrom`/`occurredTo` are **`date`** (`occurred_at` is `TIMESTAMPTZ`);
  `postingDateFrom`/`postingDateTo`, `asAtDate`, `fromDate`/`toDate` are **`dateOnly`**
  (`posting_date` and the statutory dates are `DATE`). `filterUtils.ts:49-56` documents that `date`
  *"moves the 'from' bound to the previous calendar day for users east of UTC"* — which on a
  statutory report is a wrong number, not a cosmetic shift.
- **`T-18` — verify DB column names.** The godown statement joins platform `branches`; the column is
  **`branches.branch_name`**.
- **The source-document drill-through goes through the bean-collection display resolver**
  (`FR-357`), with a base fallback. On a Mode-A install with no adapter resolver the reference must
  still render (`WH-SC-226`).
- **`L-13` — three timestamps, never one.** The register offers `occurred_at` **and** `posting_date`
  as separate filters and shows both columns. Collapsing them makes cut-off unanswerable.
