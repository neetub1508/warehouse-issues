- **`V510011`** — `wh_purchase_orders`, `wh_purchase_order_lines`.
- **PO and GRN are distinct documents** (`FR-122`): the PO carries **ordered / received / cancelled**
  quantities per line; the GRN carries what physically arrived. Each document has exactly one job —
  *PO = supplier → our warehouse* (`P-018`).
- **The layered-truth model, stated with its worked number** (`FR-123`, `P-019`) — the product's
  answer to *"which quantity is right"*: **PO = commitment · ASN = declaration · receipt = physical
  truth.** Write the worked example into the code comment and the user documentation, because the
  three numbers legitimately disagree and every support ticket about it is the same ticket.
- **The PO detail page is the lifecycle command centre** (`FR-125`, `P-020`): a **route**, not a
  modal, with sub-tabs where **every GRN, invoice, return, QC result, putaway and exception rolls
  up**.
- **Cancellation is a cascade with a stock gate** (`FR-132`, `P-026`), **not a status flip**: a PO is
  cancellable only before stock is posted; it is **refused if any GRN line has received stock**, and
  the modal **says which**.
- **`ownership_transfer_point` on the purchase document as a v1 column** (`FR-344`) — the in-transit
  location says *where*, the owner says *whose*, and the transfer point says *when it changed*.
  `P1-17` carries the transfer side.

**`DATA-MODEL.md` §2.2 (`WH-02`) is the authority on both column sets and must be re-read immediately
before the migration is written.**

## Traps

- **Cancellation is not a status flip.** `FR-132` and `P-026`: the cascade must check every GRN line
  for received stock and **name the blocker** in the refusal. A PO cancelled with stock received
  leaves a receipt with no commitment behind it and a supplier invoice nobody can match.
- **The UoM convertibility guard must run on the GRN modal too.** *The prior system had it on the PO
  and SO screens and the GRN modal offered the unconvertible unit anyway* (`FR-143`). Build it once,
  call it from both — `P1-13` inherits the same obligation.
- **The three quantities legitimately disagree, and the UI must not hide it.** PO ordered ≠ ASN
  declared ≠ GRN received is the normal case, not an error state. A screen that shows one number
  destroys the model `FR-123` exists to preserve.
- **`orderedQuantity` / `receivedQuantity` / `cancelledQuantity` are backend-computed roll-ups**,
  never a frontend `.filter()` or reduce over the lines (CLAUDE.md CRITICAL #8) — and under
  pagination a frontend sum is simply wrong.
- **`overdueOnly` is backend-computed too.** "Overdue" is `expected_delivery_date < today` in the
  **site's** timezone (`FR-439`), not the server's.
- **Both date pairs are `dateOnly`** — `order_date` and `expected_delivery_date` are SQL `DATE`
  (`FR-327`), and `date` would shift the lower bound a day for users east of UTC
  (`filterUtils.ts:49-56`).
- **`status` is a `multiselect`.** A buyer works "submitted + approved + partially received" as one
  view; a single-select forces three passes.
- **`ownership_transfer_point` is a v1 column even though the consuming logic is later** (`FR-344`,
  `P5-16`). It is the `IRREVERSIBLE.md` pattern.
- **The detail page is a route with child grids and no `gridIdentifier` per tab.** Giving each tab its
  own grid identifier means ten more `grid_preferences` rows, ten more filter scopes, and a
  configuration surface nobody asked for.
- **Hibernate native-query timestamps come back as any of four types** — the PO grid joins
  `created_at`, `updated_at` and two document dates, so copy
  `UserActivityLogQueryService.java:288-307` (R1 §8 trap `T-4`, `FR-438`).
- **`branches.branch_name`, not `branches.name`**, on any branch join (R1 §8 trap `T-18`).
- **One grid × two platform files**, and `WAREHOUSE_PURCHASE_ORDER` carries ~12 filter keys — every
  one in `COMMON_FILTER_CONFIGS` or it is silently dropped.
