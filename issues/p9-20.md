## Scope
- **One producer per event** (`D-21` item 2; R32 F-R32TR-002, -010): core emits one shipment-level **`INVOICE_REQUEST`** per
  shipment id and one **`CREDIT_NOTE_PROPOSAL`** per return receipt + QC disposition (`p8-23`); before handing either over it asks
  the core-declared enrichment SPI **`WhAccountingEnvelopeEnricher.enrich(kind, sourceEventId, shipmentId | returnReceiptId)`**
  (FRD-TRADE §12c `CN-18`, declared by core `P8-26`), which this task implements for trade-sourced demand. Trade **never emits an
  invoice or return kind of its own**; the receiver dedupes on the event id. Trade is the only producer of `SERVICE_RECEIPT`
  (p9-07) and `BILL_OF_ENTRY` (p9-18) — events core has no document for.
- Tables (`V552050`): **`wht_accounting_proposals`** (company, `proposal_kind` `SALES_INVOICE` / `SALES_RETURN` (enrichments) /
  `SERVICE_RECEIPT` / `BILL_OF_ENTRY` (trade-produced), `source_event_id` (core's event id for an enrichment; uk(company,
  `proposal_kind`, `source_event_id`) — a repeated enrichment returns the stored answer), `core_shipment_id` / `core_return_receipt_id`,
  source document type / id / ref, counterparty, currency, taxable / tax / gross totals, `handover_id` ↓ `whb_accounting_handovers`,
  `status` — enrichments `ENRICHED` / `ACKNOWLEDGED` / `REJECTED`, trade-produced `PROPOSED` / `HANDED_OVER` / `ACKNOWLEDGED` /
  `REJECTED` —, `accounting_document_no`, `accounting_document_date`, `rejection_reason`, `attempt_count`),
  **`wht_accounting_proposal_lines`** (proposal, source line, item, HSN / SAC, qty, unit price, discount, taxable value, and
  `serial_no` — one line per unit serial when the item is serial-tracked, read from the core shipment), **`wht_accounting_proposal_line_taxes`**
  (proposal line, `tax_head_code` `CGST` / `SGST` / `UTGST` / `IGST` / `CESS`, `rate_percent DECIMAL(9,6)`, `taxable_value` /
  `tax_amount DECIMAL(19,4)`, `is_reverse_charge`; uk(line, head) — typed child rows, so UTGST has a home; R32 F-R32TR-021),
  **`wht_accounting_proposal_line_part_serials`** (proposal line, `part_role` (`CHASSIS` / `MOTOR` / `CONTROLLER` / `BATTERY` /
  `CHARGER` / `OTHER`, from the registry), `part_serial_no`; uk(line, role, serial) — R32 F-R32TR-027), **`wht_so_line_billings`**
  (SO line, proposal, invoice no, invoice date, billed qty; uk(proposal_id, so_line_id, accounting_document_no) — a re-sent
  acknowledgement writes nothing; append-only; R32 F-R32TR-026).
- Invoice enrichment (FR-773, `TSO-T4-16`): for a shipment of a trade SO the enricher answers with the SO price, discount, FR-762
  tax recomputed for the shipped qty (typed head rows), HSN, customer PO, e-way bill ref (india read through core), shipped unit
  serials and, per unit, the bound part serials read through the core-declared `UnitRegistryPort.findByUnitSerial` (MFG `p10-23`;
  MFG off → the unit serial only). A shipment of an `is_replacement` release is answered **`NOT_INVOICEABLE {REPLACEMENT}`** and
  core requests no invoice (R32 F-R32TR-011). One enrichment per shipment id — a BLANKET / OPEN SO's every despatch is invoiced,
  whatever the demand header status (`OD-45` (A)).
- Billing (FR-774, `TSO-T4-17`): core's **`INVOICE_ACKNOWLEDGED`** (shipment → invoice no / date, per-line quantity, serial list;
  `D-21` item 3) → `wht_so_line_billings` + proposal `ACKNOWLEDGED`; a rejection → `REJECTED` with accounting's reason. Derived
  `billing_status`; billed vs shipped excludes replacement shipments on both sides; setting `warehouse.trade.sales.close_rule`
  (`SHIPPED_AND_INVOICED` when a handover target is configured, else `SHIPPED`) read by p9-10's auto-close. The same event moves the
  MFG unit registry `DISPATCHED → SOLD` and starts warranty (`p10-23` consumes it) — trade calls nothing on MFG for it (R32
  F-R32TR-017; ledger `crm-so-dispatch-reports:12-19`).
- **Gate-out on invoice** (CGST Act s.31(1)(a); `D-21` item 3; R32 F-R32TR-012): trade answers core's gate-out guard
  `WhGateOutGuard.check(shipmentId)` (FRD-TRADE §12c `CN-21`, declared by `P8-26`) for trade shipments — with an accounting
  handover target configured, an invoiceable shipment without `INVOICE_ACKNOWLEDGED` is refused `409 TRADE_INVOICE_NOT_ACKNOWLEDGED
  {shipmentId}`; without a target, and for a replacement shipment, the gate pass goes on a **delivery challan** basis (gate-pass
  print: *Delivery challan — not a tax invoice*); the outward gate-pass print shows the invoice no once acknowledged.
- Credit-note enrichment (FR-775, `TSR-T4-06`): on core's `CREDIT_NOTE_PROPOSAL` for an RMA raised from a trade SRA of intent
  `CREDIT` → a `SALES_RETURN` enrichment (accepted qty × SO price, tax reversal as typed head rows, the original invoice no from
  `wht_so_line_billings`); intents `REPLACE` / `WARRANTY_REPLACEMENT` → `NOT_CREDITABLE`, core proposes nothing. Core decides when
  receipt and disposition are both in and emits once per receipt (partial returns included) — trade waits for no RMA status
  (R32 F-R32TR-003).
- *Retry* (`wht_accounting_proposals:retry`) re-hands a `REJECTED` trade-produced proposal with a new attempt count; an enrichment
  is re-handed by core, which asks the enricher again with the same event id and gets the stored answer.
- Permissions / grids (`V552051`): `wht_accounting_proposals:{view,retry,export}`; WS-304 *Billing* tab grid (proposal, kind, status,
  accounting no / date, lines) + export.

## Traps
- Trade never numbers, posts or prints an invoice or credit note — it proposes; accounting's gapless GST series (Rule 46) is accounting's.
- An enrichment is built from core quantities read at the event, never from a stored shipped quantity (`TRD-03`).
- Never a second producer: no trade outbox kind for an invoice or a credit note; the enricher answers synchronously and idempotently on the event id.
- No JSON payloads: proposal lines are rows (CLAUDE.md, no JSONB).
- Without accounting no enrichment is asked, trade-produced proposals stay `PROPOSED`, the close rule is `SHIPPED` and gate-out is on a delivery challan — nothing waits forever.
