> ★ **`PNR-3` for `count_snapshot_quantity`** (`IRR-52`). Variance computed against a **live**
> quantity is not reproducible: the book figure at count time is gone the moment the next movement
> posts, so the variance on last quarter's count cannot be re-derived and **the count cannot be
> defended**. One column, captured at freeze. ★

**The load-bearing sentence, and it is the whole task.** *A count is a document that proposes an
adjustment and never writes on-hand* (`FR-153`). If a count writes the balance: the ledger no longer
explains it, there is no adjustment to post, the variance is unrecoverable, and a count keyed
against a stale snapshot **silently reverses movements made during the count**.

- **The book quantity is frozen at count start and stored on the line** —
  `wh_count_lines.count_snapshot_quantity` — **even when the count is blind**. Blind means the
  counter does not *see* it; it is stored regardless.
- **Posting emits one movement per non-zero variance line** (`FR-159`), each balanced against the
  `COUNT_VARIANCE` virtual location and each carrying **the count's reason code**, so a count is
  indistinguishable from any other ledger event to every downstream consumer.
- **Tolerance gates posting by quantity percentage *and* by value** (`FR-155`). Lines inside both
  tolerances post automatically on submission; a line outside **either** moves the count to pending
  approval and may generate a recount task. **Approval is a distinct permission and the approver may
  not be the counter** — the rule is `FR-408`, owned by `P2-23`, and this is its first enforcement
  point.
- **Recount** carries `recount_sequence` and retains the original count line.
- **`wh_count_programs` is a policy object** (`FR-156`): `program_type`
  (`ABC`/`RANDOM`/`FULL`/`ZONE`/`ITEM`/`DISCREPANCY_TRIGGERED`), `frequency_days`, `schedule_cron`,
  `next_scheduled_date` (**a `DATE`**), `is_blind_count`, `recount_threshold_pct`,
  `approval_threshold_pct`, `approval_threshold_value`, **`freeze_locations`**, `max_tasks_per_run`.
  Scope is **child rows in `wh_count_program_scopes`**, replacing the prior art's
  `scope_*_ids JSONB` (`FR-383`). *`freeze_locations` and the recount attempt are what distinguish a
  counting programme from a spreadsheet* — and both are here.
- **The full physical stocktake** (`FR-157`): a freeze window as an **object** with a start and an
  end, a book snapshot at start for every in-scope position, multi-counter zone assignment, and
  approval before posting **with the variance value shown**.

**Hand-off from `P0-03` (C2 fix pass 2, 2026-09-15) — `count.variance.posted` is this task's.** The
single writer emits `stock.movement.posted` at movement grain (`MPR-T4-07`) and cannot tell a count
variance from any other `COUNT_ADJUST` movement. So *Post* appends one `count.variance.posted` per
variance line (line grain, `PC-42`) through `WhbOutboxAppender.append`, **in the same transaction, after
`writer.post` returns** — the `receipt-qc-putaway.contract.md` `RQP-T4-07` pattern that
`receipt.line.confirmed` follows.

**The count ladder** (`RJ-004`). It is R24 Appendix A, adopted by `GAP-REGISTER-R4.md` §2.3, in
§0.11's columns. It also answers §0.11's open question: *Recount* is legal up to approval and never
after it.

**The verbs** (`RJ-005`). §10.2 had `:freeze`, `:approve` and `:post`.
- `V511203` seeds `wh_counts:generate`, `:recount` and `:cancel`.
- `V511233` inserts their `permission_dependencies` rows.

**A cancelled count gives its bins back** (`RJ-006`). The location ladder belongs to `P1-05`, and this
task is its main setter.
- *Freeze* with `freeze_locations` sets each location to `COUNTING`. *Post* or *Cancel* restores the
  status each location had before.
- **`FROZEN` is set only by the stocktake window** (`FR-157`). The window's start sets it on every
  in-scope location, and its end restores the prior status.
- Before round 4, a cancelled count left bins `COUNTING` and unpickable (`WH-SC-192`), and `FROZEN`
  had no setter anywhere.

**A count with no programme still has a tolerance** (`RJ-016`). The stocktake, `SPOT` and
`ZERO_STOCK` counts, and the count a short pick creates, inherit the install defaults
`warehouse.count.default_tolerance_pct` and `_value`, from `P1-20`'s `V511200`. A count with a
programme uses the programme's thresholds.

**`next_scheduled_date` has its job** (`RJ-012`). `P0-13`'s register row names the operative column,
`next_scheduled_date`, not `count_frequency_class`. The job does three things for every due programme:
- generates the counts, capped at `max_tasks_per_run`;
- advances `next_scheduled_date` by `frequency_days` or the cron;
- writes a `whb_job_runs` record.

**ABC is manual until v1.1** (`RK-003`). WS-093 labels `programType = ABC` *"uses manually maintained
classes"* until the simple ABC recompute ships — `P1-03`'s v1.1 increment (`FR-463`, folded from former `P3-25`). Before that, a screen offering an ABC programme implied a
computation that did not exist.

**A programme scoped by item category reads the item's `STOCKING` category** (`RG-005`). That is the
dated assignment in `whb_item_category_assignments` (`P1-01`), current at generation. It is never
another scheme, and never a scalar on the item.

**A programme belongs to one site in v1** (`RG-018`). A `WAREHOUSE` value in
`wh_count_program_scopes`, letting one programme span sites, is this task's own v2 increment (below, folded from former `P5-24`).

**Screens.** WS-093 `wh_count_programs` · `WAREHOUSE_COUNT_PROGRAM` · Customer reference, with a
child editor over the scope rows and a **Generate counts now** action. WS-094 `wh_counts` ·
`WAREHOUSE_COUNT` · Service Vehicle reference — Generate · **Freeze** · Assign zones · Enter counts
(WS-095) · Recount · **Approve** (`wh_counts:approve`) · **Post** · Cancel · **Print count sheet**
(through `P2-14`'s renderer). WS-095 is a **route, not a grid**: the line editor, with

**Statistics strip on WS-094** — open · counting · pending approval · variance value this period —
**filter-aware, therefore no cache name** (`FR-395`, `C-043`).

**Mobile.** WS-094/WS-095's entry surface is **WS-235 RF Cycle Count** (`P3`), which is a member of

## Traps

- **`C-023` — physical counts in this codebase never post.** `InventoryCountService.java:325-345`
  (line reference **refined from R1's `:322-345`** by `COEXISTENCE.md` §8.1) sets
  `status = 'POSTED'` and generates nothing; `grep -c "StockLevel" InventoryCountService.java` → **0**.
  **This is net-new work. Budget it as a full workflow, not a port.**
- **`P-033` is prior art worth adopting whole.** `wms_cycle_count_programs` already carries
  `program_type`, `frequency_days`, `schedule_cron`, `next_scheduled_date`, `is_blind_count`,
  `recount_threshold_pct`, `approval_threshold_pct`, **`freeze_locations`** and `max_tasks_per_run`,
  with `count_attempt`/`is_frozen` on the task and `is_within_tolerance`/`adjustment_id` on the
  result. Take the shape; do not take a `CHECK` on `program_type`.
- **`freeze_locations` is a location *status*, not a flag the allocator reads directly.** With it on,
  the location's status becomes `COUNTING` and `is_pickable` is false, so the allocator skips it by
  its ordinary rule. That keeps the allocator free of counting knowledge — `WH-SC-192`.
- **Blind means the number never leaves the backend.** Hiding `countSnapshotQuantity` in the grid
  and returning it in the DTO is the defect `WH-SC-110` exists to catch. Assert on the API response
  and on the export, not on the rendered DOM.
- **`P-045` / `FR-327` — `next_scheduled_date` and every statutory/count date is a SQL `DATE` mapped
  to `LocalDate`,** and its filter is **`dateOnly`**, not `date`. `filterUtils.ts:49-56` documents
  that `date` shifts to UTC day boundaries and *"moves the 'from' bound to the previous calendar day
  for users east of UTC"*. `LocalDate` also renders **date-only** — CLAUDE.md's
  `formatUTCDate(value, true, true)` guidance is wrong for it.
- **`FR-383` — scope is rows, not `JSONB`.** `wh_count_program_scopes` with a whitelisted
  `scope_type` and `scope_ref`. §1.6: no JSONB on a new `wh_` business table.
- **`FR-165`'s inverse.** The programme's `schedule_cron` needs a **registered scheduled job**.
  `P1-20` registers the count job together with its cache names and filter scopes; *a threshold
  column with no job that reads it is a defect at the moment it is merged.*
- **`T-5` — `SqlSortBuilder` whitelist or no sorting** on the count and variance grids, always with
  a default sort. Never concatenate ORDER BY.
- **Precision.** `count_snapshot_quantity`, `counted_quantity`, `variance_quantity`
  `DECIMAL(18,4)` · `variance_pct`, `recount_threshold_pct`, `approval_threshold_pct`
  **`DECIMAL(9,6)`** — *`_percent`/`_pct` beats any reading of "rate"* · `unit_cost`
  `DECIMAL(19,6)` · `variance_value`, `approval_threshold_value` `DECIMAL(19,4)`. `OD-7`.

## Round-4 additions (folded from former P5-24, #157) — a programme that spans sites

**v2 increment of this task — design the schema now, build in the v2 wave.** Former `P5-24` (`#157`)
gathered every v2 junction a round-4 lens had hung on a v1 task. On 2026-09-10 it was closed as a

comes here. `FR-468` is owned by `P1-05`; this increment is its counting part.

**Scope (`RG-018`).** A **`WAREHOUSE`** value in `wh_count_program_scopes`' whitelisted scope types, so
one programme can span sites. **No migration**: the scope table ships in `V510033`, and the value is one
more whitelisted scope type, exactly as former `P5-24` specified it.

**Closes** `RG-018` (the counting part; the other configuration scopes are `P0-11`'s, `P1-14`'s and
`P5-21`'s).

**Traps (v2 increment)**

- **A multi-site programme still generates one count per site.** The book is frozen per site and the
  variance posts per site (`L-8`), so spanning sites changes the schedule, never the count document.
- **Warehouse scope reads the user's allowed sites** (`P1-18`): a programme spanning a site the planner
  cannot see is refused, not silently narrowed.

**Acceptance (v2 increment)**
- [ ] A programme with two `WAREHOUSE` scope rows generates one count at each site on its schedule, each with its own frozen book (`RG-018`)
- [ ] **Mobile:** unchanged — each generated count is an ordinary count on the existing RF count screen (`D-13`)
