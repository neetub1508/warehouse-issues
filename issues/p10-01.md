## Why a sibling, said once

`RN-053` / `D-16`: production lives in one switchable module above core, so a pure-storage install carries
no production table and the VAS work order (`V510102`) stays single-movement (`RN-033`, MD-02). Pattern:
`warehouse-india`'s (`p2in-01`) and `warehouse-trade`'s (`p9-01`). Requirements: `docs/frd/FRD-MFG.md`.

## Traps
- **The silent three** (`ModuleImportSelector`, `filterUtils.ts`, `jest.config.js`): the build passes and
  nothing loads / filters / tests. Verify with `docker logs platform-backend | grep "Module configuration found"`.
- **`ai.warehouse.manufacturing` is wrong**: `@ComponentScan("ai.warehouse")` would load it on every install.
- **No compile dependency on india or trade.** A `pom.xml` row for either breaks "india optional" (MD-13)
  and "MRP reaches trade through core" (MD-07). The architecture test (b) is the guard.
- Do not add `enable.warehouse.manufacturing` to `FlywayConfiguration.java` or `application.yml` — verified
  not required (`MODULE-INTEGRATION.md` §2 note).
- `V560000` must not create tables; it only asserts. If a P8 seam has not landed the bootstrap fails **by
  design** — P10 depends on it. Do not soften an assertion to `NOTICE` to unblock a build.
- Do not re-seed `COST_OBJECT_TYPE.PRODUCTION_ORDER` or the two `QC_SOURCE_TYPE` values (FR-621) — core
  owns them; the bootstrap asserts them.
- **`RN-045` disable/re-enable hazard**: `FlywayDriftGuard.repairAndRetry` (`:181-199`) marks the `V56xxxx`
  rows deleted when the module is off, and re-enabling re-runs them — every MFG seed is idempotent.
- Docker only: never run `mvn` / `npm` locally to "verify".
