## Nothing else compiles until this lands

`P0-01` is the first task in the programme and every other task depends on it transitively.
`MODULE-INTEGRATION.md` §14 is a **23-step numbered order across two build systems**, and **three of
its gates fail silently** — the build goes green, the JAR is on the classpath, and the module is
inert. Those three are marked ⚠ below and they are the whole reason this is a task and not a chore.

## Traps

- ⚠ **`ModuleImportSelector.java` is the gate that fails silently.** No entry means the JAR is on the
  classpath and **nothing loads** — `ModuleImportSelector.java:52-55` (constants), `:154-186`
  (blocks). Verify with `docker logs platform-backend | grep "Module configuration found"` **before
  step two**, not at the end.
- ⚠ **`filterUtils.ts` and `jest.config.js` fail silently too.** A missing `COMMON_FILTER_CONFIGS`
  scope makes the filter UI appear to do nothing (`platform/frontend/src/utils/filterUtils.ts:346`,
  213 scopes today); a missing `jest.config.js` root means suites are written and never run.
- **Both bands in the original brief are occupied and hard-reserved.** `V900000`–`V909999` holds 135
  dealer OEM-seed files; `V910000`–`V919999` holds 434 per-client files with versions **deliberately
  reused across the five client directories** (`V910001__` exists five times) —
  `FlywayConfiguration.java:151`, `:157`, `:183` (`C-001`). Worse,
  `FlywayConfiguration.java:296-327` renumbers legacy history into those bands **and then `DELETE`s
  duplicate history rows**, so a collision does not fail loudly, it silently deletes a history row
  and re-runs a migration (`C-002`). `V500000`–`V549999` is verified empty (`C-003`).
- **Migrations are physically flattened at build time.** `Dockerfile.backend:140-181` `cp`s every
  enabled module's `*.sql` into `platform/backend/src/main/resources/db/migration/` before Maven
  runs. Two modules sharing a version is a **build/startup failure, not a merge conflict** (`C-011`,
  R1 §8 trap `T-12`).
- **The frontend merge is last-write-wins across the whole `src/` tree.** `Dockerfile.frontend:80-177`
  is `cp -r /tmp/<mod>-src/. ./src/` in a fixed order, so **every warehouse filename must be globally
  unique** — locales, components, services, types (`C-012`, R1 §8 trap `T-11`).
- **`widget_definitions.chk_module` has been dropped and rebuilt three times** — `V234:36` → `V276:10`
  → `V557:18` — and still admits neither `warehouse` nor `logistics` (`C-014`). A hardcoded DROP/ADD
  discards another module's value. **Read, union, rebuild.**
- **`global_settings.chk_global_setting_module` already allows `'WAREHOUSE'`**, added by
  `platform/V553:14-15` crediting a `V190035 (warehouse-core)` **that does not exist in this
  checkout** (`C-015`, `P-004`). Use it free; still emit the defensive merge in case a later module's
  hardcoded DROP/ADD omits it.
- **Controllers must live under `ai.<module>.controller…`** or `UserActivityTrackingAspect` cannot see
  them — pointcut `UserActivityTrackingAspect.java:59`, module derived from package segment 2 at
  `:167-181`. The recorded module names will be `WAREHOUSEBASE` / `WAREHOUSE` / `WAREHOUSE3PL`
  (`C-049`, R1 §8 trap `T-16`). This is a functional requirement, not a style preference.
- **The adapter package must be a sibling.** `@ComponentScan("ai.warehouse")` would load
  `ai.warehouse.adapter.dealer` unconditionally, in **every** install including ones where dealer is
  not built (`D-1`, `FR-351`). This is the exact trap the accounting round-4 review found.
- **Do not name anything `wms_*` or `scc_*`.** `platform/…/V528:37,57,59` and `V663:17-19` still carry
  hardcoded `wms_*` / `scc_*` / `warehouse-*` permission exclusions from a deleted earlier module
  (`P-014`). They have already run, so they grant a new module nothing — but a `wms_`-prefixed
  permission would inherit a decision nobody took.
- **There is no per-module npm manifest and no decimal library.** Only
  `platform/frontend/package.json` exists (38 deps); no `decimal.js` / `big.js` / `bignumber.js`
  (`C-013`, R1 §8 trap `T-13`). **Every** quantity, cost and valuation figure is computed on the
  backend in `BigDecimal` and sent as a formatted string (`FR-031`).
- **Every migration is individually idempotent.** `FlywayConfiguration.java:246-264` responds to any
  failure with a blind `flyway.repair()` and one retry (`C-047`). `IF NOT EXISTS` / `ON CONFLICT` /
  `WHERE NOT EXISTS`, always.
- **Warehouse-first installs need `FLYWAY_OUT_OF_ORDER=true`.** The effective Docker setting is
  `out-of-order: false` — `application.yml:105` says `true` but `docker-compose.yml:183` overrides it
  and `startX2.sh:200` hard-codes `false`. A warehouse-only install that later adds dealer (`V2xxxx`)
  is **refused** (`C-046`). State it in the install guide; it is not discoverable.
- **Do not copy accounting's band nesting.** `accounting-india` sits at `V602000`–`V602999`, *inside*
  `accounting-base`'s `V600000`–`V609999` (`C-004`, R1 §8 trap `T-15`). Warehouse's five bands are
  disjoint and ordered base < app < adapters < 3PL < India.
