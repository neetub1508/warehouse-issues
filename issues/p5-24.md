## Scope — every v2 junction a lens hung on a v1 task, lifted into one v2 task

`D-14` item 1 makes every association between two independent masters a dated many-to-many junction.
`D-14` item 7 (user decision 3) says a junction nobody needs on day one ships later **and still gets a
task**. This is that task: round 4 moved each of these off the v1 task a lens first named, so no v1 task
carries v2 work (`GAP-REGISTER-R4.md` §1.2, `FR-468`). Every table follows R22 §1.3: `effective_from`
and `effective_to` as `TIMESTAMPTZ`, half-open; one current row per key by `EXCLUDE`; no `is_active`.
The one exception is `whb_uom_scheme_codes` (item 7).

1. **`whb_item_uom_defaults`** (`RG-010`) — `item_id`, `uom_role` (`PURCHASE`/`SALE`/`ISSUE`/`COUNT`, a
   code-list value under `RL-006`), `uom_code`, nullable `counterparty_id`, `channel_id`, `warehouse_id`,
   dates; one current row per scope, `NULLS NOT DISTINCT`. It supersedes `whb_items.purchase_uom_code`
   and `.sale_uom_code`, which `P1-01` keeps in v1. Lines still freeze `uom_code` and the factor (`L-7`),
   so no history moves.
2. **Site-scoped supplier preference** (`RG-011`) — a nullable `warehouse_id` on `whb_item_supplier_sources`,
   key `(item_id, counterparty_id, warehouse_id, effective_from)` `NULLS NOT DISTINCT`, one current
   preferred per item × site. **The dating half shipped in v1** in `P1-03`; this task adds only the site.
   The replenishment run (`P2-15`) resolves the site's own preferred source before the install-wide one.
3. **`whb_warehouse_companies`** (`RG-012`) — role `OPERATOR` or `STOCK_HOLDER`, dates, one current
   `OPERATOR`. The writer's assertion moves here: a movement's `company_id` must hold a `STOCK_HOLDER`
   link at `occurred_at`. In v1 `P0-02` asserts it against the site's scalar `company_id`.
4. **`whb_owner_companies`** (`RG-013`) — role `HOUSE` or `SERVICED_BY`, dates. The one-house-owner-per-
   company partial index moves from `whb_owners` to this table; `P0-06` records the supersession.
5. **`whb_location_owner_dedications`** (`RG-014`) — the set of owners a cage is dedicated to, dated,
   and a commingle policy value `OWNER_SET` that the port evaluates (`FR-087`). `dedicated_owner_id`
   stays the v1 single-owner case.
6. **Configuration scopes** (`RG-018`) — `whb_outbox_subscription_owners` (a subscriber filtered to a set
   of owners, `P0-11`'s subscriptions), `wh_print_template_scopes` (one layout for a client group,
   `P2-14`'s templates) and `wh_inspection_plan_assignments` (the plan per item × supplier × site,
   resolved most-specific-first in the `whb_allocation_rules` shape, `P1-14`'s plans). And a `WAREHOUSE`
   scope value on `P2-04`'s existing `wh_count_program_scopes`, so one programme can span sites.
7. **Tax-scheme side tables** (`RG-020`, `RL-008`) — `whb_item_tax_classifications` (`country_code`,
   `scheme`, `code`, dates), `whb_uom_scheme_codes` (`uom_code`, `scheme`, `code`; `GST_UQC` and
   `UNECE_REC20` become rows) and `whb_reason_code_tax_treatments`. v1 already renamed the ledger
   snapshot to `tax_classification_code` + `tax_classification_scheme` and the reason-code column to
   `tax_treatment_code` (`RL-008`); this task gives a second scheme somewhere to live.

**Not in this task**, although `RG-018` names them: `whb_device_assignments` ships with `P3-03`
(`V500062`, v1.1), `whin_compliance_registration_document_kinds` with `P2-IN-01` (`V540010`, v1), and
`whb_api_client_endpoints` + `whb_api_client_companies` with `P5-22` (`V500066`). Each is built where its
parent table is built.

## Traps

- **Backfill from the v1 scalar, in the same migration, or the resolver sees nothing.** `V500070`
  writes one open-ended row per existing scalar: a `STOCK_HOLDER` + `OPERATOR` row per site from
  `whb_warehouses.company_id`, a `HOUSE` row per house owner, a dedication row per non-null
  `dedicated_owner_id`, and a `GST_UQC` row per non-null `whb_uoms.gst_uqc_code`. `effective_from` is
  the parent row's `created_at`, so a resolver reading history before v2 still finds a link (`RG-012`).
- **The scalar stays until nothing reads it, and nothing new reads it.** `whb_items.purchase_uom_code`,
  `whb_uoms.gst_uqc_code` and `dedicated_owner_id` are kept for v1 readers. Any code written in this
  task reads the junction, never the scalar, or the two drift the way `FR-079`'s three GSTIN copies did.
- **`whb_uom_scheme_codes` is deliberately undated.** A UoM's code in a scheme is an identity fact, like a
  variant value (R22 §1.3 rule 6, `RG-009`). A changed code is a correction by retire-and-reseed
  (`RL-013`), not a history row.
- **`btree_gist` is declared by the migration that uses it** (R22 §1.3 rule 2). `P1-08` declared it
  first, but `V500070` must not assume a v1 migration ran in this database's order.
- **The most-specific-first resolvers are data, not `if`s.** `wh_inspection_plan_assignments` and
  `wh_print_template_scopes` resolve the way `whb_allocation_rules` does: a ranked set of nullable
  scope columns. A template or plan with no scope row keeps its v1 scalar reading.
- **Every new vocabulary is a code list or a closed system value, never a `CHECK` on an open set**
  (`RL-006`). `uom_role` and the two company roles are code-list rows; `OWNER_SET` is a commingle-policy
  value the port already switches on.
