## Scope

**`V510032` — WH-22 — `wh_hold_types` + seed, `wh_holds`.**

`wh_hold_types` is **`D-10`'s twelfth registry, and it lives in the application** because holds are
an application concern: `code`, `name`, `owning_module` (an **opaque string, never an FK**),
`hold_scope` (`ORDER`/`LOT`/`LOCATION`/`ITEM`/`SHIPMENT`), `blocks_allocation`, `blocks_pick`,
`blocks_ship`, `requires_reason`, `release_permission`, `is_system`, `is_active`.
**No `CHECK (hold_scope IN (…))`, no Java enum, no TypeScript string union that re-closes on the
frontend what the backend opened** — the prior warehouse product broke on exactly this, with
`location_type` / `zone_type` CHECKs dropped and recreated with completely different value sets 36
versions after creation (`D-10`, R6).

`wh_holds`: `hold_number` (gapless), `hold_type_code`, `subject_type`, `subject_id`,
`reason_code_id`, `placed_by`, `placed_at`, `released_by`, `released_at`, `release_reason_code_id`,
`note`. Indexes: `uk(hold_number)`; `idx(subject_type, subject_id) WHERE released_at IS NULL` —
the **partial** index is what makes "is this thing held right now" one lookup; `idx(hold_type_code)`.

**Why a record and not a status.** *An order or a lot can be on two holds at once — fraud review
**and** out of stock — and `status = ON_HOLD` cannot represent that; releasing one hold would
wrongly release the whole thing* (`FR-151`). The gate is therefore always a **query**, never a
column read: an order releases to picking only when it has **zero open holds**
(`FR-182`, `P2-08`).

**Release is audited, never deleted.** `released_at` is set and the row stays — same shape as
`whb_reservations` (`WH-SC-185`) and the same shape as
`dealer/V20735` `pdi_storage_slot_assignments`, which `C-033` names as the repo's best
occupancy model: append-only, released rows retained, exclusivity through **partial unique
indexes**, occupancy derived at read time and deliberately not cached. Copy that shape.

**Mass hold and release** by lot, LPN, location, supplier, item or date range (`FR-152`) **writes
one `wh_holds` row per subject, with a reason, and moves nothing** (`RJ-008`).
- **A lot hold is only a `wh_holds` row** whose hold type has `hold_scope = LOT`.
- It is never `whb_lots.status_code`. That column keeps lifecycle states set by jobs, such as
  `EXPIRED`, and is never a hold. `whb_lots` has no `hold_reason_code_id` (`P1-07`).
- It is never a status-change movement either. **A status-change movement is for physical
  segregation only** — stock whose status really changes, such as a quarantine. It is a balanced
  two-line movement at the **same location** changing `stock_status_code`, never an `UPDATE` to a
  position row.

*Before round 4 a lot could be held three ways. The allocator had to consult all three, the `L-4`
rebuild could not reproduce a lot status, and each mechanism released differently.* Single-object
status change is v1. The **recall workflow that drives mass action from a lot is `P5-14`**, and this
task owns only the first half of `FR-152`. `V510032` also seeds the system hold type `RETEST_DUE`
(`hold_scope = LOT`, `blocks_allocation`), which `P2-05`'s retest job places (`RJ-012`).

**Screens.** WS-091 `wh_hold_types` · `WAREHOUSE_HOLD_TYPE` · Department reference — the same
catalogue block as `warehouse-base`'s fourteen. WS-092 `wh_holds` · `WAREHOUSE_HOLD` · Service
Vehicle reference; `subjectLabel` renders through the **display-resolver bean-collection registry**
(`FR-357`, `P0-04`), so on a Mode-A install with no dealer resolver the label falls back and does
not break. Actions: Place · **Release** (gated on the hold type's own `release_permission`) ·
**Mass hold / release** in its own modal.

**Mobile.** `mobile/src/screens/whHold` — place and release from the floor. `none` for WS-091
(a registry), stated as a decision.

## Traps

- **`OD-5` is open and it lands here first among the P2 grids.** CLAUDE.md TypeScript rule #6
  mandates string unions; `D-10` mandates open catalogues; R2 records the conflict as a *documented
  recurring defect in this codebase*. `hold_scope` is catalogue-backed and its dropdown **fetches**;
  it is not a `type HoldScope = 'ORDER' | …` in `types/whHold.ts`. If `OD-5` resolves the other way,
  raise it — do not decide it in this task.
- **`mobile/src/schemas/common.schemas.ts` is a third copy of every dropdown vocabulary**
  (`FR-382`, `BUILD-SPEC-SCREENS.md` §0.7). A `hold_scope` value the backend opened and a mobile zod
  enum closed fails the save **with no message**. Fetch it there too. **`FR-382` is now v1 · P0,
  owned by `P0-16` and worded as a rule** (`RL-009`): a registry-backed mobile field is never a
  `z.enum`. The live schema file carries 36 of them, so an adapter's seed row can make a handheld
  save fail silently. The hold-type picker and the scope dropdown on `whHold` are both registry-backed.
- **`T-9` — `menus` has no unique constraint on `(name, parent_id, menu_level)`**, so
  `ON CONFLICT DO NOTHING` does not stop a duplicate on a Flyway retry. Guard every menu insert with
  `WHERE NOT EXISTS`, the idiom spelled out at
  `assets/…/V60171__Asset_service_contract_permissions_and_menu.sql:154-155`.
- **The hold type's `release_permission` is a permission *name*, not a boolean.** A hold type naming
  a permission that no migration created is a hold nobody can release. Seed the permission in **this
  task's own `WH-206` pair — `V511212` for the verb permission with its `role_permissions` back-fill,
  `V511242` for its `→ :view` `permission_dependencies` row** (`DATA-MODEL.md` §7, `Q-001`).
  **`WH-200`'s `V511000` is released and is never edited**; the earlier instruction to seed into it
  was deleted by `P2-29`.
- **A status-change movement is two lines at the same location.** Same item, lot, serial, LPN, owner
  and duty status; only `stock_status_code` differs. `FR-103` and `WH-SC-138`. Quarantine never
  requires a physical move.
- **`C-033`'s partial-unique-index idiom** (`dealer/V20735:8`, `:43-52`, `:57-69`) is the reference
  for "one active X". Use `WHERE released_at IS NULL`, not a `is_active` boolean that two writers
  can both set.
- **`T-6`** — `WAREHOUSE_HOLD_TYPE` and `WAREHOUSE_HOLD` both go into `COMMON_FILTER_CONFIGS`
  (`filterUtils.ts:346` onward). `placedFrom`/`placedTo` are **two** keys and both must be listed;
  they are `date` (a `TIMESTAMPTZ` column), not `dateOnly`.

## Acceptance
- [ ] One lot carries **two** open holds simultaneously; releasing one leaves the other open and the gate still blocks
- [ ] The allocation and pick gates are **queries over open holds**, not reads of a status column — asserted by putting a second hold on an already-held subject and observing no status field anywhere
- [ ] `wh_hold_types` has **no `CHECK`** on `hold_scope`, no Java enum and no frontend string union; adding a hold type by migration makes it appear in the web grid, the filter dropdown **and** the mobile screen with no code change
- [ ] A release writes `released_at`, `released_by` and a release reason code and **deletes nothing**
- [ ] A mass hold over a lot writes one `wh_holds` row per subject with the reason code, posts **no** movement, and writes nothing to `whb_lots.status_code` (`RJ-008`)
- [ ] The allocator's hold check reads open `wh_holds` only; `grep` finds no read of `whb_lots.status_code` as a hold, and `whb_lots` has no `hold_reason_code_id`
- [ ] A status-change movement is posted only for a real status change such as a quarantine, as a balanced two-line movement at the same location, and **writes no position row directly**
- [ ] `RETURN_DUE` is not a seed and `RETEST_DUE` is: `V510032` seeds the system hold type `P2-05`'s retest job places
- [ ] Release is refused to a user lacking the hold type's own `release_permission`
- [ ] `mobile/src/screens/whHold` places and releases, and its scope dropdown fetches rather than enumerating
- [ ] The export of a filtered, sorted grid reproduces **that** filter and **that** sort - `getEntitiesForExport` consumes its filters map and a sort key, ratcheted by the module's `ExportServiceContractTest` (`P2-29` Rule 1, `FR-400`)
- [ ] **Scenarios** `WH-SC-139` · `WH-SC-098`
