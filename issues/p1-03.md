## Traps

- **`dateOnly`, not `date`, for every column in `FR-327`'s set.** `filterUtils.ts:49-56` documents
  that `date` shifts to UTC day boundaries for `TIMESTAMP` columns, *"which moves the 'from' bound to
  the previous calendar day for users east of UTC"*. An expiry filter that silently includes the
  previous day is a recall that misses a batch. The prior art hit this too — `P-045` is the
  date-typed-statutory-fields remediation.
- **There is no `daterange` filter type** (`filterUtils.ts:30` — eight types). Every from→to pair is
  **two keys**, and **both** go in the scope allowlist.
- **A class column with no job is a defect at merge** (`FR-165`): `abc_class`, `velocity_class` and
  `count_frequency_class` are v1 columns whose recompute is this task's own v1.1 increment for ABC (`FR-463`) and `P6-02` for the other two. Enter them in the
  **dated-obligation register** (`P0-13`) with their owning task, or the register is already
  incomplete on the day it ships.
- **Supersession cycle detection is not optional.** A → B → A is a real data-entry outcome and an
  un-detected cycle makes "resolve to the terminal item" an infinite loop in a request thread
  (`FR-071`).
- **`MERGE_STOCK` posts a movement.** It is not a data fix: merging the old part's stock into the new
  one moves quantity at the old part's cost layers and must go through the single writer service
  (`FR-436`). Gate it on its own permission.
- **No price on `whb_item_supplier_sources`.** `FR-119` keeps commercial terms out of
  `warehouse-base`; a price column here is how a second commercial master starts.
- **`tax_classification_code` must not become an FK.** `FR-066` is explicit, and the prior art's
  relational tax engine is `warehouse-india` v1.1 material (`P-043`), not a base FK target.
- **`is_catch_weight` without the two ledger columns is a dead flag.** `secondary_quantity` and
  `secondary_uom_code` are `P0-02`'s and share `PNR-2` — **verify they are in `V500030` before this
  task merges**, because after that they can never be added (`IRR-35`).
- **Three grids × two platform files**, and `belowReorderPoint` is a **backend-computed boolean
  filter** — a frontend `.filter()` over the rows is a CLAUDE.md CRITICAL #8 violation and is wrong
  under pagination anyway.

**Scope — one scheduled job, over data v1 already keeps (`RK-003`).** v1 ships a cycle-count programme

1. **Two Pareto cut-offs on the site** (`FR-463`, `V500069`): `abc_a_cutoff_pct` and `abc_b_cutoff_pct`
   on `whb_warehouses`, `DECIMAL(9,6)` (`OD-7`), defaulting to 80 and 95. An item whose cumulative share
   of the site's issue value is within the first cut-off is `A`, within the second is `B`, the rest `C`.
   Two columns, not a table: a class scheme per category or per owner is `P6-02`'s, not this task's.
   They are edited on the site's settings (`WS-016`).
2. **The job** — monthly per site, registered in `P0-13`'s dated-obligation register with a
   `whb_job_runs` row per run (`FR-165`, `FR-463`). It reads twelve months of `wh_demand_history.quantity`
   per item × site (`FR-256`, maintained by posting since `P2-15`) and values it at the item's current
   method unit cost at that site (`P2-16`). It writes `abc_class` on `whb_item_site_settings`.
3. **The previous class is kept for one cycle** (`FR-463`): the run copies the old value into
   `previous_abc_class` and stamps `abc_computed_at`, so a count programme and the stock controller can
   see which items moved class this month.
4. **`WS-093` loses its manual label** (`RK-003`). In v1 `P2-04` labels `programType = ABC` *"uses

5. **`P6-02` is narrowed, not duplicated** (`RK-003`): its scope keeps velocity, affinity and XYZ and

**Traps (v1.1 increment)**

- **The job lives in `warehouse`, the columns in `warehouse-base`.** `wh_demand_history` is an app table
  and base never reads a `wh_` table (`D-1`, `WarehouseBaseCouplingTest`). The job calls a base service
  to write the class. It never writes `whb_item_site_settings` by repository from the app module.
- **Issue value is today's cost × history's quantity, stated.** `wh_demand_history` carries quantity,
  not value. Re-costing twelve months of history would need the layer consumptions for every issue, and
  a Pareto ranking does not need that precision. The report says which cost it used (`RK-003`).
- **A zero-demand item is `C`, not null.** An item with no issue in the window still gets a class, so a
  programme scoped to `C` counts it. A null class is how the tail drops out of every programme.
- **A class typed before the first run is overwritten by the first run.** It survives one cycle in
  `previous_abc_class`. There is no manual override in this increment; an override with a reason is
  `P6-02`'s shape, and building half of it here makes two override paths.
- **The job reads an injected UTC `Clock`** (`RL-016`, `P0-13`). The twelve-month window is computed
  from it, never from `LocalDate.now()`, so the test can run the job for any month.
- **Demand history marked `is_migrated`** (`P3-18`) counts. Twelve imported months are exactly what
  makes the first run useful on go-live day.
