## Scope

- **`V510201` — `wh_three_way_matches` + `wh_three_way_match_allocations`** (`WH-101`). The junction is
  **invoice line × GRN line × PO line with an allocated quantity *and* an allocated amount** — never a
  1:1:1 header assumption and never a status column standing in for the relationship.
  One table delivers all four real cases: partial invoicing, multiple invoices per PO, one invoice
  spanning several GRNs, and one GRN line split across invoices.
  **Pairing lines by "closest price" is a named anti-pattern** (`FR-140`).
- **The value leg belongs to accounting.** Warehouse matches quantity and amount and hands the variance
  over; it does not post an accrual, a debit note or a GL entry (`D-6`).
- **`V510202` — `wh_working_calendars` + `wh_working_calendar_days`** (`WH-102`). Per-warehouse **and**
  per-client working days, open and close times, cut-off times and exceptions **layered over the
  `REGISTERED` branch's platform holiday assignment** (`RH-011`) — **used by the same code for
  computing a promise and for measuring a breach.** Without it a 24-hour SLA measured across Diwali
  reports a breach the contract does not consider one.
- **Holidays are read, never re-entered** (`RH-011`). Platform already assigns a `holiday_calendars`
  calendar per branch through `holiday_calendar_assignments`; the warehouse calendar reads the
  `REGISTERED` branch's assignment read-only and adds only per-client cut-offs and exceptions, so Diwali
  is entered once, in platform (`RH-011`).
- **`wh_working_calendar_assignments`** (`V510202`, built with this task) — the sites and clients a
  calendar applies to, as an **effective-dated junction**, not the scalars
  `wh_working_calendars.(warehouse_id, owner_id)` (`RG-017`, `D-14`). The shape is R22 §1.3:
  `effective_from`/`effective_to`, an `EXCLUDE` refusing two overlapping rows for one calendar and
  target, and no `is_active` (`RG-017`).

## Traps

- **One calendar table, two callers, one code path.** The requirement is explicit: *"used by **the same
  code** for computing a promise and for measuring a breach."* Two implementations diverge within one
  release and the customer is shown a breach their contract excludes. `P5-07` references this calendar
  **by code**, not by FK.
- **The allocation junction carries both quantity and amount.** Quantity alone cannot represent a price
  variance; amount alone cannot represent a short receipt. Both, per allocation row.
- **The PO is a movable boundary** (`G-032`). Reference it by its stable string key where the reference
  crosses toward a future supply-chain module, per `IRR-26` — the same rule that makes R7 §2.6's five
  boundaries a refactor rather than a data migration, and the same rule whose absence produced **84 FK
  references into `scc_*`, several to tables that never existed** (`G-025`).
- **Free / scheme quantity changes the match arithmetic** (`FR-141`, `P1-13`'s v1 column): landed value
  spreads across billed **plus** free, so the unit cost falls and any tolerance check **must know about
  it**. A tolerance check that ignores `free_quantity` flags every scheme receipt as a variance.
- **A GRN line split across invoices must not double-allocate.** The invariant is
  `Σ allocated_quantity per GRN line ≤ received_quantity`, enforced as a constraint, not a service loop.
- Cut-off **times** are time-of-day on a `TIMESTAMPTZ`-free column; the holiday is a `DATE`. Every
  statutory or calendar date in this product is a `DATE`, not a timestamp (`P1-03`'s rule) — and the grid
  filter is therefore **`dateOnly`**, because the timestamp type moves the lower bound back a day east of
  UTC (`filterUtils.ts:49-56`).
- `invoiceDateFrom`/`To` are two `dateOnly` filters; `hasVariance` is a boolean. Register both scopes in
  `COMMON_FILTER_CONFIGS` or they are silently dropped.

**Three-way match (WS-088, `V510201`)**
- **The residual is named, never a rounding.** `variance = price variance + unallocated`, where price variance is what the allocations bill over `quantity x order price`, and unallocated is invoice value no receipt line carries. Money rounds once, HALF_UP, at the allocation (`DECIMAL(15,2)`); header figures are sums, never re-rounded. `WhThreeWayMatchArithmetic` is the one copy.
- **Expected is priced on the BILLED quantity only.** Free / scheme units lower the landed unit cost (`amount / (billed + free share)`), never the expected amount, so a scheme receipt is not flagged as a variance (WH-SC-399).
- **The order price is restated per receipt unit** from the two frozen conversion factors (`price x grnFactor / orderFactor`); when the units differ and a factor is missing the allocation is refused (`THREE_WAY_MATCH_UNIT_UNRESOLVED`), never guessed. A blind receipt line (no order line) is refused (`..._NO_ORDER`).
- **Tolerance** is the admin setting `warehouse.three_way_match.price_tolerance_percent` (0..100, `DECIMAL(9,6)`), FROZEN on the match at save; an invalid setting reads as 0 with a warning. MATCHED = every allocation within tolerance AND nothing unallocated; otherwise VARIANCE.
- **The allocation ceiling** (WH-SC-400): the service refuses first, summing LIVE matches' allocations and this match's own earlier rows; `trg_wh_three_way_match_allocations_assert_ceiling` is the last guard.
- **Currency**: blank = the site operating company's base currency; every matched order must be in the match currency (`..._CURRENCY_MISMATCH`). Allocated amount above the invoice total is refused at validation.
- **A saved match cannot move site or supplier** (its allocations are evidence of both). The supplier invoice ref is unique per supplier while live, checked across sites - `existsLiveInvoiceRef` needs a `WhWarehouseScopeContractTest` EXEMPT_METHODS line (RETURNED).
- **Match number is issued per site at create** (series `TWM` under module `warehouse`); no Delete - a mistaken match is CANCELLED and keeps it.
- **Approve / Cancel notes** travel in `WhDocumentTransitionRequest.justification`; a VARIANCE needs a note to be approved, a cancel always needs one; `reasonCodeId` is ignored. No maker-checker. Each verb has its own authority (`:match`, `:approve`, `:cancel`).
- **Prices are not masked by cost visibility** - the screen is a finance desk and the price IS the evidence.
- Recorded-not-fixed: `wh_goods_receipts.invoice_matched` has no writer; Approve is the natural point, not built (FR-242, AHO-OPEN-05). Open interface: the approved variance is read by the ledger side by reference - warehouse writes no accrual, debit note or journal.

**Working calendars (WS-127, `V510202`)**
- **ONE resolver, `WhWorkingCalendarService`**, serves both the demand-order promise date (`promiseShipBy`, set on create when the request carries none) and the 3PL SLA clock (`workingTime(code, site).plusHours`). Moving a platform holiday moves both (WH-SC-397, one test, one code path).
- **Resolution**: site + client > client > site > default, the rule logged (WH-SC-398). Day precedence: a DATE row > the platform holiday of the site's REGISTERED branch (its own holiday calendar, lowest id; else the platform default; RESTRICTED holidays ignored; a half day splits at the midpoint) > the WEEKDAY row > closed. No warehouse table copies a holiday (RH-011).
- Cut-off: an order before the day's cut-off (blank = closing) ships that day's close; otherwise the next open day's close; the walk stops at 730 days.
- **The default calendar cannot be retired**; zero defaults is allowed (then an unassigned site has no calendar and the promise stays null). The code is immutable (SLA definitions name it).
- Assignments are dated rows, ended never edited; an overlapping row for the same target is refused (`EXCLUDE`).
- Mobile: `none` for both screens (D-13).

**P5-07 unlock**

- The measurement job's calendar skip is gone: ORDER_CYCLE_TIME with a calendar counts WORKING hours per order (`Wh3plSlaCalendarVerdict`); ON_TIME_SHIP keeps its SQL verdict (the promise it compares with is already calendar-derived). A calendar retired under an existing definition fails that window, named.

The single read carries `measured`; the definition modal disables the calendar picker and says why when it is true.
- **The drill-through tracks the LIVE calendar - ACCEPTED** (F2). A figure frozen at measure time is not re-derived, but its failing-orders list is re-read on the calendar as it is now: a changed week, date exception or moved platform holiday can change which orders are listed for an old window. Persisting per-window failing ids was not taken (it needs a warehouse-3pl migration). The drill-through resolves a RETIRED calendar (`WhWorkingCalendarService.historicalWorkingTime` - by code without the active filter), so an old window never answers 422; the measurement job still requires an ACTIVE calendar.
- **The promise and the SLA use one calendar** (F3, P5-07 acceptance 3). At definition save, a named calendar is refused (`422 SLA_CALENDAR_MISMATCH` on `calendarCode`) when any attached client row not already ended resolves TODAY to another calendar - per each site the client holds an in-force site+client assignment at, else client-wide (its client-only row, else the default) - via `WhWorkingCalendarService.resolvedCodesForOwner`. A client nothing resolves for is not refused (it has no promise calendar). Limitation recorded: a client with no site+client row is judged client-wide, so a site-only calendar at a site it ships from is not seen. **ON_TIME_SHIP ignores the definition's calendar** (its deadline is the order's promise, already calendar-computed); the check keeps the stored code honest.
- **Working calendars are ORGANISATION-WIDE masters** (F4). Update, retire / reactivate and taking the default (on create or update) need the unscoped tier (`wh_working_calendars:view:all` or ADMIN), refused `403 WORKING_CALENDAR_ORGANISATION_TIER_REQUIRED` (`WhWorkingCalendarQueryService.requireOrganisationTier`); reactivation is gated with retire because it moves promises org-wide too. Creating a non-default calendar and assignment add / end stay site- and owner-scoped as before. Assets parity note: `AssetWorkingCalendarService` has no calendar master and no write surface (it reads platform holiday calendars and branch hours), so nothing there to align; assets unchanged.
- **The promise is re-computed on edit** (F5). `WhDemandOrderService.update` calls `promiseShipBy(site, owner, createdAt)` when the request carries no promise or the owner changed (an explicit promise on an unchanged owner is kept). `WhDemandOrderPromiseRecomputeTest`.
- **The SLA consumer is proved end to end** (F6). `Wh3plSlaCalendarVerdictTest`: an ORDER_CYCLE_TIME order shipped 30 clock hours after creation across a platform holiday is MET for a 24h limit (numerator and drill-through agree), the same order without the holiday is a breach, and a retired calendar still answers the drill-through.
- Recorded (no change): **`MAX_DAYS_WALKED` (730) diverges by caller** - the promise returns null (no promise, order leaves ON_TIME_SHIP), the SLA clock falls back to wall-clock minutes; both log a WARN. Intended: a promise is optional, an SLA deadline is not. **Price tolerance is symmetric** (`abs(variance)`), so under-billing beyond tolerance is also a VARIANCE - ratified. **Zones**: `promiseShipBy` picks the resolution date in the SITE zone and walks in the CALENDAR zone; the calendar zone is authoritative for the walk, and the two differ only when a site is assigned a calendar of another zone near midnight.
