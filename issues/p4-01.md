## The four defects carried forward as blockers, from `P-043`

The prior implementation's own audit found these. They are **design defects, not typos**, and
`FR-325` makes them blockers of this pack:

| From | The defect | What this task must do |
|---|---|---|
| **T-H1** *(was unresolved)* | Five seeded intrastate slab rules (0 / 5 / 12 / 18 / 28 %) all carry `hsn_id = NULL`, `source = dest = DTA`, `interstate = false`, `priority_order = 50` — **indistinguishable by any matchable column**, so a resolver matches all five simultaneously and nothing forces a deterministic winner | Design the **discriminator model before the first seed row**. A tax engine with a nondeterministic resolver is worse than none, because it is confidently wrong |
| **T-H2** *(was fixed)* | No `UNIQUE(tax_rule_id, tax_component_id)` → two CGST rows on one rule → **silent double taxation** | Keep the unique key |
| **T-H3** *(was deferred)* | **Overlapping effective-date ranges** on the HSN master, the SAC master and the rules — *"rate for HSN X on date D"* can return two rows | `btree_gist` + an **`EXCLUDE`** constraint |
| **T-M11 · T-M13** | Slab seeds carry `rule_code = NULL`, and **NULLs never collide, so `ON CONFLICT DO NOTHING` can never fire** — re-running duplicates every rule. `version` exists for immutable versioning with **no `UNIQUE(rule_code, version)`** | `rule_code NOT NULL`, and `UNIQUE(rule_code, version)` |

**The resolution audit is the surface that answers *"why did it pick that rate"***, and it is the
reason the engine is auditable at all.

| GST state codes | **36** seed rows (states + UTs) | **RE-VERIFY** |

**Citations.** CGST Act s.35/s.36 with Rules r.56, and CGST Rules r.28 — **substance confident,
section and rule numbers `UNVERIFIED`**. Where the rule is known and the citation is not, this task
states the rule and marks the citation `UNVERIFIED`; **it does not invent a section number.** A
confidently wrong section number in a design document becomes a confidently wrong comment in a
migration and then a confidently wrong answer to an auditor.

## Traps

- **`warehouse` never computes tax** (`OD-9`, `FR-294`, R3 `D4`). It captures the tax-relevant facts
  — HSN, place of supply, `is_taxable_supply` **frozen at creation**, taxable value — and hands them
  over. **This is unresolved and it decides whether these six tables exist at all**: the India pack
  is **50 tables without the engine and 56 with it**. `INDIA-LOCALISATION-PACK.md` §11.4 recommends
  the `OD-1` three-install-state shape — warehouse carries the engine and uses it **only** where no
  accounting module is present — and explicitly refuses to number it, because inventing an `OD-n`
  there is how two things end up sharing one id.
- **The item stores its classification code as a string, never an FK into `whin_hsn_tax_master`**
  (`FR-066`). An FK from `warehouse-base` into a `whin_` table breaks `D-11` in the direction that
  cannot be undone, and it makes the core unsellable outside India.
- **No `whb_` or `wh_` table gains a foreign key to a `whin_` table, in either direction**
  (`D-11`, `MODULE-INTEGRATION.md`). Cross-module references are stable string keys or external-ref
  rows.
- **Do not build a second number-series allocator.** `warehouse-india` registers series *kinds* and
  consumes the base allocator (`INDIA-LOCALISATION-PACK.md` §11.3). The prior art built its own and
  ended up with `scc_document_sequences` carrying no `updated_at` even though `next_value` mutates on
  every allocation.
- **`btree_gist` must be created before the `EXCLUDE` constraint**, and `CREATE EXTENSION` in a
  Flyway migration needs the right privileges — verify against the Docker Postgres before writing
  `V540111`, because a failing migration takes the **whole backend** down.
- **A migration that only `RAISE NOTICE`s its checks is not verified** (`IMPLEMENTATION-PLAN.md`
  §10). Assert the seed guards with `RAISE EXCEPTION`.
- **Two prior security findings are carried as constraints, not features** (`P-044`, `FR-326`, and
  they bind the whole India module including this task): compliance request and response bodies are
  **never stored unencrypted**, and **no demo or test controller may trigger a real statutory
  filing**. The prior `ComplianceDemoController` could fire real IRN and EWB filings from a minimal
  demo body with random source-document ids, in production code.
- **Rates and percentages are `DECIMAL(9,6)`** — any `*_percent` or `*_ratio`. `DECIMAL(19,8)` is the
  **currency-conversion** type and nothing else, even where the column is named `..._rate`
  (`DATA-MODEL.md` §5.1; the sibling set stated this row wrongly for three rounds).
- **`V541100`–`V541149` is a sub-allocation of `WIN-30` and is stated, not taken silently**
  (`IMPLEMENTATION-PLAN.md` §2.9 row 3). `INDIA-LOCALISATION-PACK.md` §11.2 allocates the **same
  numbers to wave-2 DDL** — that is a live collision between two documents and it is filed in
  DEFECTS-FOUND. **`DATA-MODEL.md` §7.6 wins** (`DECISIONS.md` precedence), so this task's numbers
  are the ones above.

## Acceptance
- [ ] Five intrastate slab rules can **never** all match one query: a deterministic discriminator exists and is asserted by a test that seeds all five and resolves exactly one
- [ ] `UNIQUE(tax_rule_id, tax_component_id)` exists, and two CGST rows on one rule are refused
- [ ] Overlapping effective-date ranges are refused by an `EXCLUDE` constraint on the HSN master, the SAC master and the rules
- [ ] `rule_code` is `NOT NULL` and `UNIQUE(rule_code, version)` holds; re-running the seed duplicates nothing
- [ ] Every rate resolution writes a `whin_tax_resolution_audit` row that answers *"why did it pick that rate"*
- [ ] `whb_items` holds its classification code as a string and no FK into `whin_hsn_tax_master` exists
- [ ] No `whb_`/`wh_` table has a foreign key to a `whin_` table in either direction
- [ ] An inter-state stock transfer above the reporting threshold obtains an IRN through the **same** e-invoicing adapter a sales invoice uses
- [ ] An install **below** the threshold is unaffected and the v1 transfer document still ships
- [ ] Every threshold in the migration comments carries its value **and** a RE-VERIFY marker; no section number is stated that is not verified
- [ ] Every percentage column is `DECIMAL(9,6)`
- [ ] **Scenarios** `WH-SC-214`
