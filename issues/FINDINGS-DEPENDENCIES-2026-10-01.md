## Dependency meanings

- **Start handoff:** the specific contract, setup or evidence needed before dependent implementation. The upstream issue can remain open for later tests.
- **Completion prerequisite:** upstream evidence needed for this task’s final acceptance. Tests and independent repairs can begin sooner.
- **Conditional/external:** applies only to the named enabled customer capability; requires provider/receiver/hardware/data or a recorded scope decision.
- **Related issue:** historical ownership or overlap. It is not automatically a blocker.

The detailed reason for every start handoff and external prerequisite is in the corresponding issue. No dependency is claimed to be already satisfied merely because an old issue is closed. This graph is a reviewed scheduling baseline; implementation may uncover additional dependencies, which must be added before dependent work proceeds.

## Waves

0. Confirm adopted contracts/package boundaries and repair test/runtime infrastructure.
1. Protect stock/value/evidence and unblock core execution; establish repeatable install fixtures.
2. Complete task, import, reporting, setup and operational contracts; prepare recovery and enabled connectors.
3. Run integrated operator, security, performance, cutover, recovery and customer-specific acceptance against the corrected paths.
4. Consider deferred archive/tax-basis scope only where required; documenting an existing exclusion does not wait for other waves.

Waves are not blanket barriers. The task-specific dependencies govern execution. No whole-issue dependency cycles are present; contract handoffs explicitly separate design from later acceptance.
