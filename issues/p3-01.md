## This task is where mobile stops being a mirror

Every other phase applies `D-13` by building a web screen and its mobile counterpart. **P3 inverts
it.** For the nine screens below the handheld *is* the product and the web grid is the supervisor's
view of it. `WH-SC-227` — *"an operator with a handheld and no desk … no step requires a browser"* —
is half the v1.1 exit criterion, and it cannot be met by nine `EntityListScreen` instances.

## Scope

- **A new screen family under `mobile/src/screens/`**, not `EntityListScreen` instances. `FR-220`:
  `EntityListScreen` is a list-plus-filters component built for office use and is the wrong base for
  one-handed, gloved operation. The nine screens are `screens/whRfReceive`, `whRfPutaway`,
  `whRfMove`, `whRfPick`, `whRfPack`, `whRfShip`, `whRfCycleCount`, `whRfStockEnquiry`,
  `whRfTaskList` (`BUILD-SPEC-SCREENS.md` §6.9).
- **The interaction contract, applied identically to all nine** (`FR-219`): one active input · scan
  advances with **no confirm tap** · no free text where a scan exists · no mouse · no scrolling · no
  modal stack · a **persistent current-task banner** · an **always-available report-exception
  action** · every screen **resumable at the exact scan it reached** after a dropped connection.
- **Scan-to-response under 300 ms measured at the handheld** (`FR-424`, `FR-422`), not at the server.
  The measurement harness is part of this task; a target nobody measures is a sentence.
- Each screen backs a web screen and posts through the port:

| RF screen | Backs | Posts through |
|---|---|---|
| WS-229 Receive | WS-075 / WS-076 | `POST /movements` |
| WS-230 Putaway | WS-082 | `POST /movements` |
| WS-231 Move | WS-038, WS-042 | `POST /movements` |
| WS-232 Pick | WS-102 | `POST /movements` |
| WS-233 Pack | WS-103 / WS-104 | `POST /movements` |
| WS-234 Ship | WS-105 | `POST /movements` |
| WS-235 Cycle Count | WS-094 / WS-095 | count API, then `POST /movements` at post |
| WS-236 Stock Enquiry | WS-042, WS-071 | read-only |
| WS-237 Task List | WS-059 | task API |

- **One shared, GS1-capable scanner component, extracted from `AssetQrScannerScreen`** (`RH-008`,
  `PP-9`). The only scanner in the app is asset-specific
  (`mobile/src/screens/assets/AssetQrScannerScreen.tsx:130-131`: `qr`, `code-128`, `code-39`,
  `ean-13`, with no DataMatrix and no GS1), so all nine screens scan through the extracted component
  rather than nine copies of that one (`RH-008`).
- **Every endpoint in the table above is marked in its screen's mobile block as covered by
  `PORT-AND-ADAPTER-CONTRACT.md` §10.2's additive-only rule** (`RL-017`); the rule and the
  `warehouse.mobile.min_app_version` check are `P3-04`'s (`RL-017`).
- **i18n en / fr / hi on every string**, registered in the module SafeTranslation. `S-095`: warehouse
  operators are the most language-diverse users in the suite, and the RF screens are the one place
  where Hindi and regional languages actually decide whether the system is used.

## What the handheld does when the network drops

**This task ships the *behaviour*; `P3-04` ships the queue.** Stated here per screen so the family is
designed against it rather than retrofitted:

| Screen | Behaviour on a dropped connection | Owner |
|---|---|---|
| WS-230 Putaway · WS-232 Pick · WS-236 Stock Enquiry · WS-237 Task List | **read-cached** — the last known list survives the dropout and the screen keeps working from it | `P3-04` |
| WS-229 Receive · WS-232 Pick · WS-235 Cycle Count | **queued write** — scans buffer locally, replay on reconnect, **one idempotency key per scan**, conflicts surfaced and never swallowed | `P3-04` |
| WS-233 Pack · WS-234 Ship | **online-only, and it says so on the screen.** Pack needs carton weight and a photo from the device; dispatch is the inventory-relief event and must not be replayed blind | this task |

**Resumability is this task's obligation regardless of the queue** (`FR-219`, `WH-SC-229`): after a
reconnect the screen returns to the exact scan it reached, because an operator who has to restart a
37-unit pack from scan 1 will stop using the handheld.

## Traps

- **`EntityListScreen`/`ListHeader` supports `dropdown` and `text` filters and *not* dates.**
  `mobile/src/components/common/ListHeader.tsx:216` declares
  `type?: 'dropdown' | 'text'`; there is no date type. CLAUDE.md's *"only supports dropdowns"* is
  stale (R1 `CM-1`). Neither fact rescues the RF screens — **they do not use `ListHeader` at all** —
  but any warehouse mobile screen that *is* an `EntityListScreen` (WS-060, WS-070, the two reports)
  inherits the date-filter gap and must ship a **dropdown of named periods** instead.
- **Mobile API services are object literals, not `BaseApiService` subclasses** —
  `mobile/src/api/documentCategoryApi.ts:61`, `mobile/src/api/serviceJobApi.ts:31` and 200-odd
  siblings all use `export const xApi = { … }`. Do not refactor and do not import the web service.
- **`mobile/src/schemas/common.schemas.ts` is 5,852 lines and is a third copy of every dropdown
  vocabulary** (`wc -l` on the live tree, 2026-09-02). A catalogue value the backend opened and this
  file closed as a zod enum **fails the save with no message**. Every RF screen that renders a
  reason code, a stock status, a task type or a disposition **fetches** the catalogue (`FR-382`,
  `OD-5`); it never re-enumerates one. `P3-04` owns the sweep, this task owns not creating new ones.
  `FR-382` is a v1 · P0 rule owned by `P0-16` (`RL-009`): a registry-backed field is
  `z.string().min(1)` validated against the fetched dropdown list, never a `z.enum` (`RL-009`).
- **The frontend and mobile trees merge last-write-wins** (`Dockerfile.frontend:80-177`). Every file
  this task adds is `whRf*`-prefixed and globally unique.
- **`FOR UPDATE SKIP LOCKED` has zero precedent in this repository** —
  `grep -rn "SKIP LOCKED" --include=*.java --include=*.sql .` → **0** on 2026-09-02. WS-237 pulls its
  next task through it; the claiming query is `P3-02`'s and is load-tested there, not assumed here.
- **300 ms is measured at the handheld, not in the controller.** A p50 server timing with a 400 ms
  round trip fails `FR-424` and passes every backend test.
- **No offline mutation queue exists anywhere in the mobile app** —
  `grep -rlE "persistQueryClient|createAsyncStoragePersister|offlineQueue" mobile/src` → **0**.
  `mobile/src/services/networkService.ts:124-125` detects the drop and nothing queues behind it. Do not
  design a screen that assumes one exists before `P3-04` lands.
