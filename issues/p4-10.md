## ⚠ This task owns a migration in another module's band, deliberately

**`V530060` (`wh3_client_gst_registrations`) sits in the 3PL band** per `DATA-MODEL.md` §7.5 `W3-13`,
because the table's prefix is `wh3_` and **the band follows the prefix**. But **`FR-301`'s module is
`3pl·india` and its phase is `P4`**, and **the task follows the requirement's phase**. Both rules are
obeyed; the crossing is flagged in `IMPLEMENTATION-PLAN.md` §2.9 row 6 so a reader does not read it
as an error.

**Consequence: this is the only `P4 → P5` dependency in the whole plan.** `wh3_client_gst_registrations`
needs `wh3_clients`, which is `P5-01`'s.

## Scope

- **`V540180`** — `whin_compliance_tasks`, `whin_compliance_rules`, `whin_compliance_rule_conditions`
  (`DATA-MODEL.md` §7.6 WIN-21). Scheduled compliance obligations, and the **bounded rules** that
  raise them: **whitelisted subject columns and operators**, never a JSONB condition bag.
- **`V530060`** — `wh3_client_gst_registrations` (`DATA-MODEL.md` §7.5 W3-13): a 3PL client's GST
  registrations with **the warehouse declared as an additional place of business**, a **certificate
  document**, effective dates and an **expiry alert** (`FR-301`). *A 3PL is asked about this in every
  RFP, because the client cannot legally hold stock at an undeclared premises.*
  The effective dates follow R22 §1.3 (`RG-021`): `effective_from TIMESTAMPTZ NOT NULL` and
  `effective_to TIMESTAMPTZ NULL`, half-open, with an `EXCLUDE USING gist` over `client_id`, `gstin`,
  `warehouse_id` and the range, so two registrations of one client, GSTIN and warehouse never overlap —
  and **no `is_active`**, because `effective_to` is the only end (`RG-021`).

## Traps

- **`V530060` is in the 3PL band and is owned by a P4 task.** Do not "correct" the number into the
  India band — the prefix decides the band (`D-2`, `D-3`) and the phase decides the owner. Anyone who
  renumbers it will collide with `W3-14` or the `V530101`–`V530999` correction reserve.
- **This task depends on `P5-01`**, which is the only edge between the two v2 phases. If P4 and P5 run
  in parallel — and `IMPLEMENTATION-PLAN.md` §3.6 says they can — this is the single point where they
  must synchronise.
- **Rule conditions are rows with a whitelisted `subject_column` and `operator`, never a JSONB bag**
  (`FR-383`, and the same shape as `whb_alert_rule_conditions` in `P3-16`). A condition that becomes
  a dynamic `WHERE` fragment is a SQL-injection surface; the whitelist discipline is
  `SqlSortBuilder`'s and it is CLAUDE.md CRITICAL 3.
- **A compliance task with no scheduled job that raises it is a defect at the moment it is merged**
  (`FR-165`). The rule engine's evaluation job needs its `whb_job_runs` row (WS-064), and so does the
  registration-expiry alarm.
- **The GST certificate is a document, and the platform `documents` table has no polymorphic owner.**
  Every module builds its own link table; use **`NO ACTION`**, not `ON DELETE CASCADE` —
  `acc_document_links` uses cascade (`V600110:104-105`) and for a statutory certificate that silently
  removes the evidence when the file row goes.
- **A registration expiring with the client's stock still on our floor is the finding**, not the
  expiry itself. The alarm has to fire far enough ahead to re-declare, and *how far* is
  configuration.
- **`warehouse-3pl` depends on base **and** app, and neither depends on it** (`D-1`, `FR-281`). This
  task writes a `wh3_` table; it must not create an edge from `whin_` into `wh3_` or the reverse —
  the two modules are siblings, and cross-module references are stable string keys or external-ref
  rows (`D-11`).
- **GSTIN lives on `branches` and is per-state** (`INDIA-LOCALISATION-PACK.md` §3.3, CLAUDE.md
  Module Architecture). **Our** GSTIN is never duplicated onto a warehouse; **the client's** GSTIN is
  the client's and lives here. Those are two different facts and conflating them is how a 3PL files
  under its own registration for a client's stock.
- **Every compliance due date is a SQL `DATE`** (`FR-327`, `P-045`); **the registration's
  `effective_from`/`effective_to` are not** — they are `TIMESTAMPTZ`, because a dated junction is
  resolved at an instant, and the UI's date is converted to site-local midnight from
  `whb_warehouses.timezone` (`RG-021`, `FR-439`). `V530060` declares `btree_gist` itself for its
  `EXCLUDE` (`RG-021`). Both
  `dueWithinDays` and `expiringWithinDays` are **dropdowns of named horizons**, not date filters, so
  the decision survives the mobile constraint (`ListHeader.tsx:216`).
- **`permission_dependencies` is a PLATFORM table** (`V248:17-30`) — **insert rows, never
  `CREATE TABLE`**; columns are `permission_id` and **`dependent_permission_id`**.

## Decisions recorded at build
Gate round 1 (reviewer + functional-reviewer), ratified by the driver:
- **One OPEN task per rule and subject** (F2). The evaluator raises no task for a subject that already carries an `OPEN` task of the same rule, whatever the due date; `uk_whin_compliance_tasks_rule_subject_due` stays as the re-run backstop. A recurring obligation is raised again once the open task is completed — not one task per period.
- **Certificate replace is an edit** (F1). `POST /{id}/certificate` stays held by `:create` so the Add modal can attach to the row it just created, but a caller without `:edit` is refused (403 `CERTIFICATE_REPLACE_REQUIRES_EDIT`) when a certificate is already linked.
- **The expiry alarm is stamped only once someone was told** (F3). An alarm that reached no one fails the run (WS-064) and re-fires on the next run; an `effective_to` edited between the read and the stamp is not counted.
- **Only an APOB successor silences the expiry alarm** (F4). A later registration of the client at the warehouse covers the end only when it itself declares the warehouse as an additional place of business.
- **Rules may save only ACTIVE code-list values** (F5); a retired value stays readable on rows that hold it.
- **`dueWithinDays` is a named horizon** (0, 7, 30, 60, 90) — any other value is refused 400 `DUE_WITHIN_DAYS_INVALID` on the grid, statistics and export.
- **The client GST grid has no search box** — the unreachable `search` parameter is removed from `/management` and `/export`.
- **Record-not-fixed:** the Compliance Rules list stays a plain table inside its modal (no grid preferences, export or view popup), and the task grid's Rule filter lists active rules only.
- **Contract amendments accepted as built:** the certificate is a direct FK column `certificate_document_id` (not a link table); the task grid shows the subject's label (licence / bond / GSTIN number) rather than its id; the compliance rules carry a dropdown cache; both jobs alert holders of a named permission. `WhinComplianceSubjects.java` (the evaluator whitelist) landed in `d352f776ac` and belongs to this task.
