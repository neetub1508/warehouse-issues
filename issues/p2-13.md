Both numbers sit in the **inbound** block (`V510010`–`V510020`) even though the task is P2, because
they belong beside receiving in the migration order. That is deliberate and it is not a collision:
`P1-12`…`P1-16` own `V510011`–`V510018`.

**A supplier return is not an RMA** (`FR-139`). It is **its own document with its own state ladder**
— `DRAFT` → `APPROVED` → `PICKED` → `DISPATCHED` → `CLOSED` / `CANCELLED` — and **inventory is
reduced only at dispatch**. *The prior system's bug was a QC-fail auto-RMA stuffing the supplier's
name into a customer field.* The outbound movement shape is `P2-12`'s `FR-275`; the document, the
ladder and the state gates are here. Columns: `return_number` (gapless), `supplier_counterparty_id`,
`warehouse_id`, `owner_id`, `origin_grn_id`, `origin_lot_id`, `reason_code_id`, `status`,
`dispatched_at`, `total_value`.

**Quarantine disposition is a workflow with a QA-role gate** (`FR-134`) — release / reject / return
to supplier / scrap — and **regulated item classes are quarantined by default on receipt rather than
flagged**. The default chain is item → supplier → `AVAILABLE` (`FR-129`, `P1-13`); a regulated class
overrides it to `QUARANTINE` **on the first transaction**, and the stock is never `AVAILABLE` for an
instant. Release posts a **balanced status-change movement at the same location**
(`QUARANTINE → AVAILABLE`) with a **mandatory reason** — quarantine never requires a physical move.

**Inbound reconciliation is a decision centre that never moves stock itself** (`FR-138`). A case
carries a **type** (quantity / over-receipt / invoice / ASN / inventory variance / receipt reversal /
supplier return), a **severity**, a **status**, **nullable document links**, a **root cause** and —
the load-bearing column — a **resolution-document pointer**. Cases are **auto-created at variance
points**, and **each of the five resolutions creates a document**. The case itself posts nothing;
its resolution names the document that does.

> *`P-028` places inbound reconciliation at v1.1; `DECISIONS.md` §5 makes v1.1 = P3 execution and
> puts adjustments in the v1 exit criterion, so it lands v1/P2.* That reasoning is `FR-138`'s own —
> do not re-defer it.

**Screens.** WS-083 `wh_reconciliation_cases` · `WAREHOUSE_RECONCILIATION_CASE` · Service Vehicle —

## Traps

- **The case never posts a movement.** `wh_reconciliation_cases` has **no** `movement_id` column.
  It has `resolution_document_type` + `resolution_document_id`. The moment a case can move stock, it
  becomes a second adjustment path with no reason-code discipline.
- **"Quarantined by default" is a receipt-time default, not a post-receipt status change.** If the
  stock is `AVAILABLE` for one transaction and then moved to `QUARANTINE`, the allocator could have
  taken it in between. `FR-129`'s defaulting chain resolves **before** the first movement is built.
- **A status-change movement is two lines at the same location**, differing only in
  `stock_status_code` (`FR-103`). It is not an adjustment and it does not change quantity.
- **`C-025`** — `AccessoryIssuanceService.java:277-279` swallows non-`BusinessException` failures
  and continues (line reference **refined from R1's `:275-278`** by `COEXISTENCE.md` §8.1); the
  `BusinessException` branch immediately above at `:270-276` correctly re-throws. Do not copy the
  general `catch (Exception e)`.
- **`V510019`/`V510020` are in the inbound block but this is a P2 task.** Do not "tidy" them into
  `V510036`–`V510039`; the numbers are pre-allocated in `DATA-MODEL.md` §7.3 as WH-10/WH-11 and
  `tools/check-design-set.py` fails on a renumber.
- **The QA role is a permission, not a job title.** Seed it in `P1-20`'s `V511000` block and gate
  release on it; `permission_dependencies` rows are **inserted, never created** (`T-10`) — the
  columns are `permission_id` and **`dependent_permission_id`**.
- **`T-9`** — `WHERE NOT EXISTS` on the menu inserts.
- **`T-6`** — two scopes; `openedFrom`/`openedTo` and `createdFrom`/`createdTo` are `date` pairs and
  **all four keys** are listed.
