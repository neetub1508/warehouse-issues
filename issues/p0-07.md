## Traps

- **`whb_companies` is warehouse's own, and it is not `automotive.companies`.** The real company
  master for the dealer vertical lives in `automotive` and warehouse **must not depend on it**
  (`P-010`, `C-035`). The prior art made this exact mistake: `SccCompany` was the designated owner of
  a shared company master and **was never built**, leaving an unconstrained `scc_company_id UUID`
  column pointing at no table in any module (`SCC_MODULE_ISSUES_ANALYSIS.md` §4.4). External links go
  through `whb_company_external_refs` with an **opaque `source_module`**, never an FK out of the
  module.
- **`period_id` is `NOT NULL` on the movement, so periods must be seeded before the first post.**
  An install with no period row cannot post at all — that is intentional (`FR-021`), and the install
  guide must say so, or the first demo fails with an FK violation nobody can read.
- **A `CLOSED` period refuses a reversal too.** This is the clause reviewers soften under pressure
  ("but they need to fix it") and it is exactly what `L-8` forbids. A soft close plus an approved,
  **recorded** override is the sanctioned path; a hard close admits nothing.
- **The override is gated by a session GUC in the trigger** (`I-10`, `V500032`).
  The GUC is **`whb.period_override_id`** (`MPR-OPEN-03`), and it carries the **id of the override
  row**, not a boolean — so `I-10` can name the row that admitted the movement instead of merely
  observing that somebody asserted permission. `DATA-MODEL.md` §6.4 and
  `WhbPeriodOverrideRecorder.OVERRIDE_GUC` both read exactly that name; an earlier draft of this
  bullet said `current_setting('warehouse.soft_close_override', true)`, which names neither the
  right GUC nor the right kind of value. **`P0-02` writes `I-10`/`V500032` from this body**, so the
  name here is the one that reaches the trigger. `SET LOCAL` (via `set_config(..., is_local => true)`)
  is transaction-scoped and *should* be safe through the connection pool, but the idiom is
  **untested in this codebase** — verify it in a real Docker run before relying on it.
- **`pendingHandoverCount` couples this screen to `P0-12`.** The close action refuses while the
  accounting-handover queue is non-empty; if `P0-12` has not landed the count is zero and the guard
  is vacuous. Sequence the two, or land the guard disabled behind an explicit flag and enable it in
  `P0-12` — do not ship a guard that reads as enforced and is not.
- **`branches.branch_name`, not `branches.name`.** Any join from a warehouse screen onto the platform
  branch table uses `branch_name` (R1 §8 trap `T-18`, `V149:18`).
- **Both date pairs are `dateOnly`, not `date`.** `start_date`/`end_date` are SQL `DATE`
  (`FR-327`), and `filterUtils.ts:49-56` documents that `date` shifts the lower bound to the previous
  calendar day for users east of UTC.
- **Three grids need `default_columns` AND `default_filters`** as `'[…]'::jsonb`, three scopes in
  `COMMON_FILTER_CONFIGS`, and the two `dropdown.*` names in `CacheConfiguration.java`.
- **KEEP-SCALAR: stock-period scope** (`RG-026`). A period is scoped `(company, warehouse | all)` and
  resolves to exactly one row, because `whb_stock_movements.period_id` is single and `I-10` reads
  one period. **Never scope periods by branch** — not through `whb_company_branches`, not through
  `P1-05`'s `whb_warehouse_branches`: a period↔site or period↔branch junction admits two open
  periods over one site and date, which PostgreSQL cannot exclude across a junction and its parent
  without a trigger over both.

## Carried out of the P0-07 build — recorded, not built

These came out of building this task. **None is built here**, and each says why and who owns it.

- **Nothing anywhere captures a soft-close approval.** `whb_stock_period_overrides.approved_by` is
  written from a parameter the *caller supplies*, so `FR-408`'s maker-checker is enforced only as
  "the id you passed is not the id you posted as". The recorder refuses self-approval and a missing
  approver, which is the whole of what it *can* check — an id asserted by the poster is not an
  approval, it is a claim. **Someone must own an approve surface** (a request/approve pair on
  `whb_stock_period_overrides`, the shape `P1-05`'s closure pre-check already uses) **or a payload
  proof** the recorder can verify without trusting the caller. Until then the override audit trail
  records who was *named*, not who *approved*, and `WS-046` should not be read as evidence of an
  approval having happened.
- **`WH-SC-021`'s `details.errors["effective_date"]` is unexpressible today.** `BusinessException`
  carries a message, a code and a status but **no field path**, and `ValidationException` — the one
  platform exception that does carry `details.errors` — pins the response to `400`. `WH-SC-021` wants
  a field-level error at `409`/`422`. This is a **platform-owned decision** (widen
  `BusinessException` with an optional field path, or let `ValidationException` carry a status), not
  a warehouse one, and no warehouse task should work around it by returning the wrong status.
- **The `MONTHLY`/`CATCH_UP` period-generation job does not exist.** `RE-001` puts it in **`P0-13`'s
  register** and `P0-13` has not landed, so today the ONLY thing that creates a period is `WS-045`'s
  *Generate periods*. That is sufficient for an install and insufficient for an unattended one: a
  period boundary that arrives while nobody runs the action stops receiving, exactly as `RE-001`
  warned. Acceptance box 12's third clause cannot be ticked from this task.
- **`FR-251` is half-built.** `WhbAccountingPeriodLockProvider` is declared as a seam and **no
  implementation exists in any module**, so `accountingLock(...)` answers `Optional.empty()` on
  every install — deliberately read as "not available", never as "open". The consequence: **the hard
  close never consults the accounting lock at all.** Only the *reopen* does, and only when a provider
  exists. Whoever builds the accounting side owns both the implementation and the hard-close consult.
- **`warehouseId` on *Generate periods* is unvalidated.** `V500019.warehouse_id` ships as a bare
  `UUID` with no FK (see the note added to `P1-05`), so a generate naming a warehouse that does not
  exist creates a period nobody can reach. `P1-05` closes this when it adds the constraint; until
  then the field is trusted.
- **Acceptance box 8's "field-level error on the second default company" is unreachable.** No path
  in the built code can attempt a second default: `WhbCompanyService` clears the incumbent inside the
  same transaction, so the partial unique index is never presented with two. **Ratify the stronger
  behaviour** — "setting a default moves it, and there is never a second to reject" — rather than
  adding a rejection path so the box can be ticked.
- **`WhbPeriodCloseChecker`'s `wh_`-prefixed probes are CORRECT and must not be "fixed" to `whb_`.**
  `wh_stock_adjustments`, `wh_counts` and `wh_blocked_movements` belong to the **`warehouse`** module
  (`P2-01`'s `V510030`/`V510034` and `P2-04`'s `V510033`, `DATA-MODEL.md` §2.2), whose prefix is
  `wh_`; only the handover and movement probes are this module's `whb_`. Both prefixes appear in the
  same list on purpose, and every module's migrations run into the **same database**, so
  `to_regclass('public.wh_counts')` starts answering the moment `P2-04` lands. Renaming them to
  `whb_` would probe tables that will never exist and freeze those three classes at *unmeasurable*
  forever.
