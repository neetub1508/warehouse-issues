## A refusal is only credible if it is written where the reader looks for the feature

`FR-268`: *"**Multi-level BOM with routings is not built.** It belongs to a manufacturing module; the
re-entry path is that a manufacturing system posts N issues and one receipt through the port and the
cost-layer table values them."*

`COMPETITOR-BENCHMARK.md` §7's standing instruction governs the deliverable: *"Each refusal must appear in
the product documentation **in the place a reader would look for the feature**, with its reason.
'Not built, because X' is a credible answer in a sales conversation; silence is not."*

## Scope

- **Write the refusal and its re-entry path** into the product documentation, at the point a reader looks
  for a bill of materials — which is the kitting and value-added-services documentation, not an appendix.
- **State the re-entry path precisely**, because it is what makes this a boundary rather than a gap:
  a manufacturing system posts **N issue movements and one receipt movement** through
  `POST /api/warehouse/movements`, in one transaction, and **`whb_cost_layers` values them**. Nothing in
  `warehouse-base` needs to change for that to work — which is the actual claim being made, and the thing
  worth verifying.
- **Name what *is* built, so the refusal is not read as "no assembly at all":** `P3-11`'s work order is
  **both the VAS record and the light-manufacturing record**; kit assembly and disassembly are **balanced
  ledger transactions** (`whb_transformations` / `_inputs` / `_outputs`, `V500035`, v1); and `P5-19`'s
  genealogy survives assembly in both directions. **Single-level kitting ships. Multi-level BOM with
  routings does not.**
- **Verify the re-entry path is real**, with a fixture: N issues plus one receipt, in one movement or one
  batch, balancing per `(owner, item, lot, serial, duty status)` and valued from the layers.
  A re-entry path nobody has executed is a claim, not a path.

## Traps

- **⚠ The pressure this refusal will come under is "just one more level".** A two-level BOM is a
  recursive structure with a routing, a work-in-progress location, an operation sequence and a labour
  absorption model. It is a **product**, and the moment `warehouse` acquires a component-of-a-component
  table, it has become a manufacturing system with none of a manufacturing system's other parts.
- **The re-entry path must not require a base change**, and that is the thing to actually test.
  R7 §6 item 12: batch posting with **per-movement** idempotency and per-movement results already exists,
  and `L-1` conservation is per `(owner, item, lot, serial, duty status)` — so *N issues and one receipt*
  is expressible today. **If the fixture needs a base column, the refusal is not clean and the finding
  goes back to `P0`.**
- **`whb_movement_types.balance_rule` matters here.** A production movement consuming N components and
  producing one output balances **per item against a virtual production location**, not in aggregate —
  `MUST_BALANCE_PER_OWNER_ITEM`, not `MUST_BALANCE_PER_MOVEMENT`. Getting this wrong lets a mis-specified
  production movement balance itself out and post silently.
- **Do not let the refusal drift into "no kitting".** `P3-11` and `P5-19` ship real assembly with real
  genealogy. The refusal is narrow, and a sales conversation that overstates it loses a deal we can win.
- **This is one of 23 refusals** (`COMPETITOR-BENCHMARK.md` §7, from 27 source rows). Check the others are
  documented in their reader-facing places too, and where an R2-sourced refusal's re-entry path is marked
  `(derived)`, it is *"a proposal for the product owner, not a finding of either audit"* — say so.
