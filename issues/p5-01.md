## This task is the module boundary, and the boundary is the product

`warehouse-3pl` is a **thin module standing on a wide base concession** (R4 §5.3, restated in
[`COMPETITOR-BENCHMARK.md`](../blob/main/docs/COMPETITOR-BENCHMARK.md) §6.2/§6.6). Every column it
stands on shipped in v1 — `owner_id NOT NULL` in the position key (`D-5`), `whb_lpns.received_at`,
billable-granularity outbox events, `cost_basis` including `ZERO_BAILMENT`, owner-scoped access.
**Nothing in this task adds a column to `warehouse-base` or `warehouse`, and the test that proves it
is written here, not later.**

R4 §5.2 counts the surface: **41 of 148** fulfilment capabilities are genuinely 3PL-only, **23** are
base or app and unaddable later, **69** are general WMS, **15** are adapter-shaped. A feature flag
would have saved none of the 23 — which is why this is a module.

## Scope

- **`V530000`** — bootstrap only: the `warehouse-3pl` Maven module, sibling package **`ai.warehouse3pl`**,
  `Wh3plModuleConfig`, `ArchitectureInvariantsTest`, and the 22 integration touchpoints of
  [`MODULE-INTEGRATION.md`](../blob/main/docs/MODULE-INTEGRATION.md) §2 that apply to a v2 frontend-bearing
  module. One `whb_source_systems` row (`WAREHOUSE_3PL`).
- **`V530010`** — `wh3_clients` (`W3-01`). Contract start and end, notice period, billing cycle and day,
  currency, payment terms, credit limit, the status ladder prospect → onboarding → live → suspended →
  terminating → offboarded, go-live date, minimum monthly charge, tax profile. **`uk(owner_id)` — the one
  structural edge into base, and it points down.**
- **`V530011`** — `wh3_client_onboarding_templates`, `_template_tasks`, `wh3_client_onboarding_tasks`
  (`W3-02`), plus the **per-client document number series** so `CL-ORION` sees its own order numbers.
- **`V531000`–`V531099`** — permissions + `permission_dependencies` + menus + grid configuration +
  `admin_settings` for the whole 3PL module. `DATA-MODEL.md` `W3-20` declares `V531000`–`V531199`;
  this task claims the **first hundred** and leaves `V531100`–`V531199` free (see *Traps*).
- **The coupling test.** `Wh3plCouplingTest` asserting, by static scan:
  1. no file under `warehouse-base/**` or `warehouse/**` contains `import ai.warehouse3pl`;
  2. no migration numbered below `V530000` contains the token `wh3_`;
  3. no `whb_`/`wh_` table has a `REFERENCES … wh3_` clause;
  4. `wh3_clients.owner_id → whb_owners(id)` is the **only** FK crossing the boundary, and it points down;
  5. the scanners self-test (copy `accounting-base/…/ArchitectureInvariantsTest.java:225-346`; the reason
     is stated at `:43-57` — *"a scan that finds nothing because there is nothing to find is
     indistinguishable from a scan that finds nothing because it is pointed at the wrong directory"*).
- **`FR-303` as a written confirmation, not code:** one database per customer stands. A 3PL's clients are
  an **owner dimension**, not tenants, and the two words are never used interchangeably in a document, a
  screen label or a sales conversation.

## Traps

- **The package must be `ai.warehouse3pl`, a sibling — never `ai.warehouse.threepl`.**
  `@ComponentScan("ai.warehouse")` matches by package **prefix**, so a sub-package loads in every install
  including ones that never enabled 3PL. This is the exact trap the accounting round-4 review found
  (`D-1`).
- **`V531000`–`V531099` is a sub-allocation of `W3-20`'s declared `V531000`–`V531199`.**
  `IMPLEMENTATION-PLAN.md` §2.9 enumerates every other sub-allocation and **not this one** — recorded in
  `DEFECTS-FOUND.md`. Do not let a later 3PL config task take `V531100`+ without adding the row.
- **`V530060` is `wh3_client_gst_registrations` and it is NOT yours.** It is `W3-13`, owned by **`P4-10`**
  — a P4 task in the 3PL band, because the band follows the table's prefix and the task follows the
  requirement's phase. `P4-10` therefore depends on this task; it is the only P4→P5 dependency in the plan.
- **Never name a permission `wms_*`.** `platform/…/V528:37,57,59` and `V663:17-19` still carry hardcoded
  `wms_*` / `scc_*` / `warehouse-*` permission exclusions from a deleted earlier module. Those migrations
  have already run so they grant a new module nothing — but a `wms_`-prefixed permission would inherit a
  decision nobody took (`D-3`, R6).
- **`permission_dependencies` is a platform table** (`platform/…/V248__Create_permission_dependencies_table.sql:17-30`).
  **`INSERT` only, never `CREATE TABLE`** — `dealer/…/V20501:10` is the vestigial second attempt that
  documents the mistake (R1 `C-017`). Columns are `permission_id` and **`dependent_permission_id`**.
- **The grid config table is `filter_definitions`**, created at `platform/…/V229__Add_filter_definitions_table.sql:8`.
  **`grid_filter_definitions` does not exist**; an unguarded insert into that name fails at Flyway and
  crash-loops the backend (R1 `CM-4`). And `grid_preferences` needs **both** `default_columns` and
  `default_filters` populated — a visible `filter_definitions` row alone does not build the strip.
- **Menu inserts are guarded by `WHERE NOT EXISTS`**, not `ON CONFLICT`: the menu table has no unique key
  on `(name, parent_id, menu_level)`, and `FlywayConfiguration.java:246-264` runs a blind `flyway.repair()`
  and one retry after any failure — so a partially-failed migration **re-runs**.
- **Every warehouse frontend filename must be globally unique.** `Dockerfile.frontend:80-177` merges every
  module's `src/` with `cp -r`, last write wins (R1 `C-012`). Prefix every 3PL component `Wh3pl`.
- **`ModuleImportSelector.java:52-55, :154-186` is the gate that fails silently** — the JAR is on the
  classpath and nothing loads. `platform/frontend/jest.config.js:54-61, :69-82` is the second silent gate:
  a module in neither list has its suites *written, committed and never run* (`MI-1`).
- **The ratchet is "zero commits to `warehouse-base`", never "zero commits to `platform`"** (`D-10`
  corollary, `G-047`). This module edits `filterUtils.ts` and `CacheConfiguration.java` for every grid it
  ships, and a contract claiming otherwise is false on day one.

## Blocked on
**`OD-3`** — one database per customer, or shared multi-tenancy. `IMPLEMENTATION-PLAN.md` §7 names
**this task** as the one it blocks, and the answer is *"keep one-DB-per-customer; do not re-litigate"*.
Two consequences that are easy to miss and belong in this task: the second customer is a **different
database**, so every mapping profile, rate card, charge-code catalogue and label template must be
exportable and importable; and `platform/…/db/client/` version numbers are deliberately reused across
clients, which is why `V910000+` was unusable and `D-2` moved the bands.
