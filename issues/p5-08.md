## A client seeing another client's stock is a contract breach, not a bug

`FR-300` says it and `WH-SC-140` walks it: *"a UI filter is not a guard — this codebase's own memory
records the identical class of problem for branch scope."* This task has **no migration** and is
nevertheless one of the two most consequential in P5.

## Scope

- **The portal is a permission surface over the existing screens**, not a second application with its own
  authentication. WS-172 has **no grid of its own**. Tabs: stock (WS-042 scoped) · inbound (WS-076) ·
  outbound (WS-099 / WS-105) · billing (WS-162) · disputes (WS-164, raise) · **performance**
  (WS-167 as trend plus current period with drill-through) · documents.
  v2 adds the document vault, dispute raising, scheduled reports, client API keys and per-client
  notification routing.
- **A `PORTAL` grant only** — the portal user is an ordinary platform user with an owner-bound grant
  (`whb_owner_grants`, `V500044`), resolved **server-side**.
- **Owner segregation enforced at the row level in the query layer, with a negative test per endpoint.**
  Every read endpoint — grids, exports, statistics maps, dropdowns, the availability API, the movement
  lineage query — is filtered by the **single server-side owner resolver**. A request naming another
  client is **`403`, never an empty result**.
- **A contract test fails the build if any repository method touching an owner-scoped table takes no
  owner-set parameter** (`WH-SC-140`).
- **WS-227 — Custody & Insured Value.** For `owner_type != OWN` the product reports a **custody liability
  and an insured value: a different number, on a different report, never mixed into the inventory asset**
  (`L-14`). The inventory valuation report **omits** non-own stock; the assertion is *the number is
  absent*, not *the number is zero*.
- **The B2B trade-customer persona is a separable increment of this task** (`RK-006`). It is a second
  persona on this same portal surface (`FR-284`), scoped by customer counterparty through the single
  resolver. Filed as `P5-25` in round 4 and folded back here on 2026-09-10 (below), it is still built as
  its own increment — so the 3PL portal ships alone and neither waits on the other (`RK-006`).

## Traps

- **⚠ Refusal §7 row 21 is the trap that costs the most.** *"The portal is a permission surface over the
  existing grids. Two mechanisms is how 40 grid identifiers become 80."* If a portal tab needs a
  different column set, it is a **grid preference on the same `grid_identifier`**, never a second
  identifier and never a parallel filter mechanism.
- **Four leak sites per grid, not one.** `WH-SC-242` names them: the grid, **the export**, **the
  statistics map** and the dropdown. Every one is checked explicitly, because each grid identifier has
  all four and *"every one of them is a leak site."* Add the availability API and the lineage query for
  the portal.
- **`403`, never an empty grid.** An empty grid is indistinguishable from *"no stock"* and gets read as a
  data problem rather than a permission boundary (`FR-114`, `WH-SC-140`).
- **The platform's role model is global** (`F-004`). Owner scope is **not** a role; it is a grant row
  resolved into a `WHERE` predicate. The repo's memory records the identical class of defect for branch
  scope — `reference_branch_scope_record_level_guard`.
- **Non-own stock is never valued** (`L-14`, `I-16`). Check the *valuation* report and the *stock-to-GL
  reconciliation* as well as the custody report: a 3PL posting its clients' stock to its own balance sheet
  is *"a catastrophe in both directions"*.
- **Permission gating on the frontend is `useMemo`-computed and status-gated on a menu-reachable page**
  (`WH-SC-241`). A portal tab reachable by URL but not by menu fails `WH-SC-248`'s seven layers.
- **Client API keys (v2) have no platform precedent.** There is no API-key table in platform (grep → 0);
  the only API-key path in the repo is per-handler inside the boom-barrier webhook. This is `OD-8`'s
  territory (`PP-2`, the platform service principal) — if `OD-8` is unanswered, ship the portal on
  ordinary user accounts and **declare client API keys out of this task** rather than inventing a second
  auth mechanism.

## Round-4 additions (folded from former P5-25, #158) — the trade-customer persona

**v2, in this task's own wave, and a separable increment.** Round 4 filed the trade-customer portal as
its own task, `P5-25` (`#158`), *"so the 3PL portal ships alone"*. On 2026-09-10 it was closed as a
duplicate and folded here: it is a second persona on this task's surface (`FR-284`) through this task's
resolver (`FR-406`), and its negative tests extend this task's. The 3PL portal still ships without it —
the persona is built as its own increment inside this task. Migrations **`V510221`**, **`V511209`** and
**`V511239`**, requirement **`FR-464`** and screen **`WS-240`** move here with it.

**Scope — a second persona on `FR-284`'s surface, not a second portal (`RK-006`).** A dealer's parts
counter is increasingly a wholesale business. Garages, fleet operators and sub-dealers buy from it by
phone and WhatsApp, and they want to see availability, place an order and download the challan (`RK-006`).

1. **`wh_trade_portal_users`** (`V510221`) — `user_id` (a platform user), `customer_counterparty_id`,
   `effective_from`, `effective_to`; one current row per `(user_id, customer_counterparty_id)` by
   `EXCLUDE` (`D-14`, R22 §1.3). A fleet manager may buy for two garages; each is a row. The counterparty
   must hold a current `CUSTOMER` role link (`P1-08`).
2. **The scope key is the customer counterparty**, resolved by the **single server-side resolver**
   (`FR-406`) that already resolves this task's owner scope. It is one resolver with a second persona,
   never a second resolver. Every read endpoint the persona reaches is filtered by it.
3. **`WS-240` Trade Portal** — tabs over existing screens, as `WS-172` is:
   - **availability** — per item, a **flag**: *in stock*, *on order* or *not stocked*, across the sites of
     the dealer's company. Never a quantity, and never a site breakdown;
   - **orders** — the customer's own demand orders (`WS-099` scoped), and a *New order* action that
     creates a `demand_type = SALES` order in **`DRAFT`** for the counter to confirm (`P2-08`);
   - **shipments** — status of the customer's own shipments (`WS-105` scoped);
   - **documents** — download of the challan and packing slip printed for the customer's shipments.
4. **Permissions** (`V511209`, `V511239`): the portal resource's `:view` and the order-draft verb, their
   dependency rows, and the menu row guarded `WHERE NOT EXISTS`. The persona gets **no** other warehouse
   permission. These two numbers are a `WH-206` pair in the `warehouse` band, which is why this task's
   header now names `warehouse` beside `warehouse-3pl`.

**Requirement** `FR-464` — owned here now. **Scenario** `WH-SC-321` — a trade customer logs in, sees
in-stock and on-order flags for its own lines only, creates a `DRAFT` order and downloads its challan.
**Closes** `RK-006`. **Depends on** `P2-08` (the demand model) and `P1-08` (the `CUSTOMER` role).

**Traps (trade persona)**

- **A flag, never a number** (`RK-006`). A quantity tells a buyer, who may also buy from the next dealer,
  the dealer's whole stock position. The availability endpoint returns an enum; a test asserts the
  response carries no numeric stock field.
- **`DRAFT` reserves nothing.** A portal order enters the one demand model (`P2-08`) and waits for the
  counter. Allocation happens at the counter's confirm, under the counter user's permissions and the
  `FR-461` serving-branch rule. A portal draft that reserved stock would let an outside buyer hold the
  dealer's stock.
- **`403`, never an empty result**, on a request naming another customer (`FR-300`, `WH-SC-140`). The
  negative test per endpoint this task writes for owners is extended to this persona. It is not a
  separate test suite that can be skipped.
- **No pricing engine, no payment.** Prices come from the price-level home that `RA-002` resolves, and
  refusal #18 stands. The portal shows the price the counter will charge, or none.
- **One `grid_identifier` per grid, still** (refusal §7 row 21). A portal tab that needs different columns
  gets a grid preference on the existing identifier, exactly as for the client persona.
- **The persona is not a 3PL client.** A trade customer owns no stock in the warehouse. Its scope is the
  documents it is party to, not an owner. Reusing `whb_owner_grants` for it would make the garage an
  owner of goods it has not bought.

**Acceptance (trade persona)**
- [ ] `wh_trade_portal_users` exists at `V510221` with the R22 §1.3 columns and an `EXCLUDE` on `(user_id, customer_counterparty_id, range)`; a counterparty without a current `CUSTOMER` role is refused
- [ ] The availability endpoint returns only `IN_STOCK` / `ON_ORDER` / `NOT_STOCKED` per item; no quantity field exists in its response, asserted by a contract test
- [ ] A portal order is created as `demand_type = SALES` in `DRAFT`, creates no `whb_reservations` row, and appears on `WS-099` for the counter
- [ ] A negative test per read endpoint asserts `403` on another customer's order, shipment or document
- [ ] The resolver is the one `FR-406` resolver; a grep finds no second scope resolver in the diff
- [ ] `V511209`/`V511239` seed the resource, its dependencies and the menu, with `WHERE NOT EXISTS`; the persona sees no admin menu and gets `403` on a direct URL
- [ ] **Mobile:** `none`, with the reason stated. The portal is a browser product for an outside buyer, as the client portal is; the counter confirms drafts on `WS-099`, which already carries its mobile verdict (`D-13`)
- [ ] **Scenarios** `WH-SC-321`
