## Four answers, four single queries — and only because lot landed on the ledger line in v1

`FR-280`: *"All four are single queries if and only if lot and serial land on the ledger line in v1."*
They did (`L-5`, `V500030`). This task spends that concession.

## Scope

- **`V510211` — `wh_recalls` + `wh_recall_lines`** (`WH-111`): recall number, item, lot, recall class,
  initiated at / by, regulator reference, status, affected shipment count, notified count.
- **Quarantine all matching on-hand stock *in place*** with a **status-change movement** — no physical
  move, no re-warehousing. The stock does not travel; its `stock_status_code` changes and the ledger
  records why.
- **List every shipment that carried the lot**, with its consignee and tracking.
- **Release every reservation allocated to it** — answerable because `whb_reservations` carries the holder
  quad `(holder_system, holder_document_type, holder_document_id, holder_line_no)` (`L-10`).
- **Export the affected-customer list**, and drive the notification through the platform's existing
  providers.
- **A recalled unit is never restocked.** `return_type = RECALL` blocks it: `RESTOCK` is **not offered at
  all**, rather than offered and rejected (`WH-SC-200`).

## Traps

- **`WH-SC-200`'s third return — the recalled unit — has no data behind it until this task lands.**
  The scenario's rule is *"the recalled unit **cannot be restocked under any disposition**"*, and
  nothing in `warehouse-base` or in `P2-12` can evaluate it: there is no recall register, no
  lot-level recall flag and no disposition guard that consults one. `P0-05` closed `WH-SC-200` on the
  strength of seeding the `RETURN_TYPE` code list, which is the first third of the scenario and not
  this one; it has been withdrawn from that task's *Scenarios closed*. **`wh_recalls` /
  `wh_recall_lines` (`V510211`) are where the rule becomes evaluable**, so the disposition refusal is
  this task's to enforce: a unit whose lot is on an open recall is refused every restocking
  disposition, with a stable code, and the refusal names the recall.
- **Quarantine is a movement, not an `UPDATE`.** The position is a **cache** (`L-4`); changing a status by
  updating `whb_stock_positions` breaks the rebuild and is refused by the writer service, which has no
  update method (`P0-03`). The status change is a two-line movement from `AVAILABLE` to `QUARANTINE` at
  the same location, with a reason code from the catalogue.
- **`whb_stock_statuses` carries `requires_reason_to_enter` and `requires_reason_to_leave`.** Set them on
  the quarantine status, and the recall's reason code is what satisfies them — not a free-text note.
  Free text in v1 is a dimension that can never be aggregated for the past (R7 §6 item 10).
- **Releasing reservations must not release someone else's.** The holder quad is the whole point: release
  by `(item, lot)` **intersected with** the recall's scope, and record each release with the recall as its
  reason so an orphaned reservation is never left silently reducing availability forever (`G-`/R7 §6
  item 16).
- **A recall crosses the kit boundary.** `P5-19`/`FR-266` records which input lots went into which output
  unit; a recall on a component lot must reach the kits built from it. If `P3-11`'s transformation
  genealogy is not yet populated for the period, **say so on the screen** rather than reporting a clean
  list — an incomplete recall list presented as complete is the worst possible output of this feature.
- **The affected-customer export is likely to exceed 10,000 rows.**
  `BaseExportService.DEFAULT_MAX_EXPORT_ROWS = 10_000` (`PP-6`); use `warehouse-base`'s streaming export
  path. A truncated recall list is a regulatory problem, not a UX one.
- **Notification uses the platform's existing providers.** Do not add a second notification stack; the
  repo already carries the email-template registry and the AiSensy WhatsApp provider.
- **Period lock applies.** A quarantine movement into a locked period is refused, including a reversal
  (`L-8`). A recall spanning a closed period needs the soft-close override path, and that is a
  permissioned, audited act.
- `itemId` → `lotId` is a **cascading** typeahead pair (the Service Vehicle filter is the canonical
  reference); `initiatedFrom`/`To` is a `date` pair. Register the scope in `COMMON_FILTER_CONFIGS`.

## Acceptance
- [ ] Quarantine posts a **status-change movement** per position; `whb_stock_positions` is never updated directly, and a full ledger rebuild reproduces the post-recall positions exactly (`L-4`)
- [ ] Every shipment that carried the lot is listed with consignee and tracking, in **one** query
- [ ] Every reservation on the recalled lot is released, each with the recall as its reason; no reservation outside the recall's scope is touched
- [ ] The affected-customer list exports in full — not truncated at 10,000 rows
- [ ] A recalled unit returned cannot be restocked by any disposition, and `RESTOCK` is not rendered
- [ ] Where transformation genealogy is incomplete for the period, the screen **says so**; it never presents a partial list as complete
- [ ] A recall touching a locked period is refused unless an approved soft-close override is present, and the override is audited
- [ ] **Mobile:** the quarantine confirmation is available on the RF Move / Stock Enquiry screens so a floor operator can see a bin is recalled; the recall object itself is a desk screen — state it (`D-13`)
- [ ] A unit whose lot is on an open recall is refused every restocking disposition, the refusal
      names the recall, and the rule is evaluated from `wh_recalls` and not from a flag a person

## Decisions recorded at build
R2 fix round (2026-09-26; gate reports `p514-rev.md`, `p514-func.md`; driver decisions `R2-DECISIONS.md` §P5-14).

- **No period-override lane — withdrawn (R2 F1).** A quarantine posted under a SOFT_CLOSED override goes PENDING,
  while the planner's reservation releases run at request: the lot would be *more* sellable than before. Initiate now
  refuses any PENDING quarantine post (`RECALL_PERIOD_OVERRIDE_PENDING`, whole transaction rolls back), and the
  justification field is gone from the request and the modal. Deviation from acceptance "refused unless an approved
  soft-close override is present": a recall in a soft-closed period is refused until the period is reopened.
  (`WhbStockLedgerWriter.changeStatus(request, periodOverride)` in warehouse-base is now unused.)
- **Recalled lot never lands in an allocatable status, on any path (R2 F2).** `WhRecallPostGuard` is a
  `WhbMovementPostGuard`: any line INBOUND to a real location, in an ALLOCATABLE status, for a lot under ANY recall is
  refused `409 RECALLED_LOT_NOT_ALLOCATABLE`, naming the recall — QC release, hold release, counts, receipts,
  reversals included. `WhbMovementPostGuard.Post` gained the writer's resolved lines (6-arg constructor kept). QC_HOLD /
  PENDING_RESOLUTION / DAMAGED stock is NOT quarantined at Initiate (driver decision); the guard protects it.
  Known limit: a movement already PENDING before the recall is applied at approval without passing the guard.
- **Staged picks (R2 F3) — deviation from "release every reservation".** A hold staged by a pick may not be released
  by a status change (FR-449). Initiate refuses `RECALL_STAGED_ORDERS`, naming the staged demand orders and advising
  "cancel or de-stage these orders" — never despatch. No auto de-stage.
- **Consignee notification through the platform provider (R2 F4).** Notify sends each line through
  `WhatsAppService` (the configured AiSensy / Twilio / Pinbot provider; `LdMessageDeliveryService` precedent) to
  `COALESCE(wh_demand_orders.ship_to_phone, wh_shipments.ship_to_phone)`, and stamps `notification_channel`
  (`WHATSAPP` | `MANUAL`) and `notification_outcome` (`ACCEPTED` | `FAILED` | `NO_PHONE` | `CHANNEL_NOT_CONFIGURED`) on
  the line. No phone, or WhatsApp off → recorded MANUAL as before. A FAILED send still marks the line NOTIFIED (Notify
  is the person's record) and the Delivery column shows who must be phoned. OPEN INTERFACE: no approved recall
  template exists — the body is free text; AiSensy sends it as the single variable of its configured default campaign
  (`whatsapp_aisensy_campaign_name`), so that campaign must be a one-variable template. Email is not sent: no
  consignee email is held. Sends run synchronously inside Notify's transaction. `consigneePhone`,
  `notificationChannel`, `notificationOutcome` are in the `wh_recall_lines` grid defs, the line SELECT and the export.
- **Genealogy disclaimer in the file (R2 F5).** When `genealogy_complete = false` the affected-customer CSV opens with
  a warning row (in `lineNo`, the grid's required column).
- **The restock refusal outlives the recall (R2 F6).** Evaluated against ANY recall, OPEN or CLOSED — "a recalled
  unit is never restocked" wins over acceptance #9's "open". Applies to the return receipt, P5-13's grading (through
  `WhRecallQueryService.openRecallNumbersByLot`, kept as an alias of `recallNumbersByLot`) and the post guard.
- **Line export is CSV only (R2 F7).** Any other format on `/{id}/lines/export` is `422 LINE_EXPORT_FORMAT_NOT_SUPPORTED`.
- **Split lots are recalled (R2 F8).** Recursive `whb_lots.parent_lot_id` descendants join the lot set, walked to a
  fixed point with the transformation genealogy.
- **Close gated on the grid (R2 F9).** Grid rows carry `pendingNotificationCount` (one batched sub-select per page);
  Close is offered only at 0, Notify only above 0.
- **Initiate needs every site (R2 F10).** Refused `403 RECALL_WAREHOUSE_SCOPE_REQUIRED` unless
  `allowedWarehouses("whb_stock_positions")` is unscoped. The seeded QA / Manager bundles are branch-tier, so in
  practice ADMIN or a user granted `whb_stock_positions:view:all` with no warehouse grant can initiate.
- **Withdrawn:** the recorded gap "a shipment stores only its last order" — the functional gate proved it false
  (`wh_shipment_orders` carries every order).
- **Recorded, no change:** the genealogy AlertBox sits inside the Recall and Affected Customers tabs because
  `ViewModalBase` has no above-tab-strip slot (house pattern).
- **Mobile:** out of scope (NO MOBILE for this round); the RF quarantine-confirmation acceptance line stays open.
