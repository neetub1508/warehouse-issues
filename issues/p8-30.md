## Scope

R32 (PRD 2026-10-24 §3, §4 "Approval matrix", §13.2 `approvals (append-only)`, §13.3 "approvals append-only at DB level"; `D-20` items 2-13b, 2-18, 2-19). The design set had **two** approval shapes: the trade matrix (`P9-03`, `wht_approval_*`, trade documents only) and a per-document approve verb with `WhbMakerChecker` in core. `FR-466`'s core value-banded levels were never built (#160 closed DUPLICATE). `D-20` item 18 supersedes that closure: **one engine for every document type**. Core cannot depend on `warehouse-trade` (FKs point down only, `D-16`), so the engine is **core's**: this task takes `P9-03`'s engine design — tables, service, WS-284 / WS-285, the alert job and the notification category — into `warehouse` as `wh_approval_*`, and `P9-03` becomes the trade consumer (its R32 section). No second engine, no workflow DSL (repository rule): rules are typed rows, levels are typed rows, conditions are codes contributed by beans.

### Data model — `V511600`
- **`wh_approval_rules`**: `company_id NOT NULL → whb_companies`, `document_type_code VARCHAR(60) NOT NULL` (validated against the registered `WhApprovable` beans, `422 APPROVAL_DOCUMENT_TYPE_UNKNOWN`; no CHECK), `warehouse_id` (nullable = any site), `department_id → departments` (nullable), `item_category_id → whb_item_categories` (nullable), `currency_code VARCHAR(3) NOT NULL`, `value_from` / `value_to` `DECIMAL(19,4)` (nullable = open; CHECK from ≤ to), `qty_from` / `qty_to` `DECIMAL(18,4)`, `condition_match_mode VARCHAR(10) NOT NULL DEFAULT 'EXACT'` (`EXACT` / `INCLUDES`), `specificity SMALLINT` (computed on save: one point per non-null scope dimension), `escalation_hours INT` (nullable = the setting; `0` = never), `final_escalation_role_id → roles` (nullable), `is_active`, `status`, `version`, audit quartet. A rule that has been matched by a request is **copy-on-write** (`supersedes_id → self`, `version_no`), so a request always names the exact rule version it ran (`I-24` pattern).
- **`wh_approval_rule_conditions`**: `rule_id ON DELETE CASCADE`, `condition_code VARCHAR(60)` — codes come from `WhApprovalConditionProvider` beans (trade: `first_time_supplier`, `supplier_return_replacement`, …); uk(`rule_id`,`condition_code`).
- **`wh_approval_rule_levels`**: `rule_id`, `level_no SMALLINT` (1…n, contiguous), `mode` (`ANY_ONE` / `ALL`), `resolver_type VARCHAR(30) NOT NULL` — `ROLE` (members of `role_id`), `USERS` (the child rows), `DEPARTMENT_HEAD` (the head of the document's `department_id`, platform `departments.department_head_id`, or its `deputy_head_id` when the head is the maker; the PRD's "HOD" level, 3-29), `PERMISSION_HOLDER` (anyone holding the document type's approve verb in the document's scope) — `role_id → roles` (nullable), `approver_limit DECIMAL(19,4)` (nullable — the most this level may approve in the rule's currency; informative, frozen onto the step and the action, PRD 3-04 "value limit per approver"), uk(`rule_id`,`level_no`).
- **`wh_approval_rule_level_users`**: `level_id`, `user_id → users`; uk.
- **`wh_approval_requests`**: `company_id`, `warehouse_id`, `document_type_code`, `document_id UUID NOT NULL`, `document_ref VARCHAR(60)` (frozen number or draft ref), `document_revision INT NOT NULL DEFAULT 0` (the amendment revision, FR-728), `maker_id → users`, `submitted_at`, `department_id`, `value DECIMAL(19,4)`, `qty DECIMAL(18,4)`, `currency_code`, `condition_set VARCHAR(500)` (frozen, sorted, comma-joined), `rule_id` + `rule_version_no` (nullable when `rule_source = DEFAULT_POLICY`), `rule_source` (`RULE` / `DEFAULT_POLICY` / `ZERO_LEVEL`), `status` (`PENDING` / `APPROVED` / `REJECTED` / `RETURNED` / `WITHDRAWN` — **a projection** of the action rows, no CHECK, `D-10`), `decided_at`; partial uk(`document_type_code`,`document_id`) WHERE `status = 'PENDING'`.
- **`wh_approval_steps`**: `request_id`, `level_no`, `mode`, `resolver_type`, `role_id`, `band_from` / `band_to` (the rule's value band, frozen), `approver_limit` (frozen from the level), `currency_code`, `status` (`WAITING` / `PENDING` / `APPROVED` / `REJECTED` / `RETURNED` / `SKIPPED` — projection), `escalation_level SMALLINT NOT NULL DEFAULT 0`, `escalated_at`, `alert_episode_started_at`; uk(`request_id`,`level_no`). The level's **member list resolves at action time** (`TAM-OPEN-01` settled), so a joiner can act; the rule, levels, bands and maker are frozen.
- **`wh_approval_actions`** — **the append-only decision record** (PRD §13.2 `approvals`, `D-20` item 2-13b): `request_id`, `step_id` (nullable for request-level actions), `sequence_no BIGINT` (per request, gapless), `action` (`OPENED` / `APPROVED` / `REJECTED` / `RETURNED` / `WITHDRAWN` / `SYSTEM_APPROVED` (zero-level) / `SYSTEM_RETURNED` (input changed) / `ALERTED` / `ESCALATED`), `actor_user_id` (NULL only for `SYSTEM_*`, `ALERTED`, `ESCALATED`), `on_behalf_of_user_id` (delegation), `via_escalation BOOLEAN NOT NULL DEFAULT false`, `reason_code_id → whb_reason_codes` (NOT NULL for `REJECTED` / `RETURNED` — CHECK), `comment VARCHAR(1000)`, `rule_id`, `rule_version_no`, `level_no`, `band_from`, `band_to`, `approver_limit`, `document_value`, `currency_code`, `document_revision`, `acted_at TIMESTAMPTZ NOT NULL`. **No `updated_at` / `updated_by`.** Three layers as `L-2`: the service has no update path; `trg_wh_approval_actions_append_only` raises `APPROVAL_ACTION_IMMUTABLE` on `UPDATE` / `DELETE`; `TRUNCATE` is revoked from the application role. The `status` columns of requests and steps are **projections** written only by `WhApprovalService` in the acting transaction and rebuildable from the actions (`WhApprovalProjectionVerifier`, run by the nightly integrity job; a mismatch is an `ERROR` job run, never a silent fix).
- **`wh_approval_delegations`**: approver, delegate, `valid_from`, `valid_to`, `recorded_by`, `status` (`ACTIVE` / `PENDING_CONFIRMATION`), `confirmed_by`, `document_type_code` (nullable = all types) — a delegation recorded for another approver waits for a second administrator's confirmation (`TAM-T1-10`, `-11`). Out-of-office for **core** documents comes with it (R32 beyond-PRD item).
- **`wh_approval_notifications`** — delivery log, insert-only: `action_id`, `recipient_user_id`, `channel` (`IN_APP` / `EMAIL` / `WHATSAPP`), `outcome` (`SENT` / `FAILED` / `SKIPPED_NO_ADDRESS` / `SKIPPED_OPTED_OUT`), `attempted_at`, `error_text VARCHAR(500)`.

### Service contract (every approving task uses it unchanged)
- `WhApprovable` bean per document type (`ai.warehouse.port.approval`, FRD-STORES registry R.3): `documentType()`, `approveVerb()` (the `resource:approve` that may act — `TAM` §0.1 for trade, contract §0.1 for core), `snapshot(documentId)` → value, qty, currency, site, department, line item categories, conditions, revision, maker; `defaultPolicy()` — `REFUSE` (no rule ⇒ `422 APPROVAL_NO_RULE`; every trade type, FR-550) or `SINGLE_LEVEL` (no rule ⇒ one `PERMISSION_HOLDER` level, `rule_source = DEFAULT_POLICY`; PRD §3 "default single level") or `DOCUMENT_DEFINED` (the bean returns the implicit level list — the material requisition's value threshold, below); `requiresDocumentScreen()` (true when the approve act needs document inputs, e.g. per-line approved quantities — My Approvals then opens the document instead of approving inline); callbacks `onApproved` / `onRejected` / `onReturned` / `onWithdrawn` **in the acting transaction**.
- `WhApprovalService.open(type, id)`, `act(stepId, decision, reasonCodeId, comment)`, `withdraw(requestId)`, `history(type, id)`, `currentState(type, id)`; `WhApprovalPort` (`ai.warehouse.port.approval`) exposes the same to sibling modules.
- **Rule match** (FR-721): document type, company, currency, then the most specific active rule whose site / department / item category / value band / qty band / condition set match. **Item category** matches when every line's category is in the rule category's subtree; a mixed-category document falls back to the category-less rules. Saving a rule that could tie with another on any document is refused `409 APPROVAL_RULE_AMBIGUOUS` naming the other rule (`TAM-GRD-05`); a tie at open is refused `409 APPROVAL_RULE_TIE`.
- **Adoption of the built single-step approvals** (no behaviour change on upgrade): the approve services of the material requisition (`MRQ-T1-03`, `-06` — `defaultPolicy = DOCUMENT_DEFINED`: one level at or below `warehouse.stores.requisition_second_approval_threshold`, two above, the first `DEPARTMENT_HEAD` when the policy says so, exactly `MRQ-GRD-05`/`-11`), the gate pass (`GTE-T1-11`), the stock adjustment and the count-variance adjustment (`CCT-GRD-03`, `-07`), the revaluation and the NRV assessment (`CVL-T1-06`, `-10`), the site-branch transfer (`FBL-GRD-12`) and the GRN excess decision (`GBM-T1-05`) open an engine request and act its step inside their existing Approve endpoint; all are `SINGLE_LEVEL` except the requisition. Their existing self-approval codes (`REQUISITION_SELF_APPROVAL`, `GATE_PASS_SELF_APPROVAL`, …) are kept as the refusal code of `DAP-GRD-03` for that type, so no client breaks. An install may then add bands and levels to any of them on WS-284.
- **Open documents** wire their own type when they are built: `P8-08` MRN (`MATERIAL_RECEIPT_NOTE`, `SINGLE_LEVEL`, verb `wh_material_receipt_notes:authorise`), `P8-11` store return (the configurable approval steps of `D-20` item 2-15), `P9-*` through `P9-03`, `P10-*` (BOM / routing release with the PRD default *Design Head + Plant Head* expressible as two levels, production order release, PDI clearance, drawing release, sample dispatch, deviation). A type registered without a matching approve verb fails start-up (`ApprovalRegistryVerifier`).

### Maker ≠ checker, reasons, lock and amendment
- `DAP-GRD-03`: the acting user ≠ the request's maker, ≠ the submitter, and has not acted on another level of the same request — evaluated in the service, never in the UI, **and `ADMIN` is refused too** (`TAM-UNR-04`, PRD §3 "Maker ≠ checker, enforced in the service"); a delegate cannot act for the maker or for a principal on a level they already acted on.
- Reject and return need a reason code from `APPROVAL_REJECT` / `APPROVAL_RETURN` (`422 APPROVAL_REASON_REQUIRED`), plus a note when the code requires one.
- While a request is `PENDING`, the document refuses edits (`409 APPROVAL_PENDING`); once `APPROVED`, it refuses edits in place (`409 DOCUMENT_APPROVED_LOCKED`). **A change after approval is an amendment**: the document's own amendment action (owned by its task — `P9-11` for PO / SO / rate contracts, a new BOM / routing version in `P10-03`) writes revision n+1 with a reason from `DOCUMENT_AMENDMENT` and calls `open(type, id)` again with the new `document_revision`; the earlier revision's approval stays in the history, and the revision is approved by the rule that matches **its** value (an amendment that crosses a band upward needs the higher levels). Core internal documents (requisition, MRN, store issue / return, gate pass) are **not amendable** — they are cancelled with a reason and re-raised, which is SAP's behaviour for reservations and goods movements (R32 3-08).
- Rejected: the document goes to `REJECTED` (editable, resubmittable as a new request) — or, when `warehouse.approval.reject_returns_to_draft = true`, straight to `DRAFT` (PRD 3-27; default `false`, the design's ladder — `D-20` item 1, both legitimate).

### Time, escalation and channels
- `WhApprovalAlertJob` (hourly, `whb_job_runs`; re-homed `TradeApprovalAlertJob`): a step `PENDING` longer than `warehouse.approval.pending_alert_hours` (default 24) alerts the level's members and active delegates once per episode (`ALERTED` action).
- **Upward escalation** (`D-20` item 2-19, PRD 3-25): a step still `PENDING` after the rule's `escalation_hours`, else `warehouse.approval.escalation_hours` (default **48**, `0` = never; *default — client Q-A2*), escalates **once per level**: the members of the **next** level of the same rule become eligible to act on this step as well (`ESCALATED` action, `escalation_level + 1`, `via_escalation = true` on the act); on the last level the rule's `final_escalation_role_id`, else `warehouse.approval.final_escalation_role` (default blank = none — the step only re-alerts). The original members can still act. **Nothing is ever approved by time** (`DAP-UNR-01`). An escalated approver is still subject to `DAP-GRD-03`.
- **Channels** (`D-20` item 2-19, PRD 3-24, supersedes FRD-TRADE §12b "v1 sends in-app only"): in-app always (platform `NotificationService`, category **`NotificationCategory.WAREHOUSE_APPROVAL`** + its `NotificationCategoryMenuMapping` row to WS-285 — the two platform commits, owned here; trade's `WAREHOUSE_TRADE` category stays for trade's other kinds); e-mail through `EmailNotificationService` with the registered templates `warehouse-approval-pending`, `-escalated`, `-decided` (`EmailTemplateDefaults`, en / fr / hi); WhatsApp through `WhatsAppService` with the approved template names in `warehouse.approval.whatsapp_template_*`. `warehouse.approval.channels` (default `IN_APP`; allowed any set containing `IN_APP` of `IN_APP`, `EMAIL`, `WHATSAPP`; *default — client Q-A2*). Delivery runs **after commit** (a rolled-back approval notifies nobody); each attempt writes one `wh_approval_notifications` row; a failure is recorded `FAILED` and never rolls back or latches the episode as delivered (the `#620` defect is not repeated here: the alert episode is stamped from the in-app outcome only). A recipient without a verified e-mail / WhatsApp number is `SKIPPED_NO_ADDRESS`. Links in e-mail / WhatsApp open the document in the web app after login — **no approval by e-mail link** (signed-token approval stays out of scope, contract §6).

## Traps
- **Maker ≠ checker is not a permission**; `ADMIN` is refused too. The check runs in `WhApprovalService`, and every adopted document's Approve endpoint goes through it — a document that keeps its own `WhbMakerChecker` call **beside** the engine is a second engine.
- The action rows are the record; the `status` columns are projections. Never `UPDATE` an action, never "fix" a projection by hand — rebuild it.
- The approval and the document transition commit together; a callback exception rolls back the step. Notifications go **after** commit.
- Rule match is on the **document currency**; never convert (`OD-34`).
- Escalation widens who may act; it never approves, skips a level or relaxes `DAP-GRD-03`.
- Do not use direct `queryClient.invalidateQueries` — `useQueryInvalidation` invalidates the inbox and every document list; permissions in `useMemo`; modals via `lazyModal()` + `Suspense`; users through the platform user-display helper.
- Mobile: none (`D-20` item 5) — WS-285 is web; the e-mail / WhatsApp link opens the web page.
