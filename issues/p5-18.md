## Scope

- **The run proposes a sister-branch transfer before a purchase** where another branch holds stock
  **above its own minimum**. *For a multi-branch dealership that is where the money is: the part is
  already in the group* (`E-041`).
  The suggestion carries `suggested_source = SISTER_BRANCH_TRANSFER`, the `source_warehouse_id` and a
  `basis_note` naming the surplus it drew on — so *"why did we transfer that"* is answerable months later.
  **A sister is a site with a different `REGISTERED` branch**, so a site is never its own sister, and a
  site shared by several branches is one source, not one per branch (`RG-001` row 12).
  **Accepting a sister suggestion creates a transfer in `REQUESTED`** — `FR-462`'s request object — which
  a holder of `wh_transfer_orders:approve` scoped to the source approves, part-approves or rejects; the
  run never pushes stock out of another branch's site on its own authority (`RK-001`).
- **Emergency replenishment triggered by a short pick** — the shortage raises a replenishment task at
  pick priority, ahead of the queue, against the pick face that failed.
- **Opportunistic top-off during idle time** — a low-priority task the assignment engine (`P3-02`) hands
  out when nothing urgent is claimable, in an aisle the operator is already in.
- **Break-case replenishment from case reserve to an each pick face** — a UoM-converting internal move
  where the source and destination packaging levels differ.

## Traps

- **"Above its own minimum" is the whole rule.** A design that proposes a transfer from any branch with
  stock strips a branch that needs it, and the customer stops trusting the run after the first occurrence.
  The surplus must be computed against **that** branch's own reorder point / safety stock at item × site
  (`P1-03`'s v1 columns).
- **A sister-branch transfer is a two-movement transfer through an `IN_TRANSIT` location**, not a
  one-movement move — that is the whole reason `IN_TRANSIT` and `is_physical = false` are v1
  (R7 §6 item 2, `PORT-AND-ADAPTER-CONTRACT.md` §9.7). A suggestion that resolves into a single movement
  loses the stock between despatch and arrival.
- **Break-case replenishment must freeze the conversion factor on the line** (`L-7`,
  `conversion_factor_used`). A ledger that re-derives from today's factor silently restates last year, and
  a pack ratio that changes when a supplier changes case size is exactly how it happens. The factor is
  `DECIMAL(18,8)` — **not** `DECIMAL(19,8)`, which is the currency-conversion type and nothing else, and
  **not** `DECIMAL(18,4)`, at which a 0.000045 kg factor rounds to `0.0000` and the conversion is
  undefined before any quantity is multiplied (`DATA-MODEL.md` §5).
- **Emergency replenishment is a task priority, not a new task type.** `P3-02`'s pull-and-push assignment
  works from **one table**; a second queue for emergencies re-creates the two-mode problem `WH-SC-230`
  exists to prevent.
- **Opportunistic top-off must never starve real work.** It is claimable only when nothing at or above a
  threshold priority is claimable for that operator's zone and equipment capability.
- **Availability is computed, never stored** (`L-6`, `C-022`). A replenishment run that reads a stored
  reserved counter reproduces the accessories defect where `quantity_reserved` is read in 7 places and
  written in 0.
- **No new filter scope means no new `filterUtils.ts` edit** — but confirm, because a new suggestion-source
  filter on WS-140 **is** a new field in an existing scope, and a field absent from the scope is silently
  dropped (`filterUtils.ts:346`, CLAUDE.md CRITICAL #17).

## Acceptance
- [ ] A shortage where a sister branch holds surplus **above its own minimum** produces a `SISTER_BRANCH_TRANSFER` suggestion ranked ahead of the purchase suggestion, with `source_warehouse_id` and a `basis_note`
- [ ] A sister branch **at or below** its own minimum is never proposed as a source
- [ ] A site whose `REGISTERED` branch is the short site's own is never proposed as a sister source (`RG-001` row 12)
- [ ] Accepting the suggestion creates a transfer in `REQUESTED`, not a pushed transfer; once the source approves it, it posts **two** movements through an `IN_TRANSIT` location (`RK-001`)
- [ ] A short pick raises an emergency replenishment task that the assignment engine hands out ahead of the queue, from the same task table
- [ ] Opportunistic top-off is offered only when no higher-priority task is claimable for that operator's zone and equipment
- [ ] A break-case move converts case → each with `conversion_factor_used` frozen on the line, and a later change to the pack ratio does not restate the movement
- [ ] `wh_replenishment_suggestions.suggested_source` and `source_warehouse_id` are confirmed present from v1; **if they are not, this task stops and the defect is filed against `P2-15`**

## Decisions recorded at build
Gate round R3 (reviewer + functional-reviewer), ratified by the driver:
- **`TRANSFER` is the spelling**, not `SISTER_BRANCH_TRANSFER`. The v1 `CHECK` (`V510070:223`, RJ-014) and WH-SC-353 say `TRANSFER`; the code follows the DB. Read `SISTER_BRANCH_TRANSFER` in the Scope and Acceptance above as `TRANSFER`.
- **A sister surplus that covers only part of the need** proposes the transfer alone; the balance is left to a later run, and only if the position is still at or below the reorder point (`WhReplenishmentEngine.preferSister`).
- **Every open inbound transfer counts as on order** (F3). The run's on-order figure counts every non-terminal, not-`RECEIVED` transfer line INTO the site — suggestion-raised, requested by hand (WS-090) or pushed alike — as approved (else requested) − received − variance (`WhReplenishmentRunRepositoryCustomImpl.findOpenInboundTransferLines`). The purchase-order on-order port counts no transfer, so nothing is counted twice.
- **Opportunistic top-off respects the operator's qualification** (F1, FR-215). Nothing is raised for an operator without a `user_skills` row matching the `REPLEN` type's `required_resource_type` — the claim query's own predicate (`WhReplenishmentTaskRepositoryCustomImpl.isQualifiedForReplenishment`).
- **Opportunistic top-off matches the pulled zone the way the claim query does** (F2, P3-06 / RG-015): the face's storage zone, or a current `whb_location_zone_memberships` row of the pulled functional zone, by path.
- **The operator's aisle OVERRIDES the zone** (R3 parity): the aisle of their last completed task is searched alone first; the pulled zone is the fallback when that aisle has no candidate (or none is known). The aisle has **no age limit** — the last completed task at the site is where they stand, however long ago.
- **Behaviour tests** — WH-SC-354: `WhReplenishmentEmergencyEscalationTest`, `WhbTaskEscalatePriorityTest`; WH-SC-355: `WhReplenishmentOpportunisticTopOffTest`, `WhbTaskClaimIdleWorkTest`. The emergency value max(queued `CREATED` at the site, the failed pick) + 1 is computed in the candidate SQL (`EMERGENCY_PRIORITY`); the unit tests prove it is carried and that a queued task is escalated, never twinned.
