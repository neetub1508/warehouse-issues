## Why a table for a feature that has no RF gun yet

Every tier-1 WMS separates the **business document** from the **execution instruction**
(`FR-212`). v1 has no handheld — `P3` builds that — but the columns must exist now, because
**`assigned_at`, `started_at`, `completed_at`, paused seconds, `device_id` and travel distance cannot
be backfilled** (`FR-213`). Labour reporting in v2 needs a **year of honest data** before any standard
is set, and a duration nobody recorded is gone.

So: **v1 creates one task per putaway line and per pick line and per count line, and completes it in
the same request.** The timestamps are populated from day one, the code path is exercised, and `P3`
replaces the auto-completion with a real operator rather than introducing the object.

## Scope

> **Round-2 addition — `Y-004`.** **A task that stalls must age out on its own.** The task-type
> registry gains **`stale_after_minutes`** — it is a property of the work kind, not of the
> individual task — and a scheduled job moves any `STARTED` or `ASSIGNED` task past its type's
> threshold to `EXCEPTION` with a seeded exception code, unassigns it, and notifies the
> supervisor; an unresolved/aged task report exposes the backlog. Two one-line amendments follow:
> add *"in-flight task ageing"* to `FR-165`'s enumeration, and *"tasks stale beyond their type's
> threshold"* to `FR-398`/`WS-223`'s signal list. `P3-03`'s session handover then becomes the
> **deliberate** case sitting on a mechanism that already exists, rather than the only way a stuck
> task is ever recovered.

- **`V500034`** — `whb_tasks`: `task_type_code` → `whb_task_types(code)` (`P0-05`), `warehouse_id`,
  `zone_location_id`, **`owner_id`**, `priority`, `status` ∈ CREATED/ASSIGNED/STARTED/PAUSED/
  COMPLETED/CANCELLED/EXCEPTION, `assigned_to`, **`assigned_at`**, **`started_at`**,
  **`completed_at`**, **`paused_seconds`**, **`device_id`**, **`travel_distance`**, `exception_code`,

- The service that **creates and auto-completes** a task per execution line in v1, so the timestamps
  are real rather than synthetic.

## `V500034` carries a `PNR-3` deadline

★ **Nothing breaks if the timestamps are absent; truth is simply missing.** A duration cannot be
backfilled, so the first client's month-one dock-to-stock and labour reports **cannot be produced**
for any period before the columns existed (`IRREVERSIBLE.md` §3.2, gate `PNR-3` — *"the first
movement posted in any install"*). **The data model is the authority on the column set and must be
re-read immediately before `V500034` is written.**

## Traps

- **Do not defer the timestamps "until there is a gun to record them".** That is the entire failure
  this task exists to prevent. The v1 auto-completed task writes `assigned_at = started_at =
  completed_at = now()`, which is honest and useless for labour standards — **and it is the row that
  proves the column exists and is written.** The moment `P3` lands, the same column starts carrying
  real spans.
- **`required_resource_type` is a v1 column with a v3 consumer.** So is `travel_distance`. Both are
  `IRREVERSIBLE.md`-class observational columns: the *feature* is later, the *column* is now.
- **`owner_id` is `NOT NULL` here too** (`FR-107`). A task against a 3PL client's stock that does not
  name the owner cannot be billed for in v2 and cannot be scoped by the `FR-114` resolver in v1.
- **`FOR UPDATE SKIP LOCKED` has zero occurrences in this repository** (`C-040`). Task claiming for
  waves and picks introduces it in `P3`; this task does not need it, but the `status` ladder and the
  `assigned_to` column must be shaped so that claiming is possible without a schema change.
- **The prior art's KPI snapshot is a 29-metric daily roll-up** (`wms_kpi_snapshots`, `P-058`) and
  every one of its labour metrics reads columns this task creates. `P3-96`/`P3` builds the roll-up;
  if the columns are absent the roll-up has nothing to read.
- **`WAREHOUSE_TASK` must be registered in `COMMON_FILTER_CONFIGS`**, and `status` is a
  **multiselect** — a task grid filtered to one status at a time is unusable for a supervisor.
- **Mobile `ListHeader` supports only `'dropdown' | 'text'`** (`mobile/…/ListHeader.tsx:210-218`), so
  the P3 RF list carries a `createdWithin` dropdown rather than the `createdFrom`/`To` pair. Design
  the backend to accept both from day one.
