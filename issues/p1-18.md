## The rule

**A storekeeper at branch A must not adjust branch B's stock — and a menu filter is not a guard.**

`FR-405`: warehouse-scoped user access participates in **every management query's `WHERE`
predicate**, as a **record-level guard**, alongside the three-mode view pattern of `FR-404`
(view-all, view-branch, no view) that `P0-15` establishes. **The negative test is per endpoint.**

> **Round-4 addition — `RG-001` · `RH-001` · `RH-002` · `RJ-002` — three attributions, one resolver.**
> `whb_warehouses` no longer has a `branch_id` (`D-14`, `P1-05`), and **no `whb_`/`wh_` ledger or
> document table has one**, so platform's column-shaped `BRANCH_FILTER_SQL` (`BranchFilterService.java:167-169`)
> and `PLATFORM-DEPENDENCIES.md` §2.3's *"tables with a `branch_id` column"* rule would both pass
> vacuously on every warehouse grid (`RH-001`). This task owns R22 §1.2.5 in full:
>
> - **Branch tier = platform, not a re-implementation** (`RH-002`). The three-mode pattern of `FR-404`
>   **is** `branchScopeService.resolveStrict(principal, VIEW_ALL, VIEW_BRANCH)` over the
>   `<resource>:view:all` / `:view:branch` pair `P0-15` seeds. This task **wraps** it; it does not inject
>   `BranchStaffRepository` or resolve branches itself (`P0-15`'s architecture rule refuses both).
> - **Resolve once, bind a set** (`RH-001`). `WarehouseScopeService` (in `warehouse-base`) takes the
>   `BranchScope` and returns `Set<UUID> allowedWarehouseIds` — the sites joined to one of the caller's
>   branches by a **current** `whb_warehouse_branches` row whose role has `grants_branch_visibility`
>   (`REGISTERED`, `SERVING`, `FULFILMENT`, `RETURNS` as seeded):
>
>   ```sql
>   -- resolved once per request, never joined on a ledger-sized table
>   SELECT DISTINCT wb.warehouse_id
>     FROM whb_warehouse_branches wb
>     JOIN whb_warehouse_branch_roles r ON r.code = wb.relationship_role_code
>    WHERE wb.branch_id IN (SELECT CAST(UNNEST(STRING_TO_ARRAY(CAST(:userBranchIds AS TEXT), ',')) AS UUID))
>      AND r.grants_branch_visibility
>      AND wb.effective_from <= CURRENT_TIMESTAMP
>      AND (wb.effective_to IS NULL OR wb.effective_to > CURRENT_TIMESTAMP)
>   ```
>
>   Every query then binds **`:allowedWarehouseIds`** against the table's denormalised `warehouse_id`
>   (`DATA-MODEL.md:755`) through a `WAREHOUSE_FILTER_SQL` twin of `BRANCH_FILTER_SQL` — same null/`''`
>   shape, warehouse column.
> - **The six rules** (R22 §1.2.5, `RG-001`, `RH-001`):
>   1. **View-all** → `null` → no predicate.
>   2. **Empty in, empty out — twice.** An empty branch set short-circuits to zero rows before SQL. **So
>      does a non-empty branch set that resolves to zero warehouses** — a branch with no site link. The
>      fragment reads `''` as *no filter*, so a service that passes an empty set through returns every
>      site to a user who should see none. This case is new with the junction.
>   3. **Fail closed on an unlinked site.** An unlinked warehouse is visible to **no** branch-scoped
>      caller; accessories' *"unassigned warehouses stay shared"* arm
>      (`AccessoryStockTransferAccessGuard.java:186-187`) is **refused by name**, and accessories'
>      `is_primary` meaning is not copied (`RH-001`).
>   4. **Two-ended records** (transfers) are in scope if **either** site is in the set.
>   5. **Branch-carrying tables keep `BRANCH_FILTER_SQL` directly**: `whad_counter_sales`,
>      `whin_gstin_profiles`, `whin_delivery_challans`, `whb_number_series`.
>   6. **Access is present-tense; classification is as-at.** Who may see a site is decided on today's
>      links; which registration a historical movement belongs to is decided on the `REGISTERED` link at
>      its `occurred_at` (`P1-05`, `P0-02`'s `I-22`). Mixing the two is how a user who lost a branch keeps
>      seeing it, or how last year's return is re-filed under this year's registration.
> - **The receiving storekeeper is not locked out of transit** (`RJ-002`). A transfer's transit location
>   is a child of the **source** site (`P1-05`), so a destination-scoped user would otherwise be refused the
>   arrive leg. **`wh_transfer_orders:receive` and the transit-loss adjustment authorise posting against
>   *that transfer's* transit location regardless of site scope — and never authorise any other location
>   at the source site.** This is the only verb-carried exception to the warehouse predicate.

> **Round-2 addition — `FR-450`, `K-002`.** Scope is not only *which rows* — it is also *which
> columns*. **Cost and value are suppressed by actor**, through `warehouse:cost:view`, and the guard
> is **response-DTO omission in the mapper**, never a frontend column hide and never a grid
> preference. Platform's `role_field_configs` is client-side only, so a storekeeper without the
> permission who calls the API directly must not receive `unit_cost`, `total_value` or any layer
> amount — and a grid that merely hides the column ships the number to the browser. The same
> omission applies to export: a hidden column that appears in the CSV is the same leak with a longer
> half-life.

- The warehouse-scope predicate, resolved **server-side**, injected into every management query,
  export query, statistics map and dropdown endpoint in `warehouse-base` and `warehouse`.
- **Composition with the two other scopes that already exist:**
  1. **Owner scope** — `whb_owner_grants`, `P0-06`'s single resolver (`FR-114`). A request naming an
     owner the caller has no grant for is **`403`, never an empty grid.**
  2. **Branch scope** — the platform three-mode pattern (`FR-404`, `P0-15`), **resolved through the
     junction to `allowedWarehouseIds`** (`RH-001`, `RH-002`) — never a `branch_id` predicate on a
     warehouse table, which has none.
  3. **Warehouse scope** — this task; if `RA-001`'s warehouse-grant table is adopted it **narrows within
     the branch-derived set and never widens it**, and a user with no grant row keeps every site their
     branches reach (`RH-001`).
  The three **intersect**; they do not override one another. **The written order is owner ∩ (branch →
  warehouse) ∩ warehouse grant** (R22 §1.2.5 rule 5, `RG-001`), so two engineers do not build two
  different intersections.
- **A per-endpoint negative test**, not a single integration test: the guard is only as good as its
  least-covered query service.
- **An architecture rule** that fails the build when a management query service is written without
  the scope parameter — the same shape as `FR-406`'s owner-set contract test (`P0-06`). **The rule is
  re-aimed from `:userBranchIds` to `:allowedWarehouseIds`** (`RH-001`): every native query selecting from
  a `whb_`/`wh_` table with a `warehouse_id` (or `source_`/`destination_warehouse_id`) column binds
  `:allowedWarehouseIds`; only the four branch-carrying tables of rule 5 bind `:userBranchIds`.

## Traps

- **A menu filter is not a guard**, and it is the shortcut this repo has taken before. A hidden menu
  item with a reachable endpoint is a `403` the attacker never sees — the row simply comes back.
  `FR-404` and `FR-405` are both explicit that the guard is in the `WHERE` clause.
- **An empty result is not a denial.** For **owner** scope, `FR-114` requires **`403`, never an empty
  grid**, because an empty grid is indistinguishable from "no stock" and an operator will act on it.
  For **branch/warehouse** scope the row-level filter *is* the correct behaviour — **the two rules
  differ deliberately** and both must be implemented as stated. Do not unify them.
- **Export, statistics and dropdown endpoints are the ones that get missed.** The grid is tested; the
  export that "reuses the same query" often does not, and a dropdown that lists every site is a data
  leak with a friendly UI. `FR-114` names all four surfaces for owner scope; the same four apply
  here.
- **`branches.branch_name`, not `branches.name`**, in every scope join (`V149:18`, R1 §8 trap `T-18`).
- **The prior module's Branch Admin exclusion has already run and grants a new module nothing.**
  `platform/…/V663:17-19` deliberately withheld *"pages with NO branch filtering (warehouse `wms_*`,
  …) — granting these would leak all-branch data"* (`P-014`). That decision is **absent**, not
  inherited, and `P0-15` re-takes it; this task is what makes it true in the data rather than in a
  grant.
- **`hasAnyRole` skips named roles.** A predicate written against role names rather than authorities
  silently excludes custom roles a customer has created.
- **The scope must be applied in the SQL, not after pagination.** Filtering the page in Java gives a
  short page and a wrong total, and at ledger scale it is also a full scan.
- **The platform extraction has already happened — reuse it** (`RH-002`). `PD-D11`/`PP-13` asked
  platform to extract branch-scope enforcement; it shipped as `BranchScopeService`
  (`platform/…/service/common/BranchScopeService.java:14-40`), called from 153 files in six modules, and
  `PP-13`/`PD-D11` are **withdrawn**. Aspect-level enforcement remains optional platform work and never
  blocks this task. **Do not write a second branch resolver** — that duplicate is what the service was
  extracted to end.
- **Platform's branch fragment is column-shaped and passes vacuously here** (`RH-001`).
  `BRANCH_FILTER_SQL` binds `%s.branch_id` on the queried alias; no warehouse ledger or document table
  has that column, so dropping it into a warehouse `RepositoryCustomImpl` compiles, runs and filters
  nothing. The warehouse twin binds `warehouse_id`.
- **`''` means *no filter* to both fragments** (`RH-001`, R22 §1.2.5 rule 2). A branch-scoped user whose
  branches link to no site must get **zero rows**, not every row — short-circuit on the empty *resolved
  warehouse* set, not only on the empty branch set.
- **`P1-20` must not undo it.** Grid configuration that adds a `warehouseId` filter with a default of
  "all" reads as a scope and is not one; the predicate is server-side and applies whether or not the
  filter is set.
