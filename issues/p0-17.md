## This task exists for one reason and closes no requirement

`whb_stock_movement_lines.cost_layer_id` is a **real foreign key**, and `DATA-MODEL.md` `WHB-21`
requires **`V500021` to precede `V500030`**. That is the whole justification. **It closes no `FR`**,
and that is not a defect — it is the one place in the plan where a table's DDL and its behaviour sit
**two phases apart**, deliberately (plan §1, footnote to the phase table).

**The costing engine that fills these tables is `P2-16`.** Ship this late and `P2-19`'s opening-stock
task has no layers to write into, which is the one thing a go-live tie-out cannot fake.

## **`V500021` must land before `PNR-1` (`V500030`, `P0-02`)**

`whb_cost_layers` is **not partitioned** and is created first, so `cost_layer_id` is an ordinary FK
from a partitioned table into a non-partitioned one (`DATA-MODEL.md` §2.1, `IRR-38`).
**`DATA-MODEL.md` §2.1 is the authority on the column set of all three tables and must be re-read
immediately before the migration is written** — a column missed here is a column the ledger line can
never reference, and after `V500030` the line itself can never gain one.

## Scope — three tables, DDL only

### Adopted solution and configuration contract — finalized

The DDL declares valuation grain (company, owner, item, site). Unit cost and layer value are company-base-currency values; preserve original-currency/rate evidence from v1. This task defines schema only; P2-16 implements costing. Do not build a second costing service or treat already base-valued input as foreign price.

Apply [Global settings and resolved behaviour](https://github.com/neetub1508/warehouse-issues/blob/main/docs/GLOBAL-SETTINGS-DECISIONS.md) only within this task’s existing module/version/migration ownership. P0-15/P1-20 own the shared settings implementation; this task consumes it. Do not build unrelated settings controls or later-version capabilities here.

> COALESCE(warehouse_id, <nil UUID>) WITH =, tstzrange(effective_from, effective_to) WITH &&)`.
> `btree_gist` is first declared by `V500011` (`P1-08`), and `V500021` repeats `CREATE EXTENSION IF

> `whb_valuation_policies.category_id` names a category in the `STOCKING` scheme, and
> `whb_items.category_id` no longer exists. (4) **`RETURN_UNMATCHED`** is a legal `cost_basis` on a

- **`whb_valuation_policies`** — `company_id`, `category_id` (a `STOCKING`-scheme category, `RG-005`;
  null = all), `warehouse_id` (null = all), **`method`**, `valuation_grain`,
  `effective_from`/`effective_to` (**`TIMESTAMPTZ`**, half-open, no overlap — was `DATE`, `RG-021`).
- **`whb_cost_layers`** — `item_id`, **`owner_id`**, `warehouse_id`, `lot_id`, `serial_id`,
  `duty_status` (FK into `whb_duty_statuses`, `RL-001`), `layer_date` (`DATE`), `quantity_in`,
  **`quantity_remaining`**, `unit_cost`, `layer_value`, `currency_code`, `exchange_rate`,
  `cost_basis` (incl. `RETURN_UNMATCHED`, `RJ-010`; `ESTIMATED`, `RF-002`), `receipt_occurred_at`.
- **`whb_cost_layer_consumptions`** — **which layer fed which issue**. This is the table a credit note
  needs in order to restore the original layer, and it cannot be reconstructed from the two tables
  above.

**No service, no screen, no endpoint in this task.** WS-049 (Cost Layers) and WS-050 (Valuation
Policies) are `P2` screens.

> **Round-3 fold — `RF-004` · `OD-16` (`GAP-REGISTER-R3.md` §2.6).** **`unit_cost` and
> `layer_value` are in the install's base currency; `currency_code` and `exchange_rate` record what was
> paid** — the transaction's audit trail, supplied by the producer on the movement line and frozen at
> post exactly as `conversion_factor_used` is under `L-7`. The `V500021` DDL comment says so, and a
> layer whose `currency_code` differs from the company's base currency without an `exchange_rate` is
> refused by the writer (a `CHECK` cannot read the company's base currency). `IRR-36`: currency cannot
> be retro-fitted, so this is settled in `V500021`. The wire field (`exchange_rate`, `DECIMAL(19,8)`,
> optional, default 1) is `P0-08`'s; the base-currency falsifier on `WH-SC-160` is `P2-16`'s.

> **Round-3 fold — `RF-002` (`GAP-REGISTER-R3.md` §2.6).** **What an issue costs when no layer is
> open.** Negative stock is a shipped v1 policy, so under `ALLOW` an issue can find nothing to consume.
> It then writes a **negative layer**: a `whb_cost_layers` row with negative `quantity_remaining`,
> **`cost_basis = 'ESTIMATED'`**, and a `unit_cost` from the resolved source — last receipt cost, then
> standard cost, then zero, in that order, with the source recorded on the row. The covering receipt
> **consumes the negative layer first** through an ordinary `whb_cost_layer_consumptions` row and posts
> the estimate-versus-actual difference as a cost-variance value-only movement; the original relief is
> never restated. For this DDL that means two things: the `V500021` column comment lists `ESTIMATED`
> beside `RETURN_UNMATCHED` (still no `CHECK`), and `quantity_remaining` carries **no** non-negative
> `CHECK`. The engine and its two scenarios are `P2-16`'s. `DATA-MODEL.md` §2.1 names no column for the
> recorded unit-cost source — settle it there before the migration is written, per the re-read rule
> above, because after `V500030` the layer is referenced and a missed column is costly.

## Traps

- **The precision ladder decides three of these columns and `OD-7` is not closed.** `unit_cost` is a
  **per-unit** figure — `DECIMAL(19,6)` under accounting's resolved set — while `layer_value` is an
  **extended** total at `DECIMAL(19,4)` and `quantity_in`/`quantity_remaining` are quantities at
  `DECIMAL(18,4)`. The two normative tie-breaks matter here: **`unit_*` beats `value`/`*_amount`**,
  and **`*_percent` beats any reading of "rate"** (`DECIMAL(9,6)`; `DECIMAL(19,8)` is the
  currency-conversion type **and nothing else**). `exchange_rate` is `DECIMAL(19,8)`. **`OD-7` is a
  merge gate on `P0-02` and it gates this file too** — get it wrong here and every valuation number
  in the product is wrong at a digit nobody notices until a reconciliation.
- **`LIFO` must never be offered.** It is prohibited under Ind AS 2 / IAS 2. `OD-6` scopes v1 to
  **weighted average + FIFO**, with standard cost in v1.1; the `method` column is an open vocabulary,
  but the *screen* in `P2-16` must not list LIFO and the seed must not create it.
- **`owner_id` is `NOT NULL` on the cost layer** (`FR-107`) and **non-own stock is never valued**
  (`L-14`). A layer for `owner_type != OWN` is a modelling error, not a zero-value row.
- **`whb_cost_layer_consumptions` is not derivable later.** If issues are posted before the
  consumption rows exist, "which layer fed this issue" is unanswerable for that period and a credit
  note cannot restore the original layer (`C-027` — accessories recomputes the moving average by
  subtracting the reversed receipt's own cost, `StockReceiptService.java:346-364`, `:386-408`, and
  its valuation report reads `last_cost`, not `average_cost`, `StockReportQueryService.java:543`).
- **`moving_average_after` lives on the movement line, not here**, and it is `P0-02`'s column
  (`IRR-39`). A backdated receipt **never restates** it (`RF-001`) — it inserts a layer here, and the
  current average is computed on read from the open layers; without the per-line snapshot there
  is no way to say **what the ledger believed at the time**. Verify it is in `V500030`.
- **Do not add a cost column to `whb_items`.** `FR-052`: there is no cost column on the item master;
  cost is a property of a receipt layer. The only legitimate item-level cost is a **standard** cost,
  and it belongs to the valuation policy, not the item.
- **`uk(…, effective_from)` is not an overlap guard** (`RG-021`). It refuses two policies that start
  at one instant and admits two that overlap, which means two valuation methods for one category and
  site. Only the `EXCLUDE` refuses that. It is free before the first row and a cleanup after.
- **`duty_status` retyped or FK'd after `V500030` is a scan of every ledger partition** (`RL-001`).
  The cost layer and the ledger line must both take the FK in their first migration, and India's
  regimes (`BONDED`, `MOOWR`, `SEZ`, `FTWZ`, `EXPORT_UNDER_BOND`) are `P4-07`'s seed, never base's.
- **A category re-assignment must not re-cost history** (`RG-005`). Resolving the policy from the
  item's current category means a costing method change on `UPDATE`, and "which method costed this
  layer" becomes unanswerable.
- **Do not create a screen "while you are in there".** A grid added here would need a filter scope, a
  cache name, a permission set and a grid-config migration in `P0-15`'s block — all of which are
  `P2-29`'s to allocate.
