### Rule 1 · Export follows the visible columns and is a superset of them (`FR-400`)

- Carrying **created-by and updated-by wherever the grid shows them** — and **not** where it does
  not. *The rule is grid↔export parity, not a fixed column list.* Log- and register-style grids —
  `wh_insufficient_stock_log`, `wh_blocked_movements`, `wh_demand_history`,
  `wh_reconciliation_exceptions`, and every report grid in §7 — deliberately have **no** audit
  columns, so their exports have none either; adding export-only audit columns there emits a column
  no reader can select.
  `ExportServiceContractTest.WITHOUT_AUDIT_COLUMNS` freezes the current set as a **ratchet — it may
  shrink, never grow.**
- **A 100,000-row export does not hold a transaction open**, and that needs a **streaming** path.
  `PP-6`/`PD-D3`: `BaseExportService.DEFAULT_MAX_EXPORT_ROWS = 10_000`
  (`platform/…/service/BaseExportService.java:48`) against a 100,000-row target, and **raising the
  constant solves only the first of three problems** — the transaction is held open for the
  duration, and a per-cell style blows the 64k Excel cell-style limit **at scale, not in dev**.
  **Add a streaming path (`Stream<T>` with a fetch size, written straight to the output) in
  `warehouse-base`** rather than editing `BaseExportService`, and **propose the platform extraction
  separately so the two are not coupled.**
- **CSV keeps the UTF-8 BOM** (`BaseExportService:59`, with the reason at `:51-58`).
- **Return the raw `Boolean` from `extractRowData`.** `BaseExportService` renders Yes/No on every
  path — CSV, the Excel fallback and `ExcelExportHandler` — and nulls as blank; it does **not**
  expose `formatBoolean(Boolean)` (that is on `BaseController`), so calling it is a **compile
  error** (`T-17`). Do not write a `formatYesNo` replacement.

### Rule 2 · Filter-aware statistics carry no cache name (`FR-395`)

**The platform's cache registry already records that exact mistake with its issue numbers.**
`CacheConfiguration.java:190-196` — issues `neetub1508/classic#790`, `#791`: statistics computed from
the same search + filters as the rows *"are uncacheable under any key short of the full filter set"*,
and **registering a name for them caches nothing while reading as though it did.**
**Most warehouse strips are filter-aware, so most get no name.** A `statistics.*` name appears
**only** where the number is provably independent of the filter strip; **no v1 warehouse screen
qualifies.** `dropdown.<entityCamelCase>` names are fine and **must** be registered — an unregistered
name throws `IllegalArgumentException` on the **first call**, not at startup (`:375-377`).
`PP-8`'s fallback, if a strip is too slow: **rollup tables maintained by the same job that proves
`L-4`** — decided *with* the reconciliation design, not after it. **Never a `statistics.*` name.**

### The registry edits, and the honest statement about them

`D-10`'s corollary: **the loose-coupling ratchet can only ever be *"zero commits to
`warehouse-base`"* — never *"zero commits to `platform`"*.** `COMMON_FILTER_CONFIGS` is a TypeScript
`const` at `platform/frontend/src/utils/filterUtils.ts:346` and `CacheConfiguration.java` is platform
Java. **Every new grid edits both.** *A contract that claims otherwise is false on day one and,
being false, gets ignored — taking the true invariants with it.*

## Traps

- **`T-8` — `grid_preferences.default_filters` AND `default_columns` must BOTH be populated**, as
  `'[…]'::jsonb`. `filter_definitions.default_visible = true` **alone builds nothing**:
  `useGridPreferences` reads `defaultFilters` from `grid_preferences.default_filters`, not from
  `filter_definitions` (`V18:12`, `V229:50-51`, example `V229:53-55`).
- **`CM-4` — the table is `filter_definitions`, created in `V229`.** There is **no**
  `grid_filter_definitions` table — 0 hits over all migrations — and inserting into that name
  **fails at Flyway and crash-loops the backend.**
- **`CM-3` — "NO JSONB" is overstated and the repo's own ratchet says so.**
  `platform/…/architecture/ArchitectureInvariantsTest.java:225-239` freezes a **baseline** rather
  than banning it, and `grid_preferences.default_columns` **is** `JSONB NOT NULL DEFAULT '[]'`.
  **Every warehouse grid migration must emit `'[…]'::jsonb`.** The rule that holds is *no JSONB on
  new `wh_` business tables*.
- **`T-6` — a field not in `COMMON_FILTER_CONFIGS.{SCOPE}` is silently dropped by
  `convertFiltersForApi()`** before the API call, and the filter UI appears to do nothing.
  **Both halves of every date pair** must be listed; there is **no range type** — the eight are
  `text | select | enum | multiselect | boolean | date | dateOnly | number` (`filterUtils.ts:30`).
- **`dateOnly` versus `date` is load-bearing here, not cosmetic.** `filterUtils.ts:49-56` documents
  that `date` shifts to UTC day boundaries for `TIMESTAMP` columns, *"which moves the 'from' bound to
  the previous calendar day for users east of UTC"*. `FR-327` makes every statutory, expiry,
  manufacture and count date a SQL `DATE`; **those filters are `dateOnly`.** The DB side is a
  **different registry** — `filter_definitions.filter_type` (`V229:13`, default `'text'`) takes
  `text | select | date | number | boolean | multiselect`, and **a `dateOnly` scope entry pairs with
  a `date` row there.**
- **There is a third filter surface and it is easy to forget: the API service.** An enumerating
  `getForManagement` silently drops unknown keys, so a scope entry plus a `filter_definitions` row
  plus an unforwarded parameter is still a filter that does nothing. **Three-way parity**
  (`BUILD-SPEC-SCREENS.md` §0.5).
- **`T-9`** — `WHERE NOT EXISTS` on every menu insert; `menus` has no unique constraint on
  `(name, parent_id, menu_level)` and `ON CONFLICT DO NOTHING` does not stop a Flyway-retry
  duplicate.
- **`T-12` — module migrations are flattened into one directory at build time**
  (`Dockerfile.backend:140-181`). Two tasks claiming one number is a **startup failure**. Each grid's
  number is claimed in its own task header and `tools/check-design-set.py` fails on
  double-ownership.
- **`T-11` — the frontend merge is last-write-wins** across the whole `src/` tree
  (`Dockerfile.frontend:80-177`); every locale, component, service and type file is `wh`-prefixed.
- **`T-5` — `SqlSortBuilder` whitelist or no sorting**, always with a default sort. A sortable
  column needs four gates aligned: the column definition, the field mapping, the API sort parameter
  and the entity path.
- **Export ignores filters and export ignores grid sort are known live defects elsewhere in this
  repo.** Assert both: the export of a filtered, sorted grid reproduces **that** filter and **that**
  sort.
- **Excel mangles text columns.** Phone-like and code-like columns need the text pin; a `VARCHAR`
  part number of digits becomes a number and loses its leading zero.
