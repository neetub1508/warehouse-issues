## This is the API every future consumer builds against

A `logistics` module, a POS, an eCommerce channel and **every adapter** build against this surface.
`PORT-AND-ADAPTER-CONTRACT.md` §10.6 names four API decisions that are unrecoverable later and §2.10
names **twelve provably unaddable properties**. The idempotency semantics in particular are **either
exact or worthless**.

- **`V500041`** — `whb_inbound_messages`, `whb_movement_batches`, `whb_movement_batch_results`.
- **Persist before process** (`FR-044`): an inbound-message row with the payload reference and a
  status ladder `RECEIVED`/`PROCESSED`/`FAILED`/`DISCARDED`, written **before** any validation runs.
- **The v1 offline hooks, shipped even though v1 is online-only** (`FR-047`): a client-generated
  transaction id and a device-supplied `occurred_at`. The queue itself is `P3-04`; **the irreversible
  half is the per-scan idempotency key**, and replayed scans without one produce duplicate ledger
  rows that can only be corrected by a reversal that looks like an adjustment.
- **Item identification without warehouse's UUIDs** (`FR-038`): a line names its item by `id`, **or**
  `sku`, **or** `barcode`, **or** `(source_module, external_id)`.

## The idempotency table — exact, or it is worthless

| Condition | Response | Body |
|---|---|---|
| Key unseen | **`201 Created`** | the new movement id and its assigned `sequence_no` |
| Key seen, `payload_hash` **identical** | **`200 OK`** | the **original** movement id and its original `sequence_no`. **This is not an error.** Nothing is posted |
| Key seen, `payload_hash` **different** | **`409 Conflict`** · `IDEMPOTENCY_KEY_REUSED` | nothing posted; the body **names the original movement id** so the caller can diff |
| Key absent or blank | **`422`** · `IDEMPOTENCY_KEY_REQUIRED` | — |

> **`PC-16` — never generate a key server-side, and never silently overwrite.** A server-generated
> key makes a retried network timeout post **twice**, which is the exact failure the key exists to
> prevent. A silent overwrite makes the ledger disagree with the producer with no record that it
> ever did.

**`PC-17` — what is hashed, because no other source says.** `payload_hash` is `SHA-256`, lower-case
hex, computed **server-side** over the **canonicalised received request body**, before any
defaulting, enrichment or resolution: object keys sorted lexicographically at every level; no
insignificant whitespace; `null`-valued keys **omitted**; numbers in the decimal string form received;
timestamps normalised to UTC `Z` at millisecond precision; arrays in received order.
`idempotency_key` **is** part of the hashed body; transport headers, the authenticated principal and
`recorded_at` are **not**. **A client-supplied hash is rejected** — trusting one lets a buggy producer
declare two different payloads identical, which is a silent double-post with a clean audit trail.

## What the port must NOT carry (`FR-041`, `PORT-AND-ADAPTER-CONTRACT.md` §2.9)

No carrier, AWB, trip or vehicle · no **sales price**, customer or tax · no billing charge code · no
channel-specific field · **no JSONB payload** · no free-text `reference` · no expression, script or
rule DSL. Each has a stated home: the lineage quad, the accounting envelope, `wh3_billable_events`,
`whb_movement_line_attributes` with a **registered** key, the four lineage columns + `source_line_ref`,
bounded rows. *(A **unit cost** does ride the line, because warehouse owns cost under `D-6`; a
**price** is a commercial fact about the document that sells.)*

**Mobile is `none` for all three, and that is a stated decision, not silence** (`FR-218`): these are
support and integration surfaces, an operator has no action on them, and a handheld cannot render a
payload. **WS-054 carries an alert**: the queue non-empty beyond a threshold fires it, and the
threshold lives in `admin_settings` under `warehouse.port.rejected_queue_threshold` — a threshold
column with no job that reads it is a defect at merge (`FR-165`, `P0-13`).

All three are **ledger-style: no `createdByName`/`updatedByName`** in grid or export.

## Traps

- **The multi-implementation registry shape is settled and it is not `@Primary`.**
  `ExportService.java:31`, `BoomBarrierWebhookController.java:44-48`,
  `AccImportHandlerRegistry.java:36-44` all take a `List<T>`. `@Primary` admits exactly one
  implementation and is the wrong shape for a port with N producers (`C-039`).
- **`FR-040` — a single movement posts wholly or not at all.** There is no partial success *within*
  one movement. A producer wanting per-line independence sends one movement per line, which is what
  `/batch` is for. Do not "helpfully" skip a bad line.
- **`/batch` must not lose 399 movements because one bin was renamed** (`FR-034`). Per-movement
  transaction, per-movement result, per-movement idempotency key. The `whb_movement_batch_results`
  child grid is how a support engineer answers *"which one failed and why"*.
- **The ledger never returns quietly** (`FR-029`). The live counter-example is in the repo:
  `issueStock()` silently no-ops when no stock-level row exists
  (`InventoryStockAdjustmentService.java:56-60`) and `AccessoryIssuanceService.java:275-278` swallows
  non-`BusinessException` failures and continues (`C-025`).
- **`@PreAuthorize` on every port method, no exceptions** (`FR-043`, CLAUDE.md CRITICAL #1), **and**
  the posting permission is additionally checked against the caller's owner grants by the single
  resolver of `FR-114`. `403 OWNER_NOT_PERMITTED`, **never an empty result** (`PC-05`).
- **`GET /movements` by lineage needs all three keys in the `COMMON_FILTER_CONFIGS` allowlist**, or a
  consumer cannot find its own postings and builds a private mapping table instead (`FR-036`; an
  unlisted field is silently dropped, `filterUtils.ts:346`).
- **Hibernate native-query timestamps come back as four possible types** and a `null` return is
  silent data loss — copy `UserActivityLogQueryService.java:288-307`, which logs a warning on the
  fifth (R1 §8 trap `T-4`, `FR-438`). The port reads and writes three timestamp columns.
- **Persist-before-process is not the same as log-after-failure.** The inbound-message row must exist
  before validation, or a payload that crashes the parser leaves no evidence at all (`FR-044`).
- **`source_document_id` is `VARCHAR(100)`, never a UUID and never an FK** — an external system's id
  is not ours (`DATA-MODEL.md` §3.3). The previous attempt at this seam died of the opposite: 84 FK
  references out of warehouse into `scc_*`, several to tables that never existed (`G-025`, `G-026`).


## Acceptance
- [ ] Unseen key → `201` with the assigned `sequence_no`; **same key, same hash → `200` with the
      original movement and nothing written**; same key, different hash → `409`
      `IDEMPOTENCY_KEY_REUSED` naming the original movement id; absent key → `422`
      (`WH-SC-023`, `WH-SC-024`, `WH-SC-165`, `WH-SC-166`)
- [ ] The key is **never** server-generated, asserted by a test that submits without one
- [ ] `payload_hash` is computed server-side over the canonicalised **received** body per `PC-17`, and
      a client-supplied hash is rejected
- [ ] A batch of 400 with one bad movement posts 399 and returns a per-movement result array
      (`WH-SC-167`, `WH-SC-168`)
- [ ] `/reverse` takes its own idempotency key and a mandatory reason code, and **refuses to reverse a
      reversal** (`WH-SC-171`)
- [ ] `/simulate` returns balance deltas and the error list and **writes nothing**, proved by row
      count on `whb_stock_movements` and `whb_inbound_messages` (`WH-SC-172`)

- [ ] A payload carrying a carrier, a sales price or a JSONB blob is **rejected**, not ignored

- [ ] Every inbound request is persisted **before** it is processed, and a parser crash still leaves a

## Blocked on

**`OD-8` — how does an out-of-process consumer authenticate to the port?** *The auth model shapes the
endpoint*, so this must be answered before the endpoint is written. There is **no API-key table in
platform** (grep → 0); the only API-key path in the repo is per-handler inside the boom-barrier
webhook. **Recommendation:** a **platform service principal** — a first-class non-human identity with
role grants, so the port needs no auth mechanism of its own. It is `PP-2`, it is **platform's to
build**, and it is the only item in this set that platform must build for warehouse.

**Fallback if it does not arrive:** the port ships authenticated by an ordinary user account holding
`warehouse:movements:post`, and a separately deployed out-of-process consumer is **not supported
until v3**. That is v1-acceptable and a v3 blocker — record it in the install guide rather than
discovering it.
