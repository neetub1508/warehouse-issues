## Scope

- **`V510017`** — `wh_putaway_rules`, `wh_putaway_tasks`.
- **Rules are data, evaluated in sequence, returning a suggested location the operator may override
  — with a captured reason** (`FR-135`). The reason is **captured, never silently discarded**: the
  override rate against a rule is the only signal that the rule is wrong.
- **v1 ships the evaluation harness.** The **optimiser is v3** (`P6`), and `P3-02` makes putaway
  task-driven. Saying so here is what stops v1 growing a slotting engine.
- **Putaway tasks are `whb_tasks` rows** (`P0-10`) with a `wh_putaway_tasks` row carrying the
  putaway-specific facts. The task's `assigned_at` / `started_at` / `completed_at` are populated from
  day one because **a duration cannot be backfilled** (`FR-213`).

**`DATA-MODEL.md` §2.2 (`WH-08`) is the authority on both column sets and must be re-read immediately
before the migration is written.**

## Traps

- **The override reason must be captured, never silently discarded.** `FR-135`. Without it, the
  override rate is invisible and the rule that is always overridden is never fixed. `hasOverride` is
  a first-class filter for exactly that reason.
- **`strategy` is whitelisted, and the rule chain is rows evaluated in sequence** — not an expression
  language and not an `if` ladder in a service. `FR-041` and `PORT-AND-ADAPTER-CONTRACT.md` §2.9
  forbid a rule DSL anywhere in this product.
- **Do not build the optimiser.** v1 evaluates the chain and suggests; v3 optimises. A slotting
  heuristic added "while we are here" becomes the thing nobody can change because a customer depends
  on its output.
- **Completing a putaway posts a movement through the single writer service** (`FR-436`), from the
  staging location to the actual location — **two lines, conserving** (`L-1`). It never writes
  `whb_stock_positions`.
- **A putaway into a location the item's temperature class forbids is rejected by the port**
  (`FR-068`, `P1-03`) — the rule engine suggests, the port refuses, and both messages must be
  distinguishable to the operator.
- **A putaway violating `commingle_policy` or `dedicated_owner_id` is rejected too** (`FR-087`,
  `P1-05`). The suggestion engine should not propose such a location in the first place; the port is
  the backstop, and **a port refusal in production is an incident, not a validation.**
- **`wh_putaway_tasks` must not duplicate `whb_tasks`' lifecycle columns.** One task object, one set
  of timestamps (`P0-10`); this table carries only the putaway-specific facts. Two lifecycles is how
  the labour report and the task grid disagree.
- **`status` is a `multiselect`** — a supervisor works "created + assigned + started" as one view.
- **Two grids × two platform files**; `strategy` and `overrideReasonName` are registry-backed and
  must **fetch**, never be a TypeScript union (`OD-5`, `FR-380`).
- **`FOR UPDATE SKIP LOCKED` has zero occurrences in this repo** (`C-040`). v1 assigns putaway tasks
  explicitly; `P3` introduces claiming — do not invent it here.

## Acceptance
- [ ] Rules are **rows evaluated in sequence**, reorderable, and the **Test** modal shows which rule
      won and why (`WH-SC-074`)
- [ ] Completing a putaway with the suggested location posts a conserving two-line movement through
      the single writer service (`WH-SC-052`)
- [ ] Overriding the suggestion **requires a reason**, stores it on the task, and makes the row
      findable through `hasOverride` (`WH-SC-052`)
- [ ] The putaway task is a `whb_tasks` row with `assigned_at` / `started_at` / `completed_at`
      populated — proving `P0-10`'s columns are written from day one

      port**, with a message distinguishable from a rule-engine suggestion
- [ ] No expression language, no `if` ladder in a service: `strategy` and the scope columns are
      whitelisted
- [ ] Two grids ship `default_columns` **and** `default_filters`; both scopes registered; the mobile
      decision recorded per screen
