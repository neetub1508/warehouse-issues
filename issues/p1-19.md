## Traps

- **A missing module namespace prefix renders a BLANK label, not the key.** `warehouseBase:items.…`
  without the namespace resolves to nothing and the header is empty — which reads as a CSS problem
  and is not.
- **The wrong namespace renders silent English.** A key looked up in the platform namespace that
  happens to exist there returns the platform's string, in English, on a French install, with no
  error anywhere.
- **The frontend merge is last-write-wins across the whole `src/` tree**
  (`Dockerfile.frontend:80-177`), so **every locale filename must be globally unique**:
  `warehouseBase.json` and `warehouse.json`, never `common.json` (`C-012`, R1 §8 trap `T-11`). Two
  modules shipping `en/common.json` silently lose one of them.
- **A stale `maxLength` in an i18n file shadows the real validation message** — a known trap in this
  repo. Validation text belongs to the backend's structured field errors; the i18n file carries
  labels.
- **`SafeTranslation` registration is a runtime gate.** An unregistered namespace does not fail the
  build; it renders blank at runtime (`MODULE-INTEGRATION.md` §2 row 14).
- **The badge variant must not be a frontend map.** `const statusVariantMap = { AVAILABLE: 'success',
  … }` re-closes on the frontend exactly what `D-10` opened on the backend — the same defect `OD-5`
  names, and the one R2 records as *a documented recurring defect in this codebase*. The variant is
  `whb_stock_statuses.badge_variant`, fetched.
- **The fallback is to the registry row's `name`, not to the code.** A new status with no translation
  key must read *"Awaiting Rework"*, not `AWAITING_REWORK` (`FR-381`).
- **`mobile/src/schemas/common.schemas.ts` is a third copy of every dropdown vocabulary.** A value the
  backend opened but the zod schema closed **fails the save with no message** — so a new status,
  disposition, item type or UoM added as a catalogue row must not need a mobile schema edit
  (`FR-382`, `OD-5`). Handhelds update on an MDM schedule, so a shipped `z.enum` outlives its fix by a
  release cycle — which is why `FR-382` is now v1 · P0 and CI-enforced (`RL-009`).
- **Hindi and French expand.** Column headers and button labels that fit in `en` do not always fit in
  `fr` or `hi`; check the grid header and the modal tab strip on the three locales, not one.
- **Every warehouse locale file must cover every P0 and P1 screen** — the fourteen catalogues, the
  masters, the ledger screens, the inbound documents, every modal title, every action label, every
  validation label and every menu leaf. A partial file is worse than none: it renders half the screen
  in the user's language and half in English.

## Round-4 additions (folded from former P5-28, #161) — registry row translations

**v2 increment of this task — design the schema now, build in the v2 wave.** Round 4 filed registry row
translations as their own task, `P5-28` (`#161`). On 2026-09-10 it was closed as a duplicate and folded
here, because this task owns the fallback it extends: the status badge's i18n key *falling back to the
registry row's name* (`WH-SC-147`'s fallback half), and the three shipped locales. Migration **`V500071`**
and requirement **`FR-469`** move here with it.

**Scope — one table mirroring `menu_translations` (`RL-015`).** A registry row carries one `name`.
`PC-69` falls back to that name when an i18n key misses, which is right for a **seeded** row that has a
key. An **install-created** row (`owning_module = 'INSTALL'`, `RL-012`) has no key at all. A Hindi-first
store's own reason codes therefore render in whatever language the administrator typed, on every screen,
handheld and printed challan (`RL-015`). Platform already translates data rows: `menu_translations`,
which `V501010` writes. This increment copies that shape (`FR-469`).

1. **`whb_registry_translations`** (`V500071`) — `registry_table`, `code`, `locale`, `name`;
   `uk(registry_table, code, locale)`. `locale` is one of the install's shipped locales (`en`, `fr`, `hi`,
   this task's).
2. **The fallback order becomes** the i18n key, then this table for the reader's locale, then the row's
   own `name` (`PC-69`, `FR-469`). One resolver serves the web, the handheld and the print binding.
3. **A *Translations* tab** on each registry screen (`WS-001`–`WS-004`, `WS-006`, `WS-008`, `WS-010`,
   `WS-012`–`WS-014` and the later registries) — locale, name — editable by whoever may edit the registry
   row. No new screen id.
4. **Print templates bind the resolved name** (`P2-14`), so a regional-language challan prints the
   translated reason and status names.

**Requirement** `FR-469` — owned here now. **Scenario** `WH-SC-325` — an install-created reason code
with a Hindi translation shows the Hindi name on the `hi` user's screen and printed challan. **Closes**
`RL-015`. **Depends on** `P0-04` (the registries and immutable codes) besides this task's `P0-15`.

**Traps (v2 increment)**

- **Keyed by `code`, which is why `code` is immutable.** `RL-013` makes code-keyed FKs `ON UPDATE
  RESTRICT` and corrects a code by retire-and-reseed. A translation keyed by a mutable code would detach
  silently. It is the only thing v1 had to secure for this increment, and it did.
- **`registry_table` is a closed list checked by the service**, not a free string. It is the set of
  registry tables `DATA-MODEL.md` §2.1.1 enumerates (`I-18`). A translation for a table that is not a
  registry is refused.
- **Never a second `name` column per locale.** `name_hi`, `name_fr` is the shape this table exists to
  prevent; the next locale would be a base migration.
- **The fallback is one function.** The web frontend, the mobile app and the print renderer each resolve a
  name today. They must call one endpoint or one shared helper, or the three will disagree on the first
  missing translation.
- **Seeded rows keep their i18n keys.** This table is for install-created rows and for overriding a seeded
  name locally. It is not the product's translation mechanism for its own seeds.
