## The single row a parts manager tests us on

`IMPLEMENTATION-PLAN.md` §5.3 names this **the most commercially dangerous deferral in the plan**: we lose
to CDK, Reynolds, Tekion, Karmak and Autologue on the **computed best stocking level**, *"in the one
segment we are best positioned to win."* `FR-258`: *"No human maintains 30,000 reorder points, and this
is the single biggest gap between a stock system and a parts system."*

## Scope

- **`V510300`** — the stocking-policy object and the computed-level history: policy name, phase-in rule
  (*k* hits in *m* months), demand window, days-supply target, phase-out rule (*n* months with no hits),
  rounding and pack-multiple rules, and per item × site the computed level, the inputs it was computed
  from, the run that produced it, and **the parts manager's override with a reason and an author**.
  **This table is new: `DATA-MODEL.md` §7.3 allocates no v3 block for `warehouse`**, and
  `IMPLEMENTATION-PLAN.md` §2.9 divergence 4 carves `V510300`–`V510302` out of the
  `V510215`–`V510999` correction reserve for exactly this. Add the row to §7.3 in the same PR.
- **Computed from our own demand history** — `wh_demand_history` (`P2-15`, v1) — never from a forecast.
  Forecasting is a **deliberate refusal** (§7 row 8): *"a WMS that guesses at forecasts is a worse
  forecaster than a spreadsheet and a worse WMS for the distraction."*
- **Phase-in, phase-out and the override are three distinct states**, and each is visible: a part that
  phased in last month and a part a manager pinned are not the same thing and must not look the same.
- The computed level **writes the item × site reorder point** that `P2-15`'s run already reads — it does
  not introduce a second replenishment path.

## Traps

- **An override the next run silently erases is worse than no override.** The override is a row with an
  author, a reason and an expiry; the run **respects it and says it did**. This is the first thing a parts
  manager tests.
- **Show the working.** A level nobody can explain is a level nobody follows. Persist the inputs — hits,
  window, demand, days-supply target, lead time, pack multiple — alongside the number, exactly as
  `wh_replenishment_suggestions.basis_note` does for a suggestion.
- **`P1-03` already ships ABC / velocity / count-frequency classes as v1 columns with a v3 job.** That job
  is this phase's; do not build a second classification. Check whether `P6`'s ABC/XYZ work is allocated
  elsewhere before adding a class column here.
- **Demand history begins when the ledger begins** — `PNR-3`. A demand window longer than the install's
  history produces a confident number from nothing. Refuse, or mark the level `PROVISIONAL` and say why on
  the screen.
- **Do not build a solver.** Slotting optimisation is a deliberate refusal (§7 row 7); *"the analysis is
  v3 and not refused; the solver re-enters only after a year of our own data."* A days-supply level from a
  demand window is analysis. An objective function is not.
- **Pack multiples and minimum order quantities round the level**, and the rounding must be visible —
  a computed 7 that becomes an ordered 12 because the case is 12 is not a bug, but it is a surprise if the
  screen does not say so.
- **No float or double anywhere**, including the frontend DTO (`OD-7`). Days-supply is `DECIMAL(18,4)`;
  a service-level percentage, if any, is `DECIMAL(9,6)`.
- The run is a scheduled job and **ships with the threshold columns it reads** (`FR-165`).

## Acceptance
- [ ] A part with *k* hits in *m* months phases in automatically at a level derived from its demand window and days-supply target
- [ ] A part with no hits for *n* months phases out, and the phase-out is visible as a distinct state from "never stocked"
- [ ] A manager override with a reason **survives the next run**, and the run's output says the level was overridden and by whom
- [ ] Every computed level persists its inputs, and the screen shows the arithmetic
- [ ] A demand window longer than the install's ledger history does **not** produce a confident level — it is refused or marked `PROVISIONAL` with the reason shown
- [ ] The computed level writes the existing item × site reorder point; `P2-15`'s run is unchanged and there is no second replenishment path
- [ ] Pack-multiple rounding is applied and shown
- [ ] The migration number is recorded in `DATA-MODEL.md` §7.3 in the same PR
- [ ] **Mobile:** `none` — a stocking policy is a desk master; the resulting reorder point is already visible wherever the item is (`D-13` declaration)
