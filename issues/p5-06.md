## Scope

- **`V530044` — `wh3_freight_billing_rules`** (`W3-11`): client, mode, markup percent, markup fixed,
  tariff card code, carrier account code, effective from/to.
- **Five outcomes from four modes plus one refusal:**
  | Mode | What is metered |
  |---|---|
  | `AT_COST` | the carrier's charge, passed through unchanged |
  | `COST_PLUS_PERCENT` | cost × (1 + markup) |
  | `COST_PLUS_FIXED` | cost + a fixed amount |
  | `OWN_TARIFF` | our published tariff, from a rate card, ignoring the carrier's number |
  | `CLIENT_OWN_ACCOUNT` | **nothing** — the client's own carrier account is billed by the carrier direct |
- **The pass-through is metered at the quoted amount and reconciled when the carrier invoice lands.**
  The carrier's actual charge arrives **later than the shipment**, so a design that waits for it produces
  a run that can never close. The quote is `P5-11`'s persisted `wh_rate_quotes` row; the reconciliation
  posts a **delta billable event**, never an edit to the original.

## Traps

- **`CLIENT_OWN_ACCOUNT` must meter nothing, not meter zero.** A zero-amount `SHIPPING_PASSTHROUGH` event
  appears on the portal and on the invoice and generates a support call every month. Same distinction
  `WH-SC-032` draws for non-own stock: *"the assertion is **the number is absent**, not the number is
  zero."*
- **The carrier invoice arrives after the run may already be approved.** The reconciliation therefore
  posts a **delta event into the current open run**, exactly as `P5-05`'s post-approval rule requires —
  it never re-rates a frozen run.
- **Markup percent is `DECIMAL(9,6)`**, not `DECIMAL(19,8)`: `_percent` beats any reading of "rate", and
  `DECIMAL(19,8)` is the currency-conversion type and nothing else (`OD-7`).
- **`carrier_account_code` is a stable string key, resolved through a service — never an FK into
  `wh_carrier_accounts`.** `wh_carriers` / `wh_carrier_services` / `wh_carrier_accounts` are on R7 §2.6's
  list of **five boundaries that will move** to `logistics`, and *"applying that rule to one object and
  not the other four is how the move stops being cheap"* (`G-013`). This is also the `G-025` lesson at
  module scale: the previous attempt died of 84 FK references into another module.
- Effective-date overlap **per client** (amended at build, F7 — not per `(client, mode)`: a client has
  exactly one rule in force on any day, or metering is ambiguous) needs an `EXCLUDE` constraint, not a
  service check — same `btree_gist` argument as `P5-02`.
- `effectiveFromFrom`/`To` are two **`dateOnly`** filters; register the scope in `COMMON_FILTER_CONFIGS`
  (`filterUtils.ts:346`) or they are dropped silently.

## Decisions recorded at build
Gate round 1 (reviewer + functional-reviewer), ratified by the driver (`W3-FIX-DECISIONS.md` § P5-06):
- **End-date is strictly after today** (F1). The range is half-open `[from, to)`, so a rule ending today is already
  EXPIRED today and a shipment metered under it this morning could no longer be reconciled. `validateEndDate`
  refuses `effectiveTo <= today` (`FREIGHT_RULE_RETROACTIVE`); the End-date modal's minimum and default are tomorrow
  (or the day after the rule starts, whichever is later), and its maximum is the current end − 1 day (F9 — the
  server refuses a date not earlier than the current end).
- **Reconcile uses the rule the original charge was metered under** (F2). `reconcile(ruleId, quoted, invoicedCost)`
  loads the rule by the original `FreightCharge.ruleId` (refused `WH3_FREIGHT_NO_RULE` when it is not the client's),
  never re-finds it by ship date. OPEN INTERFACE for P5-03: persist `ruleId` on the metered event and pass it back.
- **Recorded, not fixed — F2 re-verify: PARTIAL** (W3 re-verify, `w3-reverify-func.md`). Loading the rule by id closes
  the end-dated and replaced cases, not the lead one: an UPCOMING rule can still be edited after a charge was metered
  under it for a future ship date, and `reconcile` then prices the delta with the EDITED terms. Latent - `meter` and
  `reconcile` have no caller yet. To close: freeze an UPCOMING rule's terms once a charge is metered under it, or carry
  the metered terms on the event (with the P5-03 `ruleId` hand-over above).
- **The rule lifecycle runs on the UTC day** (F3, option c). UPCOMING / ACTIVE / EXPIRED, the "starts today or later"
  guard and the End-date floor are judged on `LocalDate.now(clock)` (UTC) server-side and `getTodayUTCForInput()` in the
  modals. A freight rule is client-level and `wh3_clients` has no timezone; the strictly-after-today End-date guard
  absorbs the ±1-day skew against a site day.
- **OWN_TARIFF names our published tariff** (F4): a STANDARD card (no `wh3_rate_card_clients` row — never another
  client's negotiated card), priced in the client's billing currency, carrying an `SHP_FREIGHT` line on its ACTIVE
  version or an ancestor's. Refused at save (`FREIGHT_TARIFF_CARD_NOT_STANDARD` / `_CURRENCY` / `_NO_FREIGHT_LINE`,
  field `tariffCardCode`) and re-checked at metering (`WH3_FREIGHT_TARIFF_CARD_INVALID`; a missing line is the
  resolver's `WH3_UNRATED_EVENT`). The picker lists standard cards only.
- **Acceptance items 1–2 are carried, not claimed** (F5). Nothing calls `meter` / `reconcile` yet: posting the event
  is P5-03's, the open-run delta P5-05's, the quoted cost P5-11's. `WH-SC-378` / `WH-SC-379` are proven at the
  pricing layer only ("Unit (pricing only)") until those land.
- **`WH-SC-380`'s database half** (F6): a save that bypasses the service and hits `ex_wh3_freight_billing_rules_overlap`
  maps to the same field (`effectiveFrom`) and code (`FREIGHT_RULE_OVERLAP`), with the generic sentence "already has
  another rule" — the transaction is rollback-only, so the overlapping rule is not re-queried to be named. The
  scenario is amended to say so.
- **Overlap is per client** (F7) — the Trap above is amended.
- **A zero pass-through charge is absent** (F8): AT_COST / COST_PLUS_* that price to 0.00 return `Optional.empty()`,
  never a 0.00 `SHP_FREIGHT` line — the same "absent, not zero" rule as CLIENT_OWN_ACCOUNT.
- Spec-silent build decisions (lane return): only UPCOMING rules are editable, a rule in force is end-dated; a rule
  starts today or later; each mode carries exactly its one term and a stray term is refused on its field; no rule in
  force → 422 `WH3_FREIGHT_NO_RULE` (never a default AT_COST); `markup_percent` is percentage points (12.5 = 12.5%);
  OWN_TARIFF and CLIENT_OWN_ACCOUNT post no reconcile delta.
