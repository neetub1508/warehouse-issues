### 2 · The module — and where its migrations are numbered

**This task claims no Flyway number in this design set's bands, and that is the honest position.**
`D-2` allocates five bands — `warehouse-base`, `warehouse`, `warehouse-adapter-*`, `warehouse-3pl`,
`warehouse-india` — and **`logistics` is none of them**. It is a first-class module of our own
(`FR-366`: it posts directly and gets no adapter), so its `log_*` schema is numbered by the
`logistics` design set, in a band that set allocates, exactly as `logistics` carries its own screen
spec. Claiming `V524000`–`V524099` on this header would have this design set allocate numbers for a
module it does not own — the same category error as the `scc_*` seam below.

**What the adapter band does reserve** (`DATA-MODEL.md` §2.5.6, §7.4) is `V524000`–`V524999` for the
**warehouse-side enablement of the logistics seam** — the catalogue seed rows (`TRIP`, `MANIFEST`,
`CONSIGNMENT`, source system `LOGISTICS`) and the seam's permission, menu and grid configuration.
That block is a reservation, not a claim: **no task in this design set writes into it**, and the
first task that does claims its numbers on its own header.

- Prefix and permission namespace **reserved since v1** (`FR-346`, `FR-407`): prefix **`log_`**, and
  `logistics:*` permissions already seeded by `WHB-71` (`V501000`) with their
  `permission_dependencies` rows — *"reserving the string costs one seed row, and a permission invented
  in v2 must otherwise be re-granted by hand to every existing role across every install."*
- **Trips, ePOD and freight settlement** are the exit criterion's three named capabilities. Consignments,
  manifests, stops and legs, own-fleet vehicles and drivers, maintenance, fuel and detention follow from

## Traps

- **⚠ The failure this task exists not to repeat.** The previous attempt at this seam made warehouse
  **structurally FK-dependent** on a supply-chain module: **84 FK references into `scc_*`**, several to
  tables that **never existed** — `scc_items` (4 refs), `scc_drivers`, `scc_alert_rules`,
  `scc_alert_history`; a designated owner entity (`SccCompany`) that was never built, leaving an orphan
  `scc_company_id` column with no FK (`SCC_MODULE_ISSUES_ANALYSIS.md` §4.4); `scc*`-named classes and a
  shared i18n namespace living **inside** warehouse-core (`WAREHOUSE_CORE_ISSUES.md` WF-3, ~50 `Scc*`
  interfaces across ~60 files); and a bulk-import feature whose table and **menu** were in one module and
  whose controller and **page** were in the other, so *"core deployed alone renders a menu entry that
  404s"* (WF-1) — which only worked because the Docker frontend `cp`-merges both trees.
  **`G-025`: 84 FKs is not a seam.**
- **⚠ WHAT WOULD FALSIFY THE ZERO-COMMITS CLAIM.** State these in the PR and check each:
  1. any commit in this PR touching `warehouse-base/**` — `git log --oneline -- warehouse-base/ | wc -l`
     must equal its value at the previous commit (`PC-74`);
  2. a **new column** on any `whb_` table, however small;
  3. a **new value** added to a base vocabulary by `ALTER` rather than by a seed `INSERT` from this
     module's own migration;
  4. any `REFERENCES … log_` clause in a migration numbered below `V524000`;
  5. any `import ai.logistics` under `warehouse-base/**` or `warehouse/**`;
  6. a base **API change** made "so logistics can call it" — including a widened response field.
  **Any one of the six falsifies it.** Items 2 and 3 are the ones that arrive innocently.
- **⚠ And the caveat, stated because a false invariant gets ignored — taking the true ones with it**
  (`D-10` corollary, `G-047`, `PC-74`): **the ratchet can only ever be "zero commits to
  `warehouse-base`". It can never be "zero commits to `platform`."** `COMMON_FILTER_CONFIGS` is a
  TypeScript `const` at `platform/frontend/src/utils/filterUtils.ts:346` with **213 scopes** and a field
  absent from its scope is **silently dropped** before the request is built; `CacheConfiguration.java` is
  platform Java with **234 registered names** and warns in the file itself at `:375-376` that *"an
  unregistered name throws `IllegalArgumentException` on the FIRST call, not at startup."*
  **Every logistics grid edits both files.** Budget it; do not claim otherwise.
- **In-transit stock is the whole seam** (`FR-335`, R4 §4.3). A transfer is **at least two** movements:
  `TRANSFER_DEPART` from the origin pick face to **that transfer's own `IN_TRANSIT` location, a child of
  the source site** — never a separate transit site (`RJ-002`) — and `TRANSFER_ARRIVE`
  from there to the destination receiving, **both carrying `source_document_type = 'TRIP'` and the trip
  id** — so logistics finds its own postings through the lineage query **without base knowing what a trip
  is**. Three things fall out and customers ask for all three: in-transit stock is countable and
  reportable; a transit loss is a normal reason-coded adjustment against the transit location, which is
  what makes it claimable against the carrier; and a partial arrival is representable.
  In-transit value stays in the sender's grain, held by the transfer's frozen source branch (`RJ-002`,
  `FR-236`). The receiving post and the transit-loss adjustment are authorised against **that
  transfer's** transit location regardless of site scope, and against nothing else at the source site
  (`RJ-002`, `P1-18`).
- **⚠ *"Delivery is not a movement"* is true for a customer and FALSE for our own branch** (`G-019`,
  `FR-342`, R4 §4.4's correction). Delivery to a customer posts nothing — the stock left at despatch.
  Delivery to **our own branch posts `TRANSFER_ARRIVE`**, and a partial arrival is fewer lines. Delivery
  to a 3PL client's site is `OWNER_CHANGE` or `TRANSFER_ARRIVE` depending on the contract. *"An
  implementer who reads only 'delivery is not a movement' builds inter-branch transfers that depart and
  never arrive."*
- **The vehicle has a dual identity.** It is a `whb_locations` row of type `VEHICLE` **and** a
  `log_vehicles` row, joined through **`whb_location_external_refs`** — which exists in v1 for exactly
  this, because without it *"either `whb_locations` gets a `vehicle_id` FK into logistics (base depends on
  logistics — fatal) or logistics duplicates the location tree"* (R7 §6 item 14).
- **Freight cost apportionment is `LANDED_COST_APPLY` with quantity 0** — and **the apportionment basis
  must be on the receipt, not on the freight charge** (`G-023`). `OD-11`/`L-15` governs whether that
  movement conserves value; read the answer before posting one.
- **The gate belongs to neither module** (`FR-340`, `P5-21`). Logistics registers a **second handler** on
  the same handler list warehouse registered on — `BoomBarrierWebhookController.java:44-48`'s `List<T>`
  bean-collection shape, **never `@Primary`**, which admits only one.
- **A hub is a decision per hub** (`G-022`): `whb_warehouses` with `is_physical = true` **if stock ever
  rests there unattributed to a trip**; `log_hubs` **if it only cross-docks within one trip**.
- **`OD-8` decides whether `logistics` may be deployed separately at all.** `PC-33`: a separately
  deployed module *"has nothing to authenticate with"*; there is no API-key table in platform (grep → 0).
  `PP-2`'s fallback is explicit: an out-of-process consumer is **not supported until v3** — which is this
  version. If `OD-8` is still open, `logistics` ships **in-process only** and says so.
- **Never name anything `wms_*` or `scc_*`.** `platform/…/V528:37,57,59` and `V663:17-19` carry hardcoded
  `wms_*` / `scc_*` / `warehouse-*` permission exclusions from the deleted earlier module; they have
  already run so they grant a new module nothing, *"but a new `wms_`-prefixed permission would inherit a
  decision nobody took"* (`D-3`, R6).
- **`widget_definitions.chk_module` admits neither `warehouse` nor `logistics`** — dropped and rebuilt
  three times (`V234:36` → `V276:10` → `V557:18`). `P0-01`'s `V500200` widens it for `warehouse` using the
  **merge** idiom of `accounting-base/…/V600200:56-99` (read the live constraint, union, rebuild). This
  task does the same for `logistics`, and **never a hardcoded DROP/ADD**, because the last writer may sort
  after this file (`FR-377`).
- **Every logistics frontend filename must be globally unique** — `Dockerfile.frontend:80-177` merges
  module `src/` with `cp -r`, last write wins (R1 `C-012`).
