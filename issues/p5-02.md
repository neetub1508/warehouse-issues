## Scope

- **`V530020` — `wh3_charge_codes`** (`W3-03`). Code, name, category
  (`STORAGE` · `INBOUND_HANDLING` · `OUTBOUND_HANDLING` · `VAS` · `ACCESSORIAL` ·
  `SHIPPING_PASSTHROUGH` · `ADMIN_SETUP` · `MINIMUM_TRUEUP` · `SLA_CREDIT` · `ADJUSTMENT`), default UoM,
  `is_recurring` / `is_pass_through` / `is_taxable`, tax classification code, SAC/HSN, and a
  **`revenue_purpose_code`** — the string the accounting module resolves to an account.
  **Never a GL account id: accounting owns the chart** (`D-6`).
  Seeded with the ~40 codes the audited products ship with, so a new client's rate card is built by
  **pricing existing codes rather than inventing strings**.
  **`MINIMUM_TRUEUP` and `SLA_CREDIT` are charge codes, not special cases in the biller** — that is what
  makes `P5-04`'s true-up and `P6-07`'s SLA credit ordinary metered events.
- **`V530021` — `wh3_rate_cards` + `wh3_rate_card_lines`** (`W3-04`). A card carries a client
  (**null = the standard card**), a version, `inherits_from_card_id`, effective from/to, currency and a
  status ladder `DRAFT → ACTIVE → EXPIRED`. A line carries charge code, UoM, rate, minimum quantity,
  tier from/to, charge kind and basis.
- **Resolution is most-specific-wins with an explicit priority order and a fail-rather-than-guess rule.**
  An unrated event **blocks the run and names the missing combination**; it is never silently rated at
  zero. Inheritance resolves line-by-line: a client card overrides the standard card's line for the same
  `(charge_code, uom, basis, tier)` and inherits everything it does not override.
- **Rating is by the version live on the *event's* date**, never the card current at run time — this is
  what makes a dispute three months later re-rate to the same number.
- Charge codes are `D-10`'s thirteenth registry and live where the charges do: **`code`, `name`,
  `owning_module`, `is_system` and behaviour flags, and no `CHECK (category IN (…))`.**

## Traps

- **No `CHECK` on `charge_category`.** `D-10` is explicit and the counter-example is live:
  `widget_definitions.chk_module` has been dropped and rebuilt **three times**
  (`V234:36` → `V276:10` → `V557:18`) and still admits neither `warehouse` nor `logistics`. The
  precedent that works is `accounting-base/…/V600002__Create_acc_reason_codes.sql:22-26` —
  *"It is a CATALOGUE, not an enum."*
- **`OD-5` applies here first in this module.** The frontend must not re-close what the backend opened:
  the category dropdown **fetches** its values; a TypeScript string union of the ten categories
  re-introduces the CHECK on the client (`FR-380`, `G-064`).
- **Precision.** `rate` and every per-unit figure are **`DECIMAL(19,6)`**; amounts `DECIMAL(19,4)`;
  quantities `DECIMAL(18,4)`; **any `*_percent` / `*_ratio` is `DECIMAL(9,6)`** — `DECIMAL(19,8)` is the
  currency-conversion type **and nothing else** (`OD-7`, `DATA-MODEL.md` §5). The `_percent` name pattern
  beats any reading of "rate".
- **A rate card version is never mutated once `ACTIVE`.** `P6-07` (`FR-296`) generates a **new version for
  review**; design the status ladder and the partial unique index (one `ACTIVE` version per card per
  effective window) now, because retro-fitting immutability over cards that have already been edited is
  not possible.
- **Effective-date overlap is an `EXCLUDE` constraint, not a service check.** R6 `P-043`'s `T-H3` records
  the prior art's identical failure: overlapping effective ranges on `scc_hsn_tax_master`, `sac_master`
  and `tax_rules` meant *"rate for X on date D"* could return two rows. Needs `btree_gist`.
- **The seeded ~40 codes must be individually idempotent** (`ON CONFLICT (code) DO NOTHING` with a real
  unique key). R6 `P-043`'s `T-M11` records the prior art's seed carrying `rule_code = NULL`, where NULLs
  never collide so `ON CONFLICT DO NOTHING` could never fire and a re-run duplicated every row.
  `FlywayConfiguration.java:246-264` makes a re-run likely, not hypothetical.
- **SAC `996729` is warehousing and storage; the `9967` family is supporting services in transport**
  (`F-013`). Seed them; do not compute tax from them — `OD-9` says warehouse **never computes tax**.
- Filter scope for both grids in `COMMON_FILTER_CONFIGS` (`platform/frontend/src/utils/filterUtils.ts:346`),
  or `convertFiltersForApi()` drops the field **silently** and the filter renders and does nothing.
  `effectiveFromFrom`/`To` are **two `dateOnly` filters** — there is no `daterange` type, and `dateOnly`
  is a distinct type from `date` (`filterUtils.ts:49-56`).

## Acceptance
- [ ] A charge code is created without any `CHECK` constraint on its category, and a new category value is added by a seed `INSERT` from an owning module's migration with **no `ALTER`**
- [ ] A client card inheriting the standard card overrides one line and inherits the rest, provably — the resolution is unit-tested line by line, not asserted
- [ ] A card cannot be edited once `ACTIVE`; the only path forward is a new version
- [ ] Two `ACTIVE` versions of one card with overlapping effective ranges are refused **by the database**, and by the service first with a field-level error naming the overlapping version
- [ ] An event with no matching rate line **blocks** the billing run and the error names `(charge_code, uom, basis, date)`; it is never rated at zero
- [ ] Re-running the seed migration twice produces 40 rows, not 80
- [ ] Both grids ship column + `filter_definitions` rows, `grid_preferences` with both defaults, filter scopes, i18n `en`/`fr`/`hi`, and an export that is a superset of the visible columns honouring filters **and sort**
- [ ] **Mobile:** `none` — rate cards and charge codes are desk masters (`D-13` declaration, per `BUILD-SPEC-SCREENS.md` §4's mobile note)
- [ ] **Scenarios** `WH-SC-236`
