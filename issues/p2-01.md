Part of __P2__ · Module **`warehouse`** · Migrations **V510030, V510034** · Screens **WS-089 Stock Adjustments**, **WS-096 Insufficient Stock & Lost Sales**, **WS-097 Blocked Movements Queue**

## Scope

The first application-layer writer that is not a receipt. Three objects, two migrations.

**`V510030` — WH-20 — `wh_stock_adjustments`, `wh_stock_adjustment_lines`.**
Header: `adjustment_number` (gapless, from `whb_number_series`), `warehouse_id`, `owner_id`,
`adjustment_type` (`POSITIVE`/`NEGATIVE`/`MIXED`), `reason_code_id` **NOT NULL**, `total_lines`,
`total_value_impact`, `requires_approval`, `approved_by`, `approved_at`, `status`,
`posted_movement_id` (a **bare UUID**, not an FK — §1.9).
Line: **one `location_id`, one `stock_status_code`, one `owner_id` per line** — the from/to shape of
`accessory_inventory_transactions` is *not* re-homed here; the two-sidedness lives in the movement,
not in the document. Plus `lot_id`, `serial_id`, `lpn_id`, `duty_status`, `system_quantity`,
`actual_quantity`, `variance_quantity`, `uom_code`, `unit_cost`, `variance_value`, `reason_code_id`,
`movement_id` (bare).

- **The approval threshold is expressed by value as well as by quantity** (`FR-145`). *A one-unit
  variance on a washer is noise; a one-unit variance on an engine control unit is an investigation.*
  Both thresholds live on configuration, both are evaluated at submit, and `requires_approval` is
  the stored outcome so the decision is reproducible.
- **The reason code is mandatory and comes from the catalogue** — an FK into `whb_reason_codes`,
  never a free-text field. There is no free-text reason column anywhere on either table.
- **`affects_demand_history` on the reason code** (`FR-146`) decides whether the movement this
  adjustment posts feeds `wh_demand_history`. A write-off or a warranty issue must not inflate the
  reorder point. The column lives on `whb_reason_codes` (`P0-04`, `V500004`); this task is its first
  consumer and the first place it is read.
- **Scrap and write-off are explicit value-destroying movements** (`FR-164`) with a reason, an
  approval and a movement — never a silent quantity decrement.

**`V510034` — WH-24 — `wh_insufficient_stock_log`, `wh_blocked_movements`.**

`wh_insufficient_stock_log` is **one table for two views of the same event** (`FR-015`, `FR-257`):
every `WARN`/`ALLOW` breach of the negative-stock policy *and* every lost sale captured at the
counter or the job-issue screen. Columns: `warehouse_id`, `item_id`, `owner_id`,
`requested_quantity`, `available_quantity`, `source_type`, `source_id`, `actor_user_id`,
`occurred_at`, `policy_applied` (`BLOCK`/`WARN`/`ALLOW`), `is_lost_sale`,
`lost_sale_reason_code_id`, `captured_manually`. Ledger-style: **no audit columns, no export
audit columns** — grid↔export parity means the export has none either.

`wh_blocked_movements` makes **a physical move the system rejected a first-class object**
(`FR-028`). *Refusing the transaction does not un-move the goods.* Columns:
`warehouse_id`, `attempted_movement_type_code`, `attempted_payload` **`TEXT`** (never `JSONB`),
`rejection_code` (from the `FR-039` stable vocabulary), `rejection_detail`, `actor_user_id`,
`device_id`, `occurred_at`, `resolved_at`, `resolution_action`, `resulting_movement_id` (bare).
The queue holds the goods in a `PENDING_RESOLUTION` disposition and routes to a supervisor who can
**force with an approval and a reason**.

`warehouseId` → `ownerId` → `reasonCodeId` · `adjustmentType` · `status` **multiselect** ·
`requiresApproval` · `approvedBy` typeahead · `createdFrom`/`createdTo` **`date`** pair ·
`valueImpactMin`/`valueImpactMax` number pair. There is **no `daterange` filter type** — every
from→to is two keys and **both** go in the `COMMON_FILTER_CONFIGS` allowlist.

the mobile screen says so** rather than hiding the button. `mobile/src/screens/whBlockedMovement` —
the operator who was refused must be able to see why and raise the force request.
`none` for WS-096 (controller report), stated as a decision.

## Traps

- **`C-045` is the idea to copy and the code is not.** `accessories` already ships the good half of
  this: a global setting choosing *block* versus *issue and mark pending*, plus
  `accessory_insufficient_stock_logs` and a report
  (`accessories/…/AccessoryStockEnforcementSettingService.java:17,31`;
  `AccessoryIssuanceService.java:101`). Ship the same switch as `WAREHOUSE_ALLOW_NEGATIVE_STOCK`.
  **Do not import the code** — it is FK-bound to `accessory_products` (`V30130:34-36`).
- **`C-025` — a ledger port must never return quietly.** `InventoryStockAdjustmentService.java:56-60`
  silently no-ops when no stock-level row exists, and `AccessoryIssuanceService.java:277-279`
  swallows non-`BusinessException` failures and continues. Every refusal here is an exception with a
  stable code; every success returns a movement id the caller stores.
- **`C-021` — do not mutate a balance.** `StockReceiptService.java:373-411` moves the accessories
  balance and writes **no** transaction row at all. The adjustment document here writes **no**
  position row; it posts a movement through the port and the position follows (`D-4`, `L-4`).
- **`T-1` — never `cascade = CascadeType.ALL` on the line collection.**
  `accessories/…/entity/SalesOrder.java:161,166` is the shape to avoid; 105 occurrences repo-wide.
  A `getLines().clear()` on a posted adjustment would issue `DELETE`s that `I-2` rejects, so the
  code works on drafts and fails in production.
- **`T-2` — a JPA field initialiser beats the column `DEFAULT`.**
  `accessories/…/entity/StockLevel.java:58-64` writes `0` and the DB default is never observed.
  Decide `total_value_impact` and the quantity columns in one place.
- **`T-6` / `FR-395`** — every one of the three filter scopes goes into
  `platform/frontend/src/utils/filterUtils.ts` (`:346` onward, 213 scopes today) or the filter UI
  silently does nothing. The **statistics strip gets no cache name**:
  `CacheConfiguration.java:190-196` records that exact mistake with its issue numbers
  (`neetub1508/classic#790`, `#791`).
- **`T-8`** — `grid_preferences` needs **both** `default_columns` and `default_filters` populated as
  `'[…]'::jsonb`; `filter_definitions.default_visible = true` alone builds nothing
  (`V18:12`, `V229:50-51`).
- **`CM-4` / `T-12`** — the table is **`filter_definitions`**, created in `V229`. There is no
  `grid_filter_definitions`; that name fails at Flyway and crash-loops the backend. And every
  module's migrations are physically flattened into one directory at build time
  (`Dockerfile.backend:140-181`), so a duplicate version is a startup failure, not a merge conflict.
- **`attempted_payload` is `TEXT`, not `JSONB`.** `D-3`/§1.6: no JSONB on a new `wh_` business table.
  The exception is `grid_preferences`, which is a platform table.
- **Precision.** `variance_quantity` `DECIMAL(18,4)` · `unit_cost` `DECIMAL(19,6)` (**per-unit beats
  the word `value`**) · `variance_value` and `total_value_impact` `DECIMAL(19,4)`. `OD-7`.

## Acceptance
- [ ] An adjustment with no `reason_code_id` is refused by the service **before commit**, with a field-level error on `reason_code_id` — and there is no free-text reason field anywhere on the request DTO
- [ ] A one-unit variance under the value threshold posts on submit; a one-unit variance over the **value** threshold routes to approval even though the **quantity** threshold was not breached
- [ ] `requires_approval` is stored, not recomputed at read time
- [ ] Posting writes **no** row in `whb_stock_positions` directly; the position moves only because the movement posted
- [ ] A reason code with `affects_demand_history = false` produces a movement that `wh_demand_history` does not count
- [ ] A rejected physical move produces a `wh_blocked_movements` row carrying the attempted payload, the rejection code, the actor and the device; forcing it requires a distinct permission, a reason and an approver
- [ ] Every `WARN`/`ALLOW` breach writes one `wh_insufficient_stock_log` row and appears on WS-096
- [ ] All three filter scopes exist in `COMMON_FILTER_CONFIGS`; **no `statistics.*` cache name is registered** for WS-089's strip
- [ ] `mobile/src/screens/whStockAdjustment` creates and submits, and states that approval is desk-only
- [ ] **Scenarios** `WH-SC-249` · `WH-SC-283` · `WH-SC-122` · `WH-SC-282` · `WH-SC-108`
