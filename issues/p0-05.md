## **These migrations precede `PNR-1` (`V500030`, `P0-02`) and must land before it**

`whb_stock_movement_lines.stock_status_code` is `NOT NULL` and FKs to `whb_stock_statuses(code)`;
`stock_status_code` is also a member of the nine-part position key. **`V500005` must run before
`V500030`.** `whb_condition_codes` and `whb_attribute_keys` are referenced by the line and by
`whb_movement_line_attributes` in the same migration. **`DATA-MODEL.md` §2.1 is the authority on the
exact column set of every table here and must be re-read immediately before the migration is
written** — a behaviour flag missing from a registry row is a behaviour the ledger can never express.

## Scope

> **Round-2 addition — `FR-448`, `Y-002`.** A status change against stock carrying an **open
> reservation** had no stated outcome and no error code anywhere in the set. It has one now, and it
> belongs here because this is the task that builds *status change as a balanced two-line movement at
> the same location*: the change is **refused with `409 RESERVED_STOCK`** naming the reservation,
> unless the caller passes an explicit release intent **and** holds `whb_reservations:release`, in
> which case the reservation is released first and the release is recorded. **`FR-160`'s nightly
> reservation-expiry job is itself a status change and never releases silently** — it takes the same
> path, records the same release, and shows on `WS-064` as a job run with a count.

Six registries, one shape (`DATA-MODEL.md` §1.8), **no `CHECK (x IN (…))` on any of them** (`D-10`,
`I-18`):

- **`V500005`** — `whb_stock_statuses` with its **nine behaviour flags** (`is_on_hand`,
  `is_available_to_promise`, `is_allocatable`, `is_pickable`, `is_shippable`, `is_countable`,
  `is_owned_asset`, `requires_reason_to_enter`, `requires_reason_to_leave`) plus **`badge_variant`**;
  and `whb_condition_codes` (`is_sellable`, `is_repairable`, `grade_rank`,
  `default_disposition_code`).
- **`V500006`** — `whb_location_types` + seed, **including every virtual and transit type**, with
  `is_physical`, `is_stock_holding`, `is_virtual_counterparty`, `is_mobile`, `is_transit`,
  `allows_mixed_owner`, `requires_assigned_user`, `default_location_level`. `P1-05`'s `V500013`
  seeds the virtual **locations** themselves; this migration seeds the **types** they need.
- **`V500008`** — `whb_item_types` + seed, including `PACKAGING`, `RETURNABLE_EQUIPMENT`, `TYRE`,
  `FUEL` (the logistics-seam types of `FR-337`), with `is_stocked`, `is_serial_default`,
  `is_lot_default`, `is_returnable_equipment`, `is_asset_shaped`, `is_value_only`.
- **`V500010`** — `whb_task_types` (`is_directed`, `default_priority`, `interleavable`,
  `labour_standard_minutes`, `required_resource_type`), `whb_dispositions` (**including
  `return_type`**, `movement_type_code`, `target_stock_status_code`, `requires_inspection`,
  `emits_credit_signal`), `whb_attribute_keys` (`value_type`, `applies_to`, `is_filterable`,
  `is_exportable`).
- **Status change as a balanced two-line movement at the same location** (`FR-103`) with a mandatory
  reason code. Quarantine never requires a physical move, and the status change is still a ledger
  event with a counter-side. This is the behaviour half of the task; the writer service of `P0-03`
  executes it.

## Traps

- **`badge_variant` is a column on the registry row, not a frontend map.** `FR-381`: a status badge's
  variant comes from the row and i18n **falls back to the registry row's `name`** when a translation
  key misses. A hard-coded `statusVariantMap` in TypeScript re-closes the vocabulary the backend
  opened — the same defect `OD-5` names.
- **The nine flags are nine because collapsing them loses information.** `is_allocatable` and
  `is_pickable` are different questions (allocatable-but-not-pickable is a hold at a blocked
  location); `is_on_hand` and `is_available_to_promise` are different questions (in-transit counts as
  on-hand and does not promise). The prior art's `location_type`/`zone_type` `CHECK`s were dropped
  and recreated with completely different value sets 36 versions after creation — the flags are what
  make a new status row usable without code.
- **`whb_dispositions.return_type` lands here, in v1, even though full reverse logistics is v2.**
  `A-1` moved **basic** returns into v1/P2, and the disposition row is what the return receipt writes
  against (`FR-270`, `FR-274`).
- **The warehouse emits the disposition and never decides a refund** (`FR-274`). There is no refund
  screen, no refund amount and no payment path in any warehouse module. Do not add one to this
  registry.
- **`whb_attribute_keys` is what makes `FR-026` enforceable.** An unregistered attribute key is a
  column nobody can filter or export; `whb_movement_line_attributes` accepts registered keys only.
  This is the alternative to the JSONB the prior art put on eleven business tables (`P-007`,
  `WMS_DATABASE_DESIGN.md:99` made it a convention).
- **Six grids × two platform files.** Six `COMMON_FILTER_CONFIGS` scopes in `filterUtils.ts` and six
  `dropdown.*` names in `CacheConfiguration.java`. An unregistered cache name throws
  `IllegalArgumentException` on the **first call**, not at startup
  (`CacheConfiguration.java:375-377`).
