## ★ **`V500011` must land before `P0-06`'s `V500007` can declare its foreign key — and before `PNR-1`**

`IMPLEMENTATION-PLAN.md` §1.2, §3.2 and §3.3 all list `P1-08` among the tasks that must land before
`PNR-1`; §2.2's `Dep` cell for `P0-02` omits it. The concrete reason is **not** a ledger FK — the
movement line does not reference a counterparty — it is this:

> **`whb_owners.counterparty_id → whb_counterparties` (`DATA-MODEL.md` §2.1), and `whb_owners` is
> `V500007` while `whb_counterparties` is `V500011`.** Flyway runs `V500007` first, so **the foreign
> key cannot be declared in `V500007`.**

**Resolution taken by this issue set** — it renumbers nothing and stays inside the pre-`PNR` window:
`P0-06`'s `V500007` creates `counterparty_id` as a **bare nullable `UUID`**, and **this task's
`V500011` adds the `FOREIGN KEY` constraint by `ALTER TABLE whb_owners ADD CONSTRAINT …` in the same
file that creates the target.** `V500011` < `V500030`, so it is legal and it is before the ledger is
sealed. Recorded in `DEFECTS-FOUND.md`; `p0-06.md` carries the other half.

**`DATA-MODEL.md` §2.1 is the authority on all six column sets (four, plus `RG-003`'s two) and must
be re-read immediately before the migration is written.** `whb_counterparty_external_refs` carries `IRR-25`.

## Scope

> **Round-4 addition — `RG-003` · `RG-021` · `RJ-009`.** (1) **A counterparty has many addresses and
> many tax registrations.** `V500011` creates **`whb_counterparty_addresses`** (`counterparty_id`,
> `address_role` a value of the `ADDRESS_ROLE` code list — `REGISTERED`/`BILL_TO`/`SHIP_TO`/`PICKUP`/
> `RETURN`, `RL-006` — the structured block with `state_code`, `gln`, `is_primary` per role, and dates)
> and **`whb_counterparty_tax_registrations`** (`counterparty_id`, `country_code`, `registration_scheme`
> an opaque string per `D-8`, `registration_number`, `state_code`, `address_id`, `is_primary` per
> country, and dates; `uk(registration_scheme, registration_number, effective_from)`), both dated per
> R22 §1.3. `national_tax_id` stays as the **legal-entity** id (PAN). **`FR-119` is amended to reverse
> its exclusion for addresses and tax registrations only**, and `P2-IN-03`/`P2-IN-04` freeze
> `to_counterparty_tax_registration_id` and `to_counterparty_address_id` on the challan and the e-way
> bill (`RG-003`). (2) **Role links are dated per R22 §1.3.** `valid_from`/`valid_to` become
> `effective_from`/`effective_to` `TIMESTAMPTZ` half-open, with `EXCLUDE USING gist (counterparty_id
> WITH =, role_code WITH =, tstzrange(effective_from, effective_to, '[)') WITH &&)` and no `is_active`
> on the link (`RG-021`). **`V500011` is the first migration to declare `btree_gist`**:
> `CREATE EXTENSION IF NOT EXISTS btree_gist`, then a `DO` block that `RAISE`s, naming the extension,
> if `pg_extension` has no `btree_gist` row — `D-7`'s standalone install has neither accounting-base nor
> assets to have created it (`RG-021`). (3) **A nullable `min_shelf_life_ship_pct` on
> `whb_counterparties`** is the first step of the counterparty → channel → item order that `P1-03`
> states and `P2-05` enforces (`RJ-009`).

- **`V500011`** — `whb_counterparty_roles` + seed; `whb_counterparties`,
  `whb_counterparty_role_links`, `whb_counterparty_external_refs`, `whb_counterparty_addresses`,
  `whb_counterparty_tax_registrations` (`RG-003`); and the `whb_owners` FK.
- **A thin identity** (`FR-116`): `code`, `name`, `legal_name`, `national_tax_id` (the legal-entity
  id), `country_code`, `is_active` — the address block and `gln` are rows of
  `whb_counterparty_addresses`, no longer columns here (`RG-003`, `RG-020`). **`warehouse-base` owns it because nothing else in the
  repo does** — `asset_vendors` is assets-owned, automotive's `customers`/`companies` model buyers
  and OEMs, and accessories receiving has **no supplier field at all**.
- **Roles are a many-to-many link table with effective dates** (`FR-117`; R22 §1.3, `RG-021`) — `SUPPLIER`, `CUSTOMER`,
  `CARRIER`, `CLIENT_3PL`, `TRANSPORTER`, `JOB_WORKER`, `INTERNAL` — **never a `partner_type` enum.**
  One party is routinely two roles at once.
- **External refs keyed `(source_module, external_id)`** with `uk(source_module, external_id)` and
  **`source_module` an opaque string, never an FK** (`FR-118`).
- **The exclusion list, stated** (`FR-119`): **no payment terms, no credit limit, no bank details, no
  contacts, no scorecard.** Those belong to whichever module owns the commercial relationship.
  **Addresses and tax registrations are the one reversal** — `FR-119` is amended for them only
  (`RG-003`).
- **Every inbound receipt names a counterparty** (`FR-120`). Without it a GRN cannot be traced to who
  shipped, supplier holds cannot exist, and lot traceability has no upstream end. `P1-13` enforces it.

> **Round-3 fold — `RE-005` (`GAP-REGISTER-R3.md` §2.5).** **The counterparty-role seed is
> `IRREVERSIBLE.md` §5 row 11's v1 seed column** — `SUPPLIER`, `CUSTOMER`, `CARRIER`, `CLIENT_3PL`,
> `TRANSPORTER`, `JOB_WORKER`, `INTERNAL`. A code that appears in a requirement, a scenario fixture or another task and not in the seed is a merge blocker — the rule `FR-165` applies to threshold columns.

## Traps

- **The `whb_owners` FK ordering, above.** It is the one migration-ordering defect this issue set
  found in the plan, and it is silent: `V500007` simply cannot compile the `REFERENCES` clause, and
  the tempting fix — dropping the FK and keeping a bare `UUID` forever — leaves `whb_owners`
  pointing at nothing enforceable.
- **Never an FK from base into another module.** The previous attempt at this seam died of exactly
  that: **84 FK references from warehouse into `scc_*`, several to tables that never existed**
  (R7 §3.3, `G-025`/`G-026`, `OD-4`). Any future module joins through
  `whb_counterparty_external_refs`.
- **`SccCompany` — the designated owner of a shared party master — was never built** (`P-010`). The
  only artefact was an unconstrained `scc_company_id UUID` on `scc_gstin_profiles` (`V190045:71`) —
  *a pointer with no owning table in any module.* **This is the second time this exact mistake would
  be made**; the FK ordering trap above is the same failure in miniature.
- **Do not recreate a separate master-owning module** (`P-042`). The prior art's three-module chain
  put shared masters in a module nobody built. `warehouse-base` owns its own thin identity, full
  stop.
- **`whb_counterparty_role_links` replaces a `partner_type` enum** (`P-042`, `IRR-33`), and the
  prior art's `wms_suppliers` is re-homed onto it with `payment_terms`, `currency` and
  `certifications JSONB` **dropped** (`FR-119`, `FR-383`).
- **No commercial columns creep in.** A `credit_limit` here is how a second commercial master starts,
  and `FR-121` records the trigger for extracting a shared `party-base`: **the third module that
  needs the same GSTIN to be authoritative for tax filing.** Until then, this table.
- **`whb_lots.counterparty_id` and `whb_item_supplier_sources.counterparty_id` both FK here** and both
  are later migrations (`V500018`, `V500050`), so their ordering is fine.
- **Two grids × two platform files**, and `roleCode` **multiselect** must be in
  `COMMON_FILTER_CONFIGS` as a multiselect — an unlisted or mistyped field is silently dropped
  (`filterUtils.ts:346`, `:30`).
- **`national_tax_id` is indexed but not unique.** Two legal entities can share a tax id across
  countries, and a unique index here refuses a legitimate second party.
