## Scope

Two obligations that share one property: **both are cheap now and unrecoverable later.**

### 1 · Value-only movements conserve value (`OD-11`)

**`L-1`…`L-14` conserve quantity only.** A landed-cost movement posts `quantity = 0` with a value,
so **it balances perfectly while unbalancing the value column** — *the strongest guard in the product
reports success.* `PC-11` settles that zero-quantity, non-zero-value movements are legal and that
there is **no `CHECK (quantity <> 0)`** on the line; `PC-12` settles that such a movement is still
**two or more lines**, the positive `extended_cost` on the stock-bearing location and lot, the
negative on a **virtual offset location**, with the movement type declaring
`balance_rule = MUST_BALANCE_PER_OWNER_ITEM` for quantity **and** `value_balance_rule = MUST_BALANCE`
for value.

**The resolution `OD-11` recommends is a `VALUE_OFFSET` virtual location plus a value-conservation
invariant applying only where `quantity = 0 AND unit_cost IS NOT NULL`.** *Cheaper than discovering
that landed cost silently unbalances the value column.*

**This task cannot write either of them, and that is the point of naming it here.** The trigger is a
constraint on `whb_stock_movement_lines`, which `V500030` seals against `UPDATE` forever; the seeded
location must exist before the first movement can balance (`I-17`). `IMPLEMENTATION-PLAN.md` §7:
*"the tighter deadline wins — a conservation invariant is a constraint on the table, not on the
report"*, so **`OD-11` must be answered before `P0-02`.** This task's deliverable is the **service
layer, the movement types, the value-balance check and the tests** over columns and a trigger that
`P0-02`/`P1-05` shipped. **Add `P1-05` to this task's dependencies.**

**`FR-345` — freight capitalisation crosses the seam as a value-only movement.** *The freight charge
is a transport document; its effect on stock cost is a zero-quantity `LANDED_COST_APPLY`.*
**No prior-art transport document in this monorepo connects freight to inventory value at all**,
which is exactly why the hook must exist before the logistics module does. The **charge object and
the freight-billing rules are v2/`P5-11`**; the hook is v1.
Under `D-6` the resulting movement is **valued by warehouse** and handed over with
`handover_id` + `posting_status`; a rejected handover goes to the owned queue (`P2-18`, `P2-22`).

### 2 · Daily storage snapshots are persisted, not recomputed (`FR-289`)

**One row per date, client, owner, warehouse, basis and identity**, carrying the **oldest receipt
date as the anniversary anchor**, the age in days and **the outbox cursor at computation time**.
The table is `whb_stock_position_snapshots` (`V500045`); **this task ships the nightly job.**

**A re-run for a date *supersedes* rather than updates**, with the superseded row retained
(`is_superseded`, `superseded_by_snapshot_id`), *because a billed snapshot that silently changes is
the same defect class as a mutable ledger.*

**`IRR-51` is `PNR-3` and it is why the job starts in v1**: occupancy on each past day **cannot be
cheaply reconstructed** from a movement ledger — the query is a running balance per position per day
over the whole history, and it is exactly the query that is too slow to run on demand. So
**storage billing, ageing, days-on-hand and obsolescence all begin on the day the job was switched
on**, and a client's dispute about last month is unanswerable. *The job is trivial; the omission is
not.* **`P2-19`'s go-live runbook switches it on.**
The 3PL billing that consumes it is v2/`P5-04`; **the job is v1.**

**Mobile.** `none` — a scheduled job and a diagnostic grid. Stated as a decision.

## Traps

- **The value-offset location has two names in the source set, and `FR-084`'s seed list contains
  neither.** `DECISIONS.md` `OD-11` and `IMPLEMENTATION-PLAN.md` `P2-28` call it **`VALUE_OFFSET`**;
  `PORT-AND-ADAPTER-CONTRACT.md` `PC-12` calls it **`LANDED_COST_OFFSET`** and offers *"the reuse of
  an `ADJUSTMENT_OFFSET`-typed location"* as an alternative. `FR-084` seeds `SUPPLIER`, `CUSTOMER`,
  `ADJUSTMENT`, `SCRAP`, `PRODUCTION`, `IN_TRANSIT`, `COUNT_VARIANCE`, `OPENING_BALANCE`,
  `CONSUMED`, `JOB_WORKER` — **and no value offset at all.**
  **Agree one code before `P1-05` writes `V500013`. Do not seed a second row under the other name.**
  Filed in `DEFECTS-FOUND.md`.
- **There is no `L-15` and no `I-n` row for value conservation.** `DECISIONS.md` §4 stops at `L-14`
  and `DATA-MODEL.md` §6.3 stops at `I-20`. `PC-12` says explicitly that whether
  `value_balance_rule` is *a movement-type behaviour column or a fifteenth invariant* is a
  `DECISIONS.md` question and *"is raised in §12, not decided here"*. **It is still not decided.**
  Filed in `DEFECTS-FOUND.md`.
- **`VALUE_UNBALANCED` is already in the error-code vocabulary** (`PC` §3.9, `422`, `PC-12`). Use it;
  do not invent a second code.
- **`IRR-51`'s omission is silent.** Nothing fails if the job is not switched on — the snapshots simply
  do not exist, and the failure surfaces months later as an unanswerable client dispute. Put the
  switch-on in `P2-19`'s cut-over checklist as a **blocking item**.
- **A superseded snapshot is retained, never updated.** `is_superseded` + `superseded_by_snapshot_id`
  and a partial unique index `WHERE NOT is_superseded` — the `C-033` idiom
  (`dealer/V20735:43-52,57-69`): append-only, released rows retained, exclusivity via **partial
  unique indexes**.
- **The snapshot carries `outbox_cursor_at_computation`** so a downstream consumer can tell whether
  the snapshot saw a given event. Without it the snapshot and the outbox cannot be correlated.
- **`L-14` — non-own stock is never valued**, so a value-only movement on `owner_type != OWN` is a
  contradiction: refuse it, or the 3PL's balance sheet carries its clients' goods.
- **Precision.** `extended_cost`, `value` **`DECIMAL(19,4)`**; `unit_cost` **`DECIMAL(19,6)`**;
  `quantity_on_hand` `DECIMAL(18,4)`; `age_days` an integer.

- [ ] A `LANDED_COST_APPLY` with `quantity = 0` on both lines **posts**, and a version of it whose values do not sum to zero is **refused** with `VALUE_UNBALANCED` and a field-level error
- [ ] The value-offset virtual location exists as a **seeded** row under **one** agreed code, seeded by `V500013`
- [ ] Value conservation is enforced by a database guard **and** a service pre-check that rejects first, in the transaction, with a field-level error
- [ ] A value-only movement on `owner_type != OWN` is refused
- [ ] The nightly snapshot job produces one row per date × client × owner × warehouse × basis × identity, carrying the oldest receipt date, the age and the outbox cursor
- [ ] A re-run for the same date **supersedes**: the old row is retained with `is_superseded = true` and the partial unique index admits exactly one live row
- [ ] Switching the job on is a **blocking** item on `P2-19`'s cut-over checklist
