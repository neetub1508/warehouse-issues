## Getting this wrong breaks the adapter model permanently

Nothing fails on the day. What fails is `D-11`: an adapter that needs `PDI_CONSUME` or
`TRANSFER_DEPART` then needs a **core release** — which is precisely what the adapter contract exists
to prevent. **A base release per adapter, forever** (plan §4, risk R3).

Two failure modes, and the second is the likely one:

1. Someone adds `CHECK (direction IN ('IN','OUT'))` because it feels safe.
2. **The frontend re-closes what the backend opened**, because CLAUDE.md TYPESCRIPT RULE #6 mandates
   string unions over enums. R2 records this as *a documented recurring defect in this codebase*.
   `types/whbMovementType.ts` must **not** contain
   `type MovementTypeCode = 'RECEIPT' | 'ISSUE' | …`.

The precedent that works is live and self-documenting: `acc_reason_codes.context` carries no `CHECK`
**deliberately** — *"It is a CATALOGUE, not an enum"*
(`accounting-base/…/V600002__Create_acc_reason_codes.sql:22-26`). The counter-example is equally
live: `widget_definitions.chk_module` has been dropped and rebuilt **three times** (`V234:36` →
`V276:10` → `V557:18`) and still admits neither `warehouse` nor `logistics`. And the prior warehouse
product broke on exactly this: `location_type` / `zone_type` `CHECK`s *"dropped and recreated with
completely different enum value sets"* **36 versions after creation**.

## Scope

> **Round-2 addition — `Z-005`.** **Deactivation is a retirement, not a delete.** `is_active =
> false` means *the code may no longer be selected on a new document*; it does **not** mean the
> row is unreferenced. Deactivation is therefore **always permitted** and never returns
> `REGISTRY_ROW_IN_USE`. Historic rows continue to render the code's `name` and `badge_variant`
> exactly as before (`FR-381`), and the grid, filter and export continue to offer the retired code
> as a filter value so a five-year-old document is still findable. The dropdown endpoint returns
> active rows only, **plus the currently-selected value when editing an existing row**, so an old
> document does not silently lose its code on save. `REGISTRY_ROW_IN_USE` is retained for
> **Delete** only — `:delete`, `is_system = false`, zero references — where it is correct, and its
> message names the referencing table and the count. Each of `WS-001`, `WS-002`, `WS-003` and
> `WS-006` gains an `isActive` filter defaulting to active.

> **Round-4 addition — `RL-003` · `RL-008` · `RJ-006` · `RL-012` · `RL-013` · `RL-009`.** (1) **A
> module inserts only codes it owns** (`RL-003`): to use a base code it references it and never
> re-inserts it. Every seed uses the **guarded idiom** — `ON CONFLICT (code) DO NOTHING`, then a
> `DO $$ … IF EXISTS (SELECT 1 FROM <registry> WHERE code = … AND owning_module <> '<me>') THEN RAISE
> EXCEPTION …` block in `V600200:150-161`'s shape — idempotent for the owner, loud for anyone else.
> `PC-72` gains assertion 7: no `(registry, code)` pair is inserted by two `owning_module` values.
> `whb_reason_codes` is keyed **`uk(context, code)`** in `V500004`, so `DAMAGE` may exist in two
> contexts. (2) `whb_reason_codes.itc_treatment` is renamed **`tax_treatment_code`**, its values seeded
> by `warehouse-india` (`P2-IN-01`), not base (`RL-008`). (3) `V500003` seeds **`TRANSFER_RETURN`**,
> the return-to-sender leg `P2-02` posts when an `IN_TRANSIT` transfer is cancelled (`RJ-006`,
> `WH-SC-316`). **No drop-ship movement type is seeded in v1** — `OD-18` is open, and `D-10` lets any
> module seed it once answered (`RK-005`). (4) **Install-created configuration rows carry
> `owning_module = 'INSTALL'`**, so `P3-18`'s v1.1 configuration-package export can tell install
> configuration from module seed (`RL-012`). (5) A registry `code` is immutable once referenced, and
> every code-keyed FK is **`ON UPDATE RESTRICT`**; a wrong code is retired and reseeded (`Z-005`),
> never renamed (`RL-013`). (6) **A registry-backed mobile field is `z.string().min(1)` validated
> against the fetched list, never a `z.enum`**; a `z.enum` literal containing a seeded registry code
> fails CI (`RL-009`; `FR-382`, owned by `P0-16`).

**`COEXISTENCE.md` `M4` lands here.** The UoM, reason-code, movement-type and warehouse-code
catalogues this task seeds are the *one list on both sides* that `M4` requires, because `D-9` keeps
`accessories` permanently separate and `P2-27`'s coexistence reports can only union two inventories
whose vocabularies agree. Seed from the accessories vocabulary where one already exists, and where
it does not, record which codes have no counterpart — `P2-27` reads that list to footnote its
reports rather than silently mis-adding (`X-052`, R3 `E-085`).

**The registry shape** (`DATA-MODEL.md` §1.8) is one table shape used fourteen times: `code`, `name`,
`description`, **`owning_module`** (an **opaque string, never an FK** — `FR-376`), `is_system`,
`is_active`, plus behaviour flags. **No `CHECK (x IN (…))`, no Java enum, no TypeScript string
union.** `WarehouseBaseCouplingTest` enumerates the fourteen `table.column` pairs and asserts none
carries a `CHECK` (`I-18`).

  `hasAuthority('<table>:export') or hasRole('ADMIN')`.

## Traps

- **`OD-5` must be answered before the first warehouse page is written — and these are the first
  warehouse pages.** The recommendation: catalogue-backed dropdowns **fetch** their values; a string
  union is permitted only for a **closed system** vocabulary (`posting_status`, an import row's
  `map_status`, an HTTP outcome). `FR-380` is the rule; `OD-5` is the ruling that makes it
  enforceable.
- **`whb_document_types.display_resolver_bean` names a bean, and base must ship the fallback.**
  Without the fallback, a document type registered by a module that is not installed renders nothing
  and the movement register's "View source document" action dead-ends (`FR-357`, `WH-SC-226`).
- **`owning_module` is an opaque string and never an FK.** The previous attempt at this seam died of
  exactly the opposite: 84 FK references from warehouse into `scc_*`, several to tables that never
  existed (`P-003`, `OD-4`).
- **The `ACCESSORIES` source-system row must be unclaimable, with the reason in the migration
  comment.** `D-9` is a user decision; the row is what stops an engineer in two years wiring
  accessories in as an adapter and creating a second stock truth with a shared code (`FR-367`,
  `WH-SC-179`).
- **`filter_definitions.position` collisions.** `position` is `NOT NULL DEFAULT 0` with **no
  uniqueness**, so two filters at the same position render in an arbitrary order that changes between
  queries. Number every grid's filters from 1, contiguously, in reading order.
- **`grid_column_definitions.is_required = true` bricks the save** if the required column is not in
  `grid_preferences.default_columns` — silently, for that grid only. Mark `is_required` on **at most
  one identity column** (`code`) and assert its presence in the same migration
  (BUILD-SPEC-SCREENS §9.4).
- **Menu inserts are guarded with `WHERE NOT EXISTS`, never `ON CONFLICT DO NOTHING`** — `menus` has
  no unique constraint on `(name, parent_id, menu_level)` and a Flyway retry duplicates the row
  (`FR-410`, R1 §8 trap `T-9`).

## Round-4 additions (folded from former P5-24, #157) — reason-code tax treatments

**v2 increment of this task — design the schema now, build in the v2 wave.** Former `P5-24` (`#157`)
gathered every v2 junction a round-4 lens had hung on a v1 task. On 2026-09-10 it was closed as a
duplicate and split by parent table. This task owns `whb_reason_codes`, so the reason code's tax-scheme
side table comes here. `FR-468` is owned by `P1-05`; this increment is its reason-code part.

**Scope (`RG-020`, `RL-008`).** **`whb_reason_code_tax_treatments`** — the reason code, a
`country_code`, a `scheme` and the treatment code, dated per R22 §1.3. v1 already renamed the column to
`tax_treatment_code` (`RL-008`), seeded by `warehouse-india`; this table gives a second scheme somewhere
to live without a base migration per country. A sub-grid on `WS-006`; no new screen id.

**Migration `V500072`** — allocated at the fold from the post-v1 base gap. Former `P5-24`'s single
`V500070` could not be claimed by the seven base hosts it was split across; `GAP-REGISTER-R4.md` §4.6.

**Closes** `RG-020` (the reason-code part; the item and UoM parts are `P1-01`'s and `P1-02`'s).

**Traps (v2 increment)**

- **Backfill from the v1 column in the same migration**: one open-ended row per reason code with a
  non-null `tax_treatment_code`, under the scheme `warehouse-india` seeded it for.
- **The v1 column stays for v1 readers, and nothing new reads it.** Code written in this increment reads
  the side table, never the scalar.
- **`scheme` is a code-list value (`RL-006`), never a `CHECK` on an open set.**
