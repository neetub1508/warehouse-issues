## Scope

> **Round-2 addition — `Y-005`.** **An eighth case type: item mismatch / unordered item.**
> `FR-138`'s seven case types do not cover the commonest receiving discrepancy of all — the
> supplier sent something that was not ordered. Add one line to `FR-138`: a GRN line whose
> `item_id` does not match its `po_line_id`, or which carries no `po_line_id` on a **non-blind**
> receipt, posts to a **`PENDING_RESOLUTION`** stock status and **auto-creates the case**. The
> three resolutions are accept-and-amend-the-PO, accept-as-free-issue, and return-to-vendor
> through `wh_supplier_returns` — each an existing document, so the case type costs a status value
> and a resolution list, not a new subsystem. Add **`ITEM_MISMATCH`** to
> `wh_goods_receipts.match_status`.

**`V510050` — WH-40 — `wh_rmas`, `wh_rma_lines`, `wh_return_receipts`, `wh_return_receipt_lines`,
`wh_rto_consignments`.** *(`A-1`: basic returns are v1.)*

> `DECISIONS.md` §5.1 **`A-1`** moved returns into v1 against the original ladder, because *"a stock
> product with no return path at v1 is not credible in any segment"* and **a customer return that
> cannot be received is a stock movement the ledger simply loses**.
> `COMPETITOR-BENCHMARK.md` §4.1 called the returns row *"the most damaging line in the table and
> self-inflicted"* until `X-050`'s 2026-09-02 fix; the row now names only the v2 RMA programme,
> because this task is what closes the v1 half of it.

**The return receipt is the primary object and the RMA is optional** (`FR-269`), matched to it later
**on a screen** rather than by re-receiving. *Modelling returns as "an RMA that is later received"
makes the blind return unrepresentable, and in India and in marketplace returns generally the blind
return is the majority case.* `wh_return_receipts.rma_id` is **nullable**; `wh_rmas` has its own
lifecycle and can expire unmatched.

**Returns land in a dedicated stock status, never straight to `AVAILABLE`** (`FR-271`). The receipt
posts into `RETURNED`; a disposition then posts a **second, balanced status-change movement**.

**Disposition is a registry and v1 ships the three that close the loop** (`FR-273`) — **restock** to
available, **quarantine** for investigation, **scrap** — *so a return can always be put somewhere*.
Each value posts **a specified movement to a specified status**; the registry is `WS-012`
Dispositions (`warehouse-base`, `P0`-owned catalogue). **v2 (`P5-13`) adds** refurbish, repack,
return to vendor as a shipment, return to client, hold for client decision and donate.
**A disposition never silently discards stock:** scrap and donate post an explicit **value-destroying
movement** with a reason and an approver (`FR-164`, `P2-01`).

**Restock restores the cost layers in reverse** (`FR-234`, `P2-16`): the layers the original issue
consumed are restored, **in reverse order, at the original cost**, through
`whb_cost_layer_consumptions.reversal_of_consumption_id`. Not a new layer at today's average.

**Return to vendor is an ordinary outbound** (`FR-275`) — a vendor party and a reference to the
originating receipt or lot; **it is not a special ledger case**. *A purchase return that cannot be
shipped is stock the ledger cannot release.* **The movement and the document are v1**; the emitted
**debit-note proposal and the credit interface are v2 (`P5-13`)**. The supplier-return *document
with its own state ladder* is `P2-13`; this task provides the outbound movement shape it uses.

**RTO is an inbound stock stream, not an order status** (`FR-205`). **The v1 deliverable is the
columns** on the shipment and `wh_rto_consignments`: `initiated_at`, `rto_reason_code_id`, the
**return leg's own AWB**, `received_at`, `status`. *A lost RTO becomes a claim rather than a silent
shrinkage adjustment.* **The consignment receipt, AWB scan, match, open-and-verify, grade and
put-back flow is v2 (`P5-12`).**

**There is no refund anywhere in this product, in any version** (`FR-274`). No refund screen, no
refund amount, no payment path. **The warehouse emits the disposition; it never decides a refund.**

**Screens.** WS-135 `wh_return_receipts` · `WAREHOUSE_RETURN_RECEIPT` · Service Vehicle —
Receive · **Match RMA** · **Disposition** · Post. WS-136 `wh_rmas` · `WAREHOUSE_RMA` · Service
Vehicle — Add · Approve · Expire · Match to receipt. WS-122 `wh_rto_consignments` · `WAREHOUSE_RTO`
— columns only in v1, with the v2 workflow stated on the screen.
`returnType` is a **day-one column** (`CUSTOMER`/`RTO`/`REFUSED_DELIVERY`/`CANCELLED_IN_TRANSIT`/
`VENDOR`/`RECALL`/`CLIENT_WITHDRAWAL`/`MARKETPLACE`) and the disposition rules **branch on it**.

**Mobile.** `mobile/src/screens/whReturnReceipt` — receiving a return at the dock is a floor task.
Disposition after inspection is desk work and the mobile screen says so. `none` for WS-136 and
WS-122, stated.

## Traps

- **`rma_id` nullable is the whole of `F-050`.** A `NOT NULL` here, or an RMA auto-created at
  receipt to satisfy an FK, makes the blind return unrepresentable — and the blind return is the
  majority case in the target market.
- **Never post a return straight to `AVAILABLE`, not even for `RESTOCK`.** It is **two** movements:
  the receipt into `RETURNED`, then the disposition's status change. One movement loses the
  inspection step and makes the return indistinguishable from a receipt in the register.
- **Layer restoration is reverse-order and at the original cost.** `whb_cost_layer_consumptions`
  carries `reversal_of_consumption_id` for exactly this. A new layer at today's average is the
  drift `C-027` names — `accessories` reverses a receipt by *subtracting the reversed receipt's own
  cost from the weighted average* (`StockReceiptService.java:386-408`), **which is not the inverse
  of a weighted average**.
- **`P-028` places inbound reconciliation and supplier returns at v1.1; `D-12` and the v1 exit
  criterion put them at v1/P2.** Read `FR-138`/`FR-139`'s own note. Do not re-defer them.
- **The RTO columns ship empty.** Resist building the v2 flow. The rule is `F-046`: *the columns are
  v1 and the workflow is v2*, and the reason the columns cannot wait is that an RTO initiated before
  the columns existed is a silent shrinkage forever.
- **`P5-13`/`P5-12` are named on each screen.** A screen that silently lacks refurbish, grading and
  NDR reads as unfinished; a screen that says so reads as scoped.
- **`T-9`** — the returns menu inserts need `WHERE NOT EXISTS`; `menus` has no unique constraint on
  `(name, parent_id, menu_level)`.
- **`T-6`** — three filter scopes. `receivedFrom`/`receivedTo` are `date`; `rmaDateFrom`/`rmaDateTo`
  are **`dateOnly`** (`rma_date` is a `DATE`).
- **Precision.** Line quantities `DECIMAL(18,4)`; there is **no refund amount column** to type.
