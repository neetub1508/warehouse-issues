## Get this wrong and `warehouse-3pl` is a rewrite, not a module

`IRREVERSIBLE.md` `IRR-06` calls `owner_id` **"the single most expensive column to add late in the
entire design"**, and four lenses reached it independently (R2 `T-002`, R4 `F-001`/`F-002`, R5,
R7 §6). **There is no rule that recovers whose a unit was.** Everything historical would default to
`OWN`, which means consignment stock received before the column existed is **already on the balance
sheet** and cannot be reclassified without restating closed periods. It simultaneously changes the
unique key of the hottest table in the product — so it is a **re-key and an unbackfillable, at the
same time**.

## **`V500007` must land before `PNR-1` (`V500030`, `P0-02`)**

`whb_stock_movement_lines.owner_id` is `NOT NULL` (`IRREVERSIBLE.md` §3.4) and `owner_id` is a member
of the nine-part position key. **The data model is the authority on the column set and must be
re-read immediately before the migration is written.** The columns bound to this deadline:
`IRR-06` (`owner_id` on the line), `IRR-07` (the owner-type registry), `IRR-60`.

> **The other end of the sequence: `V500007` cannot be the band's first file either.** It declares
> `whb_owners.company_id ... REFERENCES whb_companies (id)` and its house-owner seed reads
> `whb_companies` directly, but **`whb_companies` is created by `P0-07`'s `V500001`** (`DATA-MODEL.md`
> §7.2 row `WHB-01`). **`V500001` < `V500007`, so a fresh ascending `flyway migrate` is already
> correct** — the FK needs no `ALTER TABLE` deferral of the kind `whb_counterparties` needs below,
> and nothing here renumbers. What it does mean is that **`P0-07` must land in the repository before
> any database runs this band at all**: with `V500001` absent, `V500007` fails at the FK and Flyway
> crash-loops the backend, which reads as a defect in this task and is not one. The plan's Dep column
> for `P0-06` should therefore read `P0-04 P0-07 P1-08`.

**The trap is not omitting the column — `D-5` is emphatic. The trap is shipping a "single-owner mode"
for v1 convenience.** `FR-109` forbids exactly that: **v1 posts against the seeded house owner on
every movement, so the owner code path is exercised from day one** rather than from the day the first
3PL client arrives.

## Owner-scoped access — the rule and its test

> A request naming an owner the caller has no grant for is rejected **`403 OWNER_NOT_PERMITTED`,
> never returned empty**, because an empty grid is indistinguishable from "no stock" (`FR-114`,
> `PORT-AND-ADAPTER-CONTRACT.md` `PC-05`).

**One resolver, server-side**, passed to every query service, export service, statistics map and
dropdown endpoint. `FR-406`: **a contract test fails the build if a repository method touching an
owner-scoped table has no owner-set parameter.** That test is the deliverable; the resolver alone is
not the guarantee.

> **The resolver's subject is owner-scoped STOCK and the owner-grant junction — NOT the owners
> master.** `WS-019` is the administration surface for the owners themselves, and the person who
> grants access to an owner has to be able to see the owner first; a list narrowed by grants hides
> exactly the rows the administrator is there to configure. So `/management`, `/statistics`,
> `/dropdown` and `/export` on **owners** take no owner parameter, name no owner, and are neither
> refused nor narrowed — while `GET /{id}`, `PUT`, `PATCH /{id}/status` and `DELETE` do name one and
> do answer `403`. **Client-facing scoping of this screen is `P5-08`'s portal work**, which is the
> `P0·P5` split this file already states for `FR-114`. Until then, the only gate on the master list
> is `whb_owners:view`.
>
> **`WS-020` grants are different and ARE scoped**, because a grant row names an owner in its own
> `ownerId` filter — on the grid, on the statistics map **and on the export**, which reaches neither
> the CRUD service nor its guard. That export was the leak: the list endpoint called the resolver and
> the export did not, so naming an owner you hold no grant on downloaded that owner's entire access
> list. `IRR-60` names export, statistics tile and dropdown as the three bypass surfaces for exactly
> this reason, and "the list query guards it" is never the answer.
>
> **Narrowing is never the fallback for either.** A surface that cannot refuse must not silently
> filter instead (`PC-05`): an empty grid is indistinguishable from "no stock", and the operator acts
> on it.

## Traps

- **`whb_owners.counterparty_id` FKs to `whb_counterparties`, which is created in `V500011` —
  a *later* migration owned by `P1-08`.** `DATA-MODEL.md` §2.1 (`whb_owners` row) declares the FK;
  §7.2 puts `whb_owners` at `V500007` and `whb_counterparties` at `V500011`. Flyway runs `V500007`
  first, so **the FK cannot be declared in `V500007`.** *Resolution taken here:* `V500007` creates
  `counterparty_id` as a bare nullable `UUID`, and **`P1-08`'s `V500011` adds the
  `FOREIGN KEY` constraint by `ALTER TABLE` in the same file that creates the target.** That is legal
  (`V500011` < `V500030`, so it is inside the pre-`PNR` window) and it renumbers nothing. Recorded in
  `DEFECTS-FOUND.md`; `p1-08.md` carries the other half. **The plan's Dep column for `P0-06` does not
  record this dependency — it should read `P0-04 P1-08`.**
- **A "single-owner mode" is the failure, not a simplification.** `FR-109`. If the house owner is
  implicit in v1, the owner-resolution path, the grant check and the per-owner balance rule are all
  unexercised until the first 3PL client — which is the worst possible moment to discover them.
- **`duty_status` is governed by the same argument** and rides in `P0-02`: bonded and duty-paid stock
  of one SKU commingled is **a customs offence, not a data-quality issue**, and no algorithm
  separates them afterwards.
- **Accessories receiving has no supplier field at all** — `StockReceiptRequest.java:23-51` has ten
  fields, none a vendor, and `accessory_inventory_transactions` has no vendor column (`C-031`). There
  is no in-repo precedent for party-scoped stock; do not look for one.
- **No shared party master exists.** `asset_vendors` is assets-owned (`V60056:3-38`); automotive
  `customers`/`companies` model buyers and OEMs (`automotive/V10002:11`, `V10010:9`) (`C-035`).
  `whb_owners.counterparty_id` points at warehouse's own thin identity (`P1-08`), never out of the
  module.
- **`branches.owner_type` and `branches.branch_type` already allow `'WAREHOUSE'`** (`V149:61`, `:63`)
  — that is the *platform branch* axis and it is unrelated to `whb_owner_types`. Do not conflate the
  two words (`C-016`).
- **The grantee display must use the shared user-display helper** —
  `{firstName} {lastName} [{employee_id}] {primary_phone}` — never concatenated at the call site.
  Note the real column names: `user_details.employee_id`, `user_details.primary_phone` with a
  fallback to `phone` (R1 §8 trap `T-18`).

> **"Field-level error" is not a thing this platform can currently produce from a business rule, so
> this file no longer asks for one.** The acceptance box above used to read "refused with a
> **field-level error**, not a 500", and a builder reading it reasonably expects the message to land
> under the offending input. It cannot. `BusinessException`
> (`platform/backend/.../exception/BusinessException.java`) carries **message + `errorCode` +
> `HttpStatus` and no field path** — there is nowhere to put `"isHouse"` — and on the other side the
> Owners page types its catch as `err as Error & { details?: { errors?: Record<string, string> } }`
> and then **reads only `error.message`**, handing it to `showError` as a toast; `details.errors` is
> declared and discarded on every mutation handler. Jakarta `@Valid` field errors are a different
> path and do populate `details.errors`, which is what makes the phrase look available when it is not.
>
> **What the requirement actually is, and all it ever needed to be:** the second house owner is
> refused with a **named error code** (`OWNER_HOUSE_ALREADY_SET`) and a message that **names the
> owner already holding the flag**, surfaced to the user — never a raw PostgreSQL
> `uk_whb_owners_house_per_company` violation inside a 500. Every sibling refusal in this task reads
> the same way (`OWNER_CODE_EXISTS`, `OWNER_IS_HOUSE`, `OWNER_TYPE_HAS_VALUED_OWNERS`, `GRANT_OWNER_IMMUTABLE`).
>
> **If per-field business errors are wanted, they are a platform change, not this task's:**
> `BusinessException` would need a field-path carrier, `GlobalExceptionHandler` would need to emit it
> under `details.errors`, and every page's catch block would need to feed `validationErrors` from it.
> That is a cross-module change to shared code and belongs in its own issue.
