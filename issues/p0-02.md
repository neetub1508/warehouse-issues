## ★★ THIS TASK IS `PNR-1` **AND** `PNR-2`, IN ONE FILE ★★

**`V500030` is the point of no return for the entire product.** It creates
`whb_stock_movements` + `whb_stock_movement_lines` + `whb_movement_line_attributes` **and installs
the `L-2` append-only trigger in the same file** (`IRREVERSIBLE.md` §3.5, `DATA-MODEL.md` `WHB-30`).

> **After `V500030` has run, a column added to either ledger table is `NULL` forever on every row
> that already existed, to every actor including `ADMIN`, because the backfill is an `UPDATE` and
> the `UPDATE` is refused.** `ALTER TABLE … ADD COLUMN` is DDL and the trigger does not block it;
> `UPDATE` is DML and the trigger does. There is no later window.

`PNR-1` and `PNR-2` are deliberately collapsed because *"the gap between them is the only window in
which a column can be added and backfilled, and a window that exists will be used, quietly, by
someone who does not know what it costs"* (`IRREVERSIBLE.md` §3.5). Accounting kept them apart
(`V600090`/`V600094`) and paid for it with a documented near-miss on `acc_journals.book_id`.

**Before writing `V500030`, walk `IRREVERSIBLE.md` §2 row by row against the `CREATE TABLE`.**
`DATA-MODEL.md` §2.1 is the authority on the exact column set and it must be **re-read immediately
before the migration is written**, not summarised from this issue. The columns that share this

## Scope

> **Round-2 addition — `Y-001` · `Y-008` · `K-006`.** **Three amendments to the ledger table and
> its grid.** (1) The `whb_stock_movements` header carries **`on_behalf_of_actor_id`** (UUID,
> nullable, FK to platform `users(id)`) beside `actor_user_id` — a v1 **column** for a v1.1
> **feature**, null until platform ships impersonation (`FR-409`), because `IRR-48` and `IRR-61`
> make adding it to a hash-chained partitioned ledger afterwards far more expensive than carrying
> it empty. Mirror the column in `DATA-MODEL.md` §7.2's row for `V500030`. (2) `WS-040` gains an
> **`approvalStatus`** select filter alongside `postingStatus`; the two are different questions
> and a register that can only filter one of them cannot answer *"what is waiting on me"*. (3)
> **The partition boundary fails in both directions.** The acceptance line already requires a
> forward-dated movement to find its partition already made (`WH-SC-043`); amend it so a movement
> dated **backward**, before the oldest live partition, is refused with `422
> OCCURRED_AT_BEFORE_RETENTION` on `occurred_at` — the mirror of `WH-SC-031`'s ceiling — rather
> than reaching PostgreSQL and surfacing as an opaque 500. Add one `edge`-class scenario next to
> `WH-SC-031`, and one line to `P6-01`: *detaching a partition moves the `occurred_at` floor, and
> the refusal boundary is read from the live partition set, never from a constant.*

> **Round-4 addition — `RG-001` · `RG-012` · `RL-001` · `RL-006` · `RL-007` · `RL-008` · `RL-010` ·
> `RL-013`.** **Two new invariants and seven column rulings, all bound to this file's deadline.**
> (1) **`I-22` in `V500030`** (`RG-001`, R22 §1.2.2 guard 2): a plain, **non-deferred** `BEFORE
> INSERT` trigger on `whb_stock_movements` requires a `whb_warehouse_branches` row with
> `relationship_role_code = 'REGISTERED'` at `NEW.warehouse_id` whose `[effective_from,
> effective_to)` contains `NEW.occurred_at`. The writer pre-checks first and returns a field-level
> error on `occurredAt`; the trigger is the backstop (`WH-SC-312`). The junction is `P1-05`'s
> `V500012`, so **`V500012` must land before `V500030`**.
> (2) **`I-23` in `V500037`** (`RG-001`, guards 1 and 3): the `REGISTERED` history — the no-overlap
> exclusion `V500012` already created, plus a **deferred constraint trigger** asserting every active
> warehouse ends the transaction with a current `REGISTERED` row (memoised per `DATA-MODEL.md` §6.2),
> plus a `BEFORE UPDATE OR DELETE` trigger on `REGISTERED` rows: `DELETE` is refused when a posted
> movement at the warehouse falls in the row's range; `warehouse_id`, `branch_id`,
> `relationship_role_code` and `effective_from` are frozen on such a row; `effective_to` may be set
> only at or after the latest posted `occurred_at` in the range and never inside a `CLOSED` period
> (`I-10`). One seek on `idx_whb_stock_movements_wh_occurred`. It reads the ledger, so it cannot live
> in `V500012`.
> (3) **`duty_status VARCHAR(40) NOT NULL DEFAULT 'DOMESTIC' REFERENCES whb_duty_statuses(code)`**
> on the line (`RL-001`; the registry is `P0-05`'s `V500005`). A misspelt regime is an FK violation,
> not a new balance grain (`WH-SC-327`).
> (4) The line's tax snapshot is **`tax_classification_code VARCHAR(20)` +
> `tax_classification_scheme VARCHAR(20)`** (`HSN` for India) — there is no `hsn_code` column
> (`RL-008`).
> (5) `whb_movement_line_attributes` takes `DATA-MODEL.md`'s **four typed value columns** —
> `value_string`, `value_number`, `value_date`, `value_boolean` — never `(attribute_value,
> value_type)` (`RL-007`).
> (6) **Neither partitioned ledger table carries a `CHECK (… IN …)`.** `actor_type` (the
> `ACTOR_TYPE` code list), `approval_status`, `cost_basis` and `posting_status` are enforced by the
> writer service and `I-2` (`RL-006`).
> (7) Every code-keyed FK in `V500030` is **`ON UPDATE RESTRICT`**, never `CASCADE`; a wrong code is
> retired and reseeded, never renamed (`RL-013`).
> (8) The writer asserts the movement's `company_id` equals its site's `whb_warehouses.company_id`
> before any row is written (`RG-012`; `P5-24`'s `whb_warehouse_companies` replaces the scalar at v2).
> (9) `whb_negative_stock_policies` in `V500031` is versioned under **`I-24`**: once a recorded

## The nine-member position key (`L-5`, `I-5`)

`(company_id, owner_id, item_id, location_id, lot_id, serial_id, lpn_id, stock_status_code,
duty_status)`. **Every one of those columns exists in v1 even where its feature ships later.**

`whb_stock_positions` has **no independent deadline** — `L-4` makes it a cache, so a key member added
after the index exists is recovered by dropping the index, adding the column and rebuilding from the
ledger — **if and only if the ledger line already carries the column** (`IRREVERSIBLE.md` §3.3).
Do not spend review time defending the position table; spend it defending the line.

## Traps

- **The from/to shape is the defect, and three sources propose it.** R4 §3.3 and R5 row 20 propose
  `from_location_id`/`to_location_id` on **one** line; the prior art shipped exactly that
  (`wms_stock_transactions`, `WMS_DATABASE_DESIGN.md:1930-2005`) and it means
  `SUM(quantity) GROUP BY location` **has no defined answer** for a putaway or a cross-dock, and a
  forgotten destination line is a **silent stock leak** (`P-009`, `T-001`, `IRR-01`). A
  `STATUS_CHANGE`, an `OWNER_CHANGE`, a putaway and a bin-to-bin move are each **two lines**.
- **The live in-repo counter-example is `accessories`.** `accessory_inventory_transactions` is a
  single-sided log written next to an in-place-mutated `accessory_stock_levels` row, and
  **`StockReceiptService.java:373-411` moves the balance and writes no movement at all**, so the
  balance is not derivable from the movements (`C-021`). Do not copy it, and do not let a reviewer
  cite it as precedent.
- **The prior art's unique key is not valid PostgreSQL.** `WMS_DATABASE_DESIGN.md:1898`
  `UNIQUE (item_id, location_id, COALESCE(lot_id, '000…'))` — a table-level `UNIQUE` takes a column
  list; an expression needs `CREATE UNIQUE INDEX` (`P-008`). The deeper point: the `COALESCE`-to-nil
  idiom exists because the grain is nullable. Use `NULLS NOT DISTINCT` on the nine-member index, not
  a sentinel expression.
- **`CREATE CONSTRAINT TRIGGER` has exactly one precedent in this repo** —
  `accounting-base/V600111:773-786`, `:812-815`, `:838-841` — and that file records the two
  PostgreSQL rules it learned: a constraint trigger must be **`AFTER`** and must be **`FOR EACH
  ROW`** (`C-037`). `V500030` should be the **first** migration run against a real Docker build.
- **A per-row deferred check is O(N²) unless memoised.** `DATA-MODEL.md` §6.2 carries the
  transaction-local memoisation pattern verbatim; use it rather than re-deriving it.
- **A trigger firing in production is an incident, not a validation** (`DECISIONS.md` §4,
  `DATA-MODEL.md` §6.0). Every one of `I-1`…`I-17` needs a **service pre-check that rejects first,
  in the transaction, with a field-level error naming the difference** — `WH-SC-002` asserts the
  message text and asserts that `trg_whb_movement_lines_conserve` **does not fire**. A deferred
  trigger raises at `COMMIT`, after the service method has returned, so no `catch` can translate it.
- **`cascade = CascadeType.ALL` on a collection resurrects a repository-deleted child** — 105
  occurrences repo-wide, e.g. `accessories/…/entity/SalesOrder.java:161,166` (R1 §8 trap `T-1`).
  `whb_stock_movements → whb_stock_movement_lines` is **`ON DELETE RESTRICT`, no cascade**
  (`DATA-MODEL.md` §1.7): `L-2` forbids deleting either, and a cascade is a delete path that exists
  in the schema and must not.
- **A JPA field initialiser beats the column DEFAULT.** `@Builder.Default private BigDecimal
  quantityOnHand = BigDecimal.ZERO` writes `0` and the DB `DEFAULT` is never observed —
  `accessories/…/entity/StockLevel.java:58-64` (R1 §8 trap `T-2`). This bites
  `posting_status DEFAULT 'NOT_APPLICABLE'` and `is_counter_side DEFAULT false` directly
  (`DATA-MODEL.md:204`).
- **Do not expose a generated column on the entity.** `quantity_available` as
  `@Column(insertable=false, updatable=false)` is **stale in session** after `setQuantityOnHand(...)`
  — `StockLevel.java:66-68` (R1 §8 trap `T-3`). `FR-168` requires availability **computed, never
  stored**; `P0-03` owns the computation.
- **Hibernate native-query timestamps come back as any of `OffsetDateTime`, `Instant`,
  `java.sql.Timestamp` or `LocalDateTime`**, and returning `null` for an unhandled type is silent
  data loss. Copy `UserActivityLogQueryService.java:288-307` verbatim — it logs a warning on an
  unknown type (R1 §8 trap `T-4`, `FR-438`). This table carries **three** timestamp columns, so it is
  the worst place in the product to get it wrong.
- **`SqlSortBuilder` whitelist or no sorting**, always with a default sort (R1 §8 trap `T-5`).
- **`filter_definitions` is the table; `grid_filter_definitions` has never existed** and is named in
  six prior-art documents fourteen times (`P-006`). Inserting into it fails at Flyway and
  crash-loops the backend.
- **No `CHECK (quantity <> 0)`.** Zero-quantity non-zero-value movements are legal (`FR-010`) —
  freight, duty, clearing and write-downs arrive after the goods.
- **`source_document_id` is `VARCHAR(100)`, deliberately not a UUID and never an FK.** An external
  system's id is not ours (`DATA-MODEL.md` §3.3).
- **KEEP-SCALAR: the base UoM** (`RG-024`). `L-1` sums `base_quantity` in **one** base UoM per item,
  and `I-9` (`V500036`) freezes it once stock exists. Every other UoM is already many-to-many through
  conversions; a base-UoM junction would break `L-7`, `I-8` and `I-9`.
- **KEEP-SCALAR: physical containment** (`RG-025`). A location sits in one warehouse: `sequence_no` is
  gapless per warehouse (`I-4`), `whb_stock_positions.warehouse_id` is denormalised from the location,
  and a movement header names one warehouse (`IRR-17`). Cross-cutting zones are `P3-06`'s junction,
  never a second parent.
- **KEEP-SCALAR: branch or registration never joins the ledger line or the `L-5` key** (`RG-027`). A
  `branch_id` or `gstin` on `whb_stock_movement_lines` would be a tenth key member (refused for MRP
  under `OD-10`), dead on arrival after `PNR-2`, and it is derivable exactly from the dated
  `REGISTERED` link at `occurred_at` — the link `I-22` guarantees exists. `whb_serials.current_*` are
  caches of the last movement (`L-4`), never a junction.

## Blocked on

**Five open decisions gate the merge of this task. This is the single reason `P0-02` is not the
first task started** (plan §7.1).

- **`OD-10` — is MRP a dimension of the position key?** *(`FR-321`.)* **The tightest deadline in the
  programme.** It must be answered before `V500030` sets the key and seals the ledger in the same
  file. Recommendation: **No** — MRP belongs on the lot (`FR-320`), and `P4-05` reads it from there.
  A tenth key member costs every index and every rebuild, and if the answer is wrong it is a re-key
  of the hottest table plus an unbackfillable column, simultaneously.
- **`OD-7` — precision.** Adopt accounting's resolved set **verbatim and by citation**
  (`accounting/docs/DATA-MODEL.md:2443-2453` §5.1): quantities `DECIMAL(18,4)`, money
  `DECIMAL(19,4)`, **per-unit** figures `DECIMAL(19,6)`, **percentages and ratios — any `*_percent`,
  `*_ratio` — `DECIMAL(9,6)`**, exchange rates `DECIMAL(19,8)`. Two normative tie-breaks: `unit_*`
  beats `value`/`*_amount`; `*_percent` beats any reading of "rate". Note `conversion_factor_used` is
  `DECIMAL(18,8)` in `DATA-MODEL.md` §2.1 while R4 §3.3 proposes `numeric(18,8)` and accounting's
  `DECIMAL(19,8)` is *"the currency-conversion type and nothing else"* — resolve explicitly. Check
  against `currencies.default_decimal_places CHECK (<= 4)` (`V203:17`).
- **`OD-11` — do value-only movements conserve value?** `L-1`…`L-14` conserve **quantity only**, and
  a landed-cost movement posts `quantity = 0` with a value. `DECISIONS.md` §3 says *"before P2
  valuation"*; `PORT-AND-ADAPTER-CONTRACT.md` §12.2 says *"before `P0-02` writes the ledger"*.
  **The tighter deadline wins** — a conservation invariant is a constraint on the table, not on the
  report. Recommendation: a `VALUE_OFFSET` virtual location and an `L-15` applying only where
  `quantity = 0 AND unit_cost IS NOT NULL`.
- **`OD-1` — the reciprocal accounting edits.** `D-6` requires the `accounting` design set to add a
  **third install state** ("a warehouse product is present and owns quantity"). It is an edit to a
  *different repository's* design set and is that set's to make; it is cheap now and expensive once
  `acc_valuation_entries` has rows.
- **`OD-12` — the partition key: `occurred_at` or `posting_date`?** `FR-022` and `DATA-MODEL.md`
  `WHB-30` say `occurred_at`; `PLATFORM-DEPENDENCIES.md` `PD-D5` says `posting_date`. **Numbered
  `OD-12` on 2026-09-02** (`X-024`), which closes the "no id" half of this gate; the decision itself
  is still open and must be taken **before this migration is written**. *"A partition key cannot be added to a
  populated table without a rewrite."* The substantive argument on each side: `occurred_at`
  partitions by when it physically happened, which is what the as-at query and EPCIS want;
  `posting_date` partitions by the accounting date, which is what period close and the statutory
  register want. `L-13` says these are **different columns**, so the choice is real. **This task
  currently follows `FR-022` + `DATA-MODEL.md` (`occurred_at`), which is also `OD-12`'s
  recommendation, and must not be merged until `OD-12` is taken.**
