## An interface, never a control layer

`FR-229`: *"Automation, conveyors, sorters, AS/RS and robotics integrate through a **published
task-event contract and the movement port** (`actor_type = DEVICE`), never through protocol-level control
in our codebase. An AMR vendor integrating against a documented event stream is a two-week integration
for them."*

The refusal behind it (`COMPETITOR-BENCHMARK.md` §7 row 5): direct automation control is *"real-time
control software with safety implications, written to a different engineering standard than a web
application."* SAP EWM's MFS is uniquely deep and we are not competing with it. **The re-entry path is
already open**: an adapter per vendor posting through the port, which the port supports today because
`actor_type = DEVICE` is a **v1** column (R7 §6 item 11).

## Scope

- **`V500101`** — the automation event contract as data: the **published task-event catalogue** (which
  `whb_tasks` lifecycle events a device may consume and emit), the device-integration registration
  (vendor, protocol adapter code, subscribed event codes, the `whb_outbox_subscriptions` row it maps to,
  and its permission), and the per-integration delivery/telemetry state.
  **This table is new: `DATA-MODEL.md` §7.2 allocates `V500064`–`V500199` as *post-v1 base DDL* and names
  no rows for it.** Claim the number and add the row to §7.2 in the same PR.
- **Outbound**: the automation vendor subscribes to `whb_outbox` by cursor, at-least-once, in
  `sequence_no` order, over **HTTP delivery** — the `whb_outbox_subscriptions` table shipped in v1 and
  the HTTP path in v1.1 (`PC-39`, `P3-22`).
- **Inbound**: the device posts through `POST /api/warehouse/movements` and the task API with
  `actor_type = DEVICE` and a `device_id`, its own `idempotency_key`, and **per-movement results on the
  batch endpoint** — *a device syncing forty scans must not lose thirty-nine because of one bad row*
  (R7 §6 item 12).
- **The contract is published**, versioned per `PC-`/§10.4, and **a code may be added, never renamed,
  never repurposed** — a vendor's retry logic branches on it.
- **Nothing in this task speaks a PLC protocol, drives a conveyor, or holds a safety interlock.**

## Traps

- **⚠ `actor_type = DEVICE` and `device_id` are v1 columns and must be verified before this task starts.**
  R7 §6 item 11: *"a geofence-triggered arrival and a scan-gun posting have no attributable actor
  otherwise. Diagnosing a mis-scanning device retroactively is impossible."* `DATA-MODEL.md` marks
  `actor_type` as **no `CHECK`**, with `DEVICE` arriving in v1.1 and `INTEGRATION` in v2 — it is a
  catalogue value, so adding one is a seed `INSERT`, never an `ALTER`.
- **The event vocabulary is fixed in v1 and adding a *dimension* to an existing code is not additive**
  (`PC-38`, `PC-42`): the dimension was never emitted for the events already consumed, and consumers'
  cursors have already passed them. If an automation vendor needs a field the event does not carry, the
  answer is **a new event code**, not a widened old one.
- **The cursor blocks on a poison message and that is correct** (`PC-47`). A blocked automation
  subscription stops the conveyor's event feed, which is visible and alarming — skipping would deliver an
  out-of-order stream to a consumer that was **promised** ordering by `PC-44` and could not detect it.
  The dead-letter grid (`PC-48`) is where the operator sees it.
- **`OD-8` is the authentication gate.** A separately-deployed automation controller *"has nothing to
  authenticate with"*: there is no API-key table in platform (grep → 0), and the only API-key path in the
  repo is per-handler inside the boom-barrier webhook. The recommendation is a **platform service
  principal** (`PP-2`) — the only item in this design set that platform must build for warehouse. Without
  it, an out-of-process device integration is not supported and this task ships the in-process path only,
  **and says so** rather than inventing a second auth mechanism.
- **Replay is the only supported recovery** (`PC-45`): a permissioned, audited
  `POST /outbox/subscriptions/{code}/replay?from_sequence_no=…`. There is **no "re-emit this one event"**
  and no manual insert into `whb_outbox`, because either breaks the gapless-cursor guarantee consumers
  deduplicate against.
- **No JSONB payload on the outbox** (`PC-37`). Event-specific facts are typed rows in a side table keyed
  by registered `whb_attribute_keys`.
- **`@Async` is not an outbox** and the repo's own memory records `reference_async_notification_lazyinit`
  as a live trap (`PC-35`).

## Acceptance
- [ ] A device posts a movement with `actor_type = DEVICE` and `device_id`, and the same `idempotency_key` replayed posts **nothing** and returns the original movement
- [ ] A batch of 40 device scans with one bad row commits 39 and returns a per-movement result array
- [ ] A subscriber reads the task-event stream by cursor, in `sequence_no` order, and deduplicates on `(subscriber_code, sequence_no)`
- [ ] A poison message blocks the cursor, appears in the dead-letter grid, and is recoverable **only** by replay
- [ ] The published contract is versioned; a test asserts no existing event code was renamed or repurposed
- [ ] `grep -rin "modbus\|opc\|plc\|telegram\|interlock" warehouse-base/backend/src/main/java` returns **nothing** — the refusal is asserted
- [ ] Where `OD-8` is unanswered, only the in-process path ships and the limitation is documented — no second auth mechanism is invented
- [ ] The migration number is recorded in `DATA-MODEL.md` §7.2 in the same PR
- [ ] **Mobile:** `none` — a device integration has no human surface; the dead-letter grid is a desk screen (`D-13` declaration)
- [ ] **Scenarios** the ids this task authors into `SCENARIO-CATALOGUE.md`
