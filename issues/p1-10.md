## Scope

> **Round-2 addition — `Z-003`.** **Master import is the bulk-amendment surface, and an update
> needs a before-image.** A handler declares a `mode` of `CREATE_ONLY`, `UPDATE_ONLY` or `UPSERT`,
> with the match key stated per import kind (`whb_items` matches on `(owner_id, sku)`). For
> `UPDATE_ONLY` and `UPSERT` the batch row records **`beforeValueJson` per changed cell as
> `TEXT`** — never JSONB, per `DATA-MODEL.md` §1 — which is what makes **Reverse** meaningful for
> an update: it restores the recorded prior values, and is refused where any field it would
> restore is frozen. The dry run shows a **per-cell before/after diff**, not just a validation
> result, and `WS-065`'s detail grid gains `changedCellCount`. **Bulk edit from the grid is
> deliberately not proposed** — an import batch with a diff and a reversal is a better audit
> object than a multi-select toolbar action, and it reuses a framework that already exists.

> **Round-4 addition — `RH-009` · `RL-012`.** (1) **Above `bulk_import_max_rows` the file never
> reaches the browser parser.** Platform's `ImportModal` parses client-side under one install-wide cap
> (`bulk_import_max_rows`, seeded `500`), and opening stock is 200k–1M rows. A file above the cap is
> uploaded to platform `documents` (`whb_import_batches.document_id`), then **parsed, validated and
> applied server-side by the handler in batches, with progress on the batch row**; `validate` on this
> path persists nothing, exactly as on the small path. `ImportButton` serves small masters only, and
> **the global setting is never raised**. `P2-19`'s opening stock takes this path (`RH-009`). (2) **The
> v1.1 configuration-package kinds come later on this framework** — one `import_kind` per configuration
> object, upsert keyed on `code`, the dry run as the diff — owned by `P3-18`. Nothing here builds them,
> and nothing here may preclude them (`RL-012`).

- **Bulk import covers** (`FR-418`): items, identifiers and barcodes, packaging, locations, opening

## Traps

- **This codebase has shipped the opposite defect.** A `validate` endpoint that **persisted**,
  producing **duplicate rows on the subsequent real import** (`FR-417`). The acceptance test is a
  **row count on the target table *and* on `whb_import_batches`** — not an inspection of the code
  path, because the second write is usually a side effect of a service call the validator makes for
  convenience.
- **Reuse the platform import wizard; keep the job and audit tables in the module** (`P-041`). A
  second wizard is a second UX and a second set of bugs. Reuse it **below `bulk_import_max_rows`
  only** — it parses in the browser under an install-wide 500-row cap (`RH-009`).
- **Every import kind needs a reversal handler, not just an apply handler.** A framework whose
  reversal is "delete the created rows" fails the moment an imported item has a movement — the
  reversal must **refuse**, with a message naming what blocks it, and the refusal is part of the
  handler contract.
- **Opening stock is imported as `OPENING_BALANCE` movements from the opening virtual location, never
  as a position `UPDATE`** (`WH-SC-049`, `P2-19`). The framework must not offer a handler that writes
  `whb_stock_positions` directly — that would be a second writer and `FR-436` allows exactly one.
- **The date parser is a known trap in this repo.** Import date columns must go through the shared
  parser, and every statutory date is a SQL `DATE` (`FR-327`), so the imported value is date-only,
  not a timestamp shifted by the server's zone.
- **Reference preload matters at scale.** A handler that resolves each row's item, location and owner
  with a `findById` per row is an N+1 across 50,000 rows; batch-load the references once per chunk
  (CLAUDE.md CRITICAL #5).
- **Per-row, per-cell errors, not a batch-level failure.** *"Row 412, column `base_uom_code`:
  `CSE` is not a UoM"* is actionable; *"import failed"* is not. `whb_import_batch_rows` is what makes
  the difference, and its `errorCode` must come from the stable vocabulary of `FR-039`.
- **`WAREHOUSE_IMPORT_BATCH` in `COMMON_FILTER_CONFIGS`**, `default_columns` **and**
  `default_filters` on the grid.
- **`ImportButton` is the platform component** and the Service Vehicle page is the reference
  (`services/frontend/src/app/dashboard/services/vehicles/page.tsx`). Do not build a second uploader.
  It serves small masters; above the cap the file goes through `documents` to the server-side path,
  and `bulk_import_max_rows` is never raised to make a large file fit (`RH-009`).

## Acceptance
- [ ] `validate` on a 5,000-row file with 300 bad rows reports **per-row, per-cell** errors and
      **writes nothing** — asserted by row count on the target table **and** on
      `whb_import_batches` (`WH-SC-047`, `WH-SC-048`)
- [ ] **Apply** creates the rows and records `createdEntityType`/`createdEntityId` per import row
- [ ] **Reverse** removes exactly what a batch created, and is **refused** with a named blocker once
      any created entity has a movement
- [ ] A new import kind is added by registering **one handler**, with no change to the framework, the
      grid or the migration
- [ ] The location generator (`P1-06`) and the item import (`P1-01`) both commit through this
      framework
- [ ] Reference resolution is batch-loaded per chunk — no `findById` in a loop
- [ ] Imported dates parse as SQL `DATE` with no timezone shift
- [ ] A 200,000-row opening-stock file is uploaded to `documents` and parsed, validated and applied
      server-side in batches, with progress on the batch row; no browser parses it and
      `bulk_import_max_rows` is unchanged (`RH-009`)
- [ ] `validate` on the server-side path persists nothing, asserted by the same two row counts
      (`RH-009`)
- [ ] The grid ships `default_columns` **and** `default_filters`, its scope is in
      `COMMON_FILTER_CONFIGS`, and the mobile decision is recorded with its reason
- [ ] **Scenarios** `WH-SC-047` · `WH-SC-048`
