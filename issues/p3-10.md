## Scope

- **`whb_kit_definitions`, `whb_kit_components`** (`V500060`, `DATA-MODEL.md` §7.2 WHB-60).
- **Virtual and physical kits are different objects with the same BOM** (`FR-075`) — this is the
  whole requirement, and a design supporting only one is rebuilt when the second client arrives:
  - a **PHANTOM** kit **never holds stock**; its availability is `MIN(component available ÷ required)`
  - a **STOCKED** kit **holds stock**, has its own on-hand and its own cost, and a work order
    converts components into it (`P3-11`)
- The BOM child editor carries `component_item_id`, `quantity`, `uom_code`, `sort_order`,
  `is_optional` and `scrap_factor_percent`.
- Kit definitions are **versioned and effective-dated** (`version`, `effectiveFrom`, `effectiveTo`),
  because a BOM that changes retroactively makes every past assembly unexplainable.

## Traps

- **`MIN(component available ÷ required)` is computed on the backend and rendered as a read-only
  column.** CLAUDE.md FRONTEND RULE 8 forbids business logic in a page, and there is **no decimal
  library on the frontend** (`PLATFORM-DEPENDENCIES.md` §2.11) — an availability computed in
  IEEE-754 doubles from four component quantities is a number that disagrees with the backend's.
- **A phantom kit must never acquire a stock position.** The guard belongs in the movement service:
  a line whose item is a `PHANTOM` kit is refused. Without it a single adjustment creates stock for
  something that by definition cannot have any, and the reconciliation report can never explain it.
- **`kit_type` is a catalogue-shaped column with no `CHECK`** (`D-10`). The prior warehouse product's
  `location_type`/`zone_type` CHECKs were dropped and recreated with completely different value sets
  36 versions after creation (R6); the same fate awaits any two-value CHECK the moment a third kind
  of kit appears.
- **`scrap_factor_percent` is `DECIMAL(9,6)`, not `DECIMAL(9,4)`.** `DATA-MODEL.md` §5.1's precision
  ladder: any `*_percent` or `*_ratio` is `DECIMAL(9,6)`, and the accounting set stated this row
  wrongly for three rounds. `DECIMAL(19,8)` is the currency-conversion type and nothing else.
- **`whb_kit_definitions` is `warehouse-base`.** `wh_work_orders` (`P3-11`, app) references it
  downward; base gains no reference upward (`D-1`, `D-11`).
- **Effective-dated rows need a range guard.** Two active versions of one kit on one date makes the
  BOM non-deterministic — the same class of defect as `P-043`'s tax resolver. Enforce it, and note
  that a **partial unique index cannot be declared `DEFERRABLE` in PostgreSQL** (recorded in five
  migrations, e.g. `accounting-base/V600001:150`), so the write path owes an explicit `flush()`.
- **`whb_kit_components` must not be mapped `cascade = ALL, orphanRemoval = true`** if the parent is
  ever reachable from a ledger-adjacent aggregate — 105 occurrences of that mapping repo-wide, and
  `accessories/.../entity/SalesOrder.java:161` is the live example (R1 `T-1`).

## Acceptance
- [ ] A kit is created as PHANTOM or STOCKED with the same BOM and the two behave differently
- [ ] A phantom kit's availability is `MIN(component available ÷ required)`, computed on the backend, and refreshes when a component's stock changes
- [ ] Posting any movement line against a phantom kit item is **refused**, with a field-level error
- [ ] A stocked kit can hold stock and appears in the position report
- [ ] `kit_type` has no `CHECK` constraint and a third value can be registered by migration
- [ ] `scrap_factor_percent` is `DECIMAL(9,6)`
- [ ] Two overlapping effective-dated versions of one kit are refused
- [ ] The mobile decision is stated as `none` with its reason
- [ ] **Scenarios** `WH-SC-287`'s master half — the two kit kinds and the phantom's availability (the assembly half is `P3-11`'s)
