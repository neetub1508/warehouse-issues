## There is no precedent for this in the repository

`PLATFORM-DEPENDENCIES.md` §4.9 is blunt: **balance-cache-with-rebuild — warehouse invents it.**
There is one good precedent for a balance *derived* from an append-only table
(`pdi_storage_slot_assignments`, `dealer/V20735:43-52`, occupancy computed at read time) and **none
at all** for a cache that a full rebuild must reproduce **exactly**, proved nightly, with drift
alerting. Budget it as invention, not as a port.

## Scope

> **Round-2 addition — `J-001` · `K-004`.** **The fourth concurrency concern, and one GSTIN
> pair.** `@Version` **detects** contention; it does not **resolve** it. The writer service
> retries on `OptimisticLockingFailureException` up to `warehouse.position.max_contention_retries`
> with jittered backoff, re-reading the position row inside the retry; on exhaustion it returns
> **`409 POSITION_CONTENTION` — a different code from `INSUFFICIENT_STOCK`**, because one means
> *try again* and the other means *there is not enough*, and an operator who cannot tell them
> apart stops trusting both. The caller's `(source_system, idempotency_key)` is consumed exactly
> once regardless of retry count (`L-9`). Both settings seed in `WHB-75` beside
> `warehouse.outbox.max_attempts`. Acceptance gains: *200 concurrent allocations against one
> position row produce no oversell, no livelock, and a bounded number of `409 POSITION_CONTENTION`
> responses* — with a `conc`-class scenario next to `WH-SC-198`. Separately,
> `whb_transport_details` carries **`ship_to_gstin VARCHAR(15)`** and **`dispatch_from_gstin
> VARCHAR(15)`**, both nullable at the base layer, with `warehouse-india` enforcing that
> `ship_to_gstin` is present and is either a valid GSTIN or the literal `URP` before an e-way bill
> or IRN payload is built (GSTN Advisory 664, effective 2026-08-01); a matching `FR-` row is
> needed under `FR-308`'s area. **And correct this file's opening premise:**
> `PLATFORM-DEPENDENCIES.md` §4.9's *"warehouse invents balance-cache-with-rebuild — budget it as
> invention, not as a port"* is **false as of 2026-09-01** — `accounting-base`'s
> `AccBalanceRebuildJob`, `AccBalanceDrift`, `AccBalanceDriftAlertService` and
> `AccBalanceCacheProvider` are live, and following the stale instruction buys a second rebuild
> framework in the same database.

> **Round-4 addition — `RL-011` · `RL-016`.** (1) **`whb_stock_position_snapshots` is partitioned at
> `CREATE`** — `PARTITION BY RANGE (snapshot_date)`, monthly, in `V500045` — its partitions made by
> `P0-02`'s partition-creation job, with a retention-class row (`P4-09`) so disposal is a partition
> drop (`RL-011`). **Only non-zero positions are snapshotted**, stated here because a full daily
> snapshot of five million live positions is 1.8 billion rows a year. (2) **The writer service takes
> the injected UTC `Clock`** (`P0-13`) for `recorded_at`, the as-at boundary and the snapshot's day
> boundary — never a bare `Instant.now()` (`RL-016`).

- **The single writer service** — the only path that touches `whb_stock_movements`,
  `whb_stock_movement_lines` and `whb_stock_positions`, asserted by an **architecture test**
  (`FR-436`). *The gateway alone is not the guarantee; the test is.* No update method exists on it.
- **Availability computed, never stored** (`FR-168`):
  `available = Σ on_hand where status.is_allocatable − Σ open reservations`. A stored column drifts
  and its drift is invisible.
- **Negative-available refusal and the negative-on-hand policy** (`FR-014`, `L-6`). Available may
  never go below zero. Physical on-hand may go negative **only** where an explicit per-item × per-site
  policy allows it (`whb_item_site_settings.negative_stock_mode`, `P1-03`). Every `WARN`/`ALLOW`
  breach writes an **insufficient-stock log row** (`FR-015`).
- **The concurrency discipline — all three, not a choice of one** (`FR-016`): optimistic `@Version`
  on the position row, a database `CHECK`, and a **stated lock-ordering discipline**. Advisory locks
  (`SELECT pg_advisory_xact_lock(hashtext(:key))`) serialise movements on a key that has no row to
  lock; the precedent is `DocumentFolderService.java:266`, `GridPreferenceService.java:144`,
  `services/BoomBarrierWebhookService.java:146`.
- **The as-at query** — `GET /stock/as-at?at=…` answers a past balance **from the ledger**
  (`FR-013`), so reconstructibility is exercised in production and not only in tests.
- **The stable error-code vocabulary** (`FR-029`, `FR-039`): every refusal is an exception carrying a
  machine-readable code; every success returns a movement id the caller stores. The ledger never
  returns quietly.
- **`V500045`** — `whb_stock_position_snapshots` (partitioned by `snapshot_date`, non-zero positions
  only, `RL-011`) and `whb_position_drift_findings`.
- **The nightly rebuild that proves `L-4`** and writes findings to the drift table, plus the alert.

## `V500045` carries a `PNR-3` deadline

★ **`whb_stock_position_snapshots` is `PNR-3` for the snapshot job's start date.** Occupancy on each
past day cannot be cheaply reconstructed, so **ageing, days-on-hand, obsolescence and 3PL anniversary
storage billing all begin on the day the job was switched on** (`DATA-MODEL.md` `WHB-45`,
`IRREVERSIBLE.md` §3.2). Nothing breaks; truth is simply absent. **Switch the job on at go-live, not
when the first report is requested.**

## Traps

- **`accessory_stock_levels` has no concurrency control at all**, and the code comment names the
  race: `StockLevel` has no `@Version` (`entity:35-68`), `StockLevelRepository` has no `@Lock`
  (`:23-88`), there is **no `CHECK (quantity_on_hand >= 0)` in any migration**, and the negative
  guard is a Java read-compare-write —
  `InventoryStockAdjustmentService.java:63-72` says *"this only fires when that check raced against
  another movement"* (`C-024`). **All three** mechanisms, not one.
- **`issueStock()` silently no-ops when no stock-level row exists** —
  `InventoryStockAdjustmentService.java:56-60` — and `AccessoryIssuanceService.java:275-278` swallows
  non-`BusinessException` failures and continues (`C-025`). This is the exact shape `FR-029` forbids.
- **Reservations in `accessories` are schema-only**: `quantity_reserved` is read in 7 places and
  written in 0; `StockLevel.reserveQuantity()` / `releaseReservedQuantity()`
  (`StockLevel.java:189-206`) have **zero call sites** (`C-022`). Availability arithmetic here is
  net-new; assume no prior art.
- **`FOR UPDATE SKIP LOCKED` has zero occurrences in this repository** (`C-040`). It is not needed by
  this task, but it is needed by wave/pick claiming in `P3`, and the lock-ordering discipline this
  task states is what makes that safe later.
- **A *generated* available column is not a substitute for the three mechanisms** (`FR-016`) and it is
  stale in-session through JPA (`StockLevel.java:66-68`, R1 §8 trap `T-3`).
- **The rebuild must reproduce the position table *exactly*, not approximately.** `WH-SC-061` is a v1
  exit criterion: the rebuild reproduces the position report **row for row**. A rebuild that agrees
  on totals and differs on grain has not proved `L-4`.
- **A migration that only `RAISE NOTICE`s its checks is not verified** (plan §10). Assert with
  `RAISE EXCEPTION`.
- **Register the drift and snapshot grids' filter scopes in `filterUtils.ts`** — an unlisted field is
  silently dropped by `convertFiltersForApi()` and the filter appears to do nothing
  (`filterUtils.ts:346`, R1 §8 trap `T-6`). `snapshotDateFrom`/`To` are **`dateOnly`**, not `date`:
  `filterUtils.ts:49-56` documents that `date` shifts the lower bound to the previous calendar day
  for users east of UTC.
- **Both grids need `grid_preferences.default_columns` AND `default_filters`** as `'[…]'::jsonb`.
  `filter_definitions.default_visible = true` alone does **not** build the default strip
  (`V18:12`, `V229:50-51`, R1 §8 trap `T-8`).

## Acceptance
- [ ] An architecture test **fails the build** if any class outside the writer service writes
      `whb_stock_movements`, `whb_stock_movement_lines` or `whb_stock_positions` (`FR-436`)
- [ ] A full rebuild from `whb_stock_movements` reproduces **every** `whb_stock_positions` row
      exactly, and the nightly job reports zero findings on clean data (`WH-SC-061`)
- [ ] Deliberately corrupting one position row makes the job write a `POSITION_DRIFT` finding with the
      cached and rebuilt quantities and the difference, and raises the alert (`WH-SC-014`)
- [ ] `GET /stock/as-at?at=…` reproduces a past balance **from the ledger**, not from a snapshot
      (`WH-SC-040`)
- [ ] Two concurrent issues of the last unit: one succeeds, one is refused with a stable error code —
      **no over-issue, and no lost update** (`WH-SC-190`, `WH-SC-196`, `WH-SC-198`)
- [ ] Negative **available** is refused unconditionally; negative **on-hand** is permitted only where
      the item × site policy allows it, and every breach writes an insufficient-stock log row
      (`WH-SC-017`, `WH-SC-018`)
- [ ] The error-code vocabulary is published as an artefact, not scattered through `throw` sites
      (`WH-SC-041`)
- [ ] The snapshot job is scheduled, appears on **WS-064 Job Runs** (`P0-13`), and its start date is
      recorded in the install guide as the day the ageing reports begin
- [ ] `whb_stock_position_snapshots` is created partitioned by `snapshot_date`, a snapshot run writes
      no zero-quantity row, and next month's partition exists before the job needs it (`RL-011`)
- [ ] The writer and the snapshot job run on a fixed injected `Clock` and reproduce `recorded_at` and
      the day boundary deterministically (`RL-016`)
