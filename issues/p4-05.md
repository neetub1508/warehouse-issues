## Scope

- **MRP becomes a balance dimension, including for non-batch-tracked items** (`FR-321`), with a
  **stock-by-MRP report** and **MRP-inclusive back-calculation of the taxable value** on the issue
  document.
- **MRP lives on the lot, with an item-level default — it is *not* in the position unique key**
  (`OD-10`, `WH-SC-144`). Two batches of one SKU after a price revision are **already separate
  position rows because their lots differ**, so MRP segregation works without a tenth key member. The
  report reads MRP **through the lot**.
- `whb_lots.mrp`, `net_content`, `country_of_origin` and pack month/year shipped in **v1/P1**
  (`FR-320`, `V500018`). **This task writes no migration**; it is a report and a calculation over
  columns that already exist.
- **The back-calculation:** where a price is MRP-inclusive, the taxable value is derived by removing
  the tax component — computed on the **backend** in `BigDecimal`, with the rounding rule stated once
  (`DATA-MODEL.md` §5.3 / §5.4) and not re-derived per screen.

## Traps

- **`OD-10` is the tightest deadline in the whole programme and it is not this task's to answer.**
  *Is MRP a dimension of the stock position?* It must be answered **before `P0-02` writes `V500030`**
  — the migration that sets the position unique key and, in the same file, seals the ledger against
  `UPDATE` forever. The recommendation is **No**: MRP belongs on the lot. **This task reads it from
  there.** If `P0-02` shipped MRP in the key against the recommendation, this report is different and
  the position table is a tenth member wider; check what was actually built before writing the query.
- **A tenth key member is not free.** It multiplies every index and every rebuild on the hottest
  table in the product (`IRREVERSIBLE.md` §3.3, `DATA-MODEL.md` §7.7). The recovery, if MRP ever must
  join the key, exists **only** because `L-4` makes the position a cache **and only if the ledger
  line already carries the column** — so the argument is always about `whb_stock_movement_lines`,
  never about `whb_stock_positions`.
- **Non-batch-tracked items still need an MRP.** That is the specific words of `FR-321`. For an item
  with no lot, the MRP resolves to the **item-level default** (`FR-320`), and the report must show
  which source it used rather than rendering a blank.
- **The back-calculation is backend arithmetic.** There is **no decimal library on the frontend** —
  `ls */frontend/package.json` → **1 file**, 38 dependencies, no `decimal.js`/`big.js`
  (`PLATFORM-DEPENDENCIES.md` §2.11) — so an MRP-inclusive taxable value computed in the page is
  IEEE-754 and disagrees with the filed figure.
- **Rounding is stated once, not per screen.** `DATA-MODEL.md` §5.3/§5.4 carries the rule and the
  rounding-away-from-zero problem, which is sharper here than in accounting.
- **`asAtDate` computes from movements, never from the position cache** (`FR-328`).
- **`mrpFrom`/`mrpTo` are two `number` filter keys.** There is no range type — eight types only
  (`filterUtils.ts:30`) — and **both** keys go in `COMMON_FILTER_CONFIGS`, in
  `filter_definitions`, and in the API service's `getForManagement` list, or the filter renders and
  does nothing.
- **`whb_lots.mrp` is money and is `DECIMAL(19,4)`.** It is an extended retail price, not a per-unit
  cost.
- **`warehouse-india` may not add a column to a base table** (`D-11`). If the lot is missing an MRP
  field this is a `P1` amendment, not a `whin_` `ALTER`.
